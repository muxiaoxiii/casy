# Casy 真实案件测试前功能审查（2026-09-04）

## 结论

从“下周拿真实案件和卷宗文件试用”的角度看，Casy 现在已经可以进入受控 dogfooding：新建案件、导入进行中案件、归档文件、OCR/PageIndex、知识库沉淀、全局检索和 Markdown 写作链路已经形成闭环。

本轮在进入真实测试前排除了几类会直接影响信任的隐患：并行案件路由缺口、文件上传未先归档、PDF 页文本未进入全局索引、搜索特殊字符失败、收件箱归档分类漂移，以及编辑器/导出/打开路径的高风险安全点。

仍需把测试口径说清：PDF 处理依赖本机 `casy-doc-engine` 和 OCR 运行环境；Markdown 编辑器可用于办案记录、引用和导出，但“证据页码锚定、批注复核、引用反查”还不是最终律师工作台形态。

## 场景一：新建案件 + 新增卷宗文件

目标用户路径：新建案件 → 填基本信息/程序路由 → 上传 PDF/图片/文档 → 生成可搜索 PDF/PageIndex → 全局搜索/推理检索 → 沉淀知识 → 在 Markdown/文书中引用。

当前能力：

- 案件向导已支持 `caseRoute` 和三条程序状态字段，包含 `民事诉讼+行政诉讼` 这种并行路由。
- 案件创建时会把路由相关状态一起提交；无关程序状态写 `null`，避免误造另一条程序线。
- 案卷页普通“上传文件”已改为 `importToCase`，会先复制到案件归档目录再登记数据库，符合后端路径安全约束。
- 文档智能主路径会生成 `document_processing_jobs` 与 `document_pages`，处理完成后页文本进入 `document_pages_fts`。
- 全局搜索会同时查知识库、文件摘要和最新完成的 PDF 页文本，结果带 `[pN]` 页码摘要。
- PageIndex 可以再沉淀为知识库根笔记和结构化子笔记，供写作、引用和后续检索使用。

风险与测试重点：

- 上传后立即搜索不会命中 OCR 内容，必须等文档处理状态到 completed；UI 需要在 dogfooding 中观察提示是否足够明确。
- 扫描质量、表格、手写批注、双栏版式仍取决于 OCR 引擎实际效果，需要用真实卷宗抽样记录失败页。
- 大文件/多文件批量处理的队列恢复、失败重试和进度显示需要在连续使用中压测。

## 场景二：导入进行中并行案件

目标用户路径：从 Excel/飞书导入一个正在处理中的复杂案件，事实包含民事侵权诉讼和行政裁决/行政诉讼并行，已有案号、状态、日期、对方、法院/机关、材料目录和后续期限。

当前能力：

- Excel 与飞书导入都已识别 `民事诉讼+行政诉讼`，也能从“侵权、行政裁决并行”等自然描述推断并行路由。
- 导入字段映射已补齐 `caseRoute`、`civilStatus`、`invalidationStatus`、`adminStatus`、无效决定日期/类型、行政立案/裁判/二审日期。
- 更新已有案件时空值不会覆盖已有值，降低“导入表格某列为空导致业务数据被清空”的风险。
- 看板筛选能把组合路由同时纳入民事/行政视图，也可以单独按 `民事诉讼+行政诉讼` 过滤。
- Schema v25 会重建旧 `cases` 表约束，使真实库也能保存该组合路由，并保留旧案件和 `cases_fts` 搜索能力。

风险与测试重点：

- “行政裁决”在业务上可能指专利无效行政阶段，也可能指行政诉讼前置决定；当前路由已经支持民事+行政诉讼，但更精细的“行政裁决程序”仍需在真实样本中确认字段命名是否够贴近业务。
- 并行案件之间的材料、期限、任务可以关联，但还缺少面向并行程序的专门时间轴视图；真实测试时应记录律师是否需要一屏对照民事线/行政线。
- 关系合并和跨案引用已可做，但批量导入后自动识别同专利、同当事人、行政决定对应民事案仍是后续优化方向。

## PDF 与知识库索引

当前状态：

- `document_pages` 是页级事实表，保存 OCR 纯文本、Markdown、版面区域和置信度。
- `document_pages_fts` 是 v26 新增的 FTS5 trigram 索引，适合中文短语检索；新页由触发器自动同步，旧页在迁移时 rebuild。
- 全局搜索只取每个文件最新 completed job，避免旧 OCR 版本污染结果。
- 知识库自身仍走 `knowledge_fts`；PageIndex 沉淀后，PDF 全文和结构节点会作为知识笔记参与知识检索。

尚未完成的高阶能力：

- PDF 页索引已不是简单 LIKE 扫描，但还没有把页码、坐标、引用锚点暴露成统一前端结果模型。
- 知识库“全量索引”在数据库文本层面已经覆盖知识笔记和沉淀后的 OCR 文本；对未沉淀 PDF，也已由全局搜索覆盖页文本。下一步应把知识库搜索页也接入页级 PDF 结果，而不只在全局搜索里出现。
- 语义检索与页级 FTS 还没有统一 RRF 融合，真实材料量上来后可以根据命中质量再做排序优化。

## Markdown 编辑器

当前状态：

- TipTap/ProseMirror 编辑器已有基础富文本、Markdown 转安全 HTML、知识链接、块引用、证据链接、Copilot 侧栏和 DOCX 导出能力。
- 已修复知识块引用裸 `v-html` 与 WikiLink 建议浮层 `innerHTML` 风险，导入/OCR/AI 文本不会直接在编辑器里执行脚本。
- DOCX 渲染/导出返回字段已统一 camelCase，未填充字段告警和导出后打开文件可以正常消费返回结果。

仍需优化：

- 对律师真实写作来说，编辑器还缺“证据摘录 → 页码/坐标 → 文书引用 → 回跳原卷宗”的强闭环。
- 批注、修订痕迹、文书模板字段复核、脚注/法条引用格式需要用真实文书样本继续打磨。
- Markdown 足够做笔记和草稿，不建议把第一周测试目标设成“正式替代 Word 完成全套提交文书”。

## 真实测试建议

第一周建议按两套样本跑：

1. 新建一个干净案件，上传 5 到 10 个不同质量 PDF，记录 OCR 状态、页内搜索、PageIndex 沉淀、知识引用和导出文书的摩擦。
2. 导入一个进行中并行案件，检查路由、状态、日期、材料、任务、期限、看板筛选和搜索是否能还原现有办案上下文。
3. 每天只记录 P0/P1 摩擦：数据写错、搜不到应搜内容、文件打不开、状态不可理解、导出不可用、编辑器让人不敢继续写。
