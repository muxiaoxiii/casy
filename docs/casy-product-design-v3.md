# 上篇：产品定位

## 第一章 Casy 是什么

### 1.1 一句话定位

> **Casy 是专利律师的「全流程秩序引擎」。**

它不是案件管理工具，不是 GTD 工具，不是知识库——而是**三者合一的一个秩序系统**。

律师的工作环境比普通知识工作者更混乱：

- 事件突然涌现（收案、送达文书、对方反诉）
- 期限不可错过（上诉期 15 天、口审通知、答辩期）
- 大量时间在**等**（等法院裁定、等对方答复、等文书送达）
- 同一案件多轨并行（民事 + 无效 + 行政诉讼同时进行）

**Casy 的价值不是"帮你记更多"，而是"打开就知道——现在该做什么、在等什么、卡在哪"。**

### 1.2 为谁做

**核心用户**：专利律师（尤其是同时处理多个案件、多种程序类型的律师）

**用户画像**：
- 同时跟进 10-30 个活跃案件
- 每个案件涉及多个程序（民事诉讼、专利无效、行政诉讼）
- 期限敏感，错过一天可能导致不可挽回的后果
- 需要频繁切换上下文（从 A 案的答辩状切换到 B 案的证据整理）
- 积累大量可复用的知识（法律条文、判例、办案经验）但分散各处

**用户痛点**：
1. **信息孤岛**：案件信息在 Excel、邮件、微信、笔记本之间分散
2. **期限焦虑**：害怕错过任何期限，但手动跟踪 30 个案件的期限极易出错
3. **上下文切换成本**：刚进入 A 案的状态，被 B 案的紧急事项打断，再回来时忘了做到哪
4. **知识流失**：办案经验只存在于律师脑中，团队新人无法快速继承
5. **临时工作冲击**：确定的工作计划被临时插入的事项打乱，导致赶工

### 1.3 解决什么问题

| 问题 | Casy 的解法 |
|------|------------|
| 信息分散 | 案件 = 统一容器，所有相关信息（任务、文书、知识、期限）归集到案件下 |
| 期限焦虑 | 自动计算 + 分级预警（R1-R4），提前 7/3/1/0 天提醒 |
| 上下文切换 | 案件详情页 = 项目书，打开一个案件就看到全部状态 |
| 知识流失 | 知识库与案件关联，办案经验沉淀为可复用知识 |
| 临时冲击 | GTD 双轨设计：硬性日程锁定时间块，弹性任务按优先级动态调度 |

### 1.4 完全体愿景

> 所有的案件所有的信息，既相互隔离，又能通过某种方式链接，从而提供一种全面的反馈——信息流通、流程顺畅、反馈及时、推荐智能，系统与律师一同成长。

| 特征 | 含义 | 对应设计 |
|------|------|---------|
| **相互隔离** | 每个案件数据独立，不互相污染 | 案件独立存储 + 独立状态机 |
| **又能链接** | 客户/当事人/关联案件/共同任务可互联 | 方向感 Relation |
| **信息流通** | 一个入口改，相关处自动更新 | 任务↔案件↔知识 Relation + 状态自动推导 |
| **流程顺畅** | 案件推进有顺序，解锁无卡点 | 顺序项目 + blocked |
| **反馈及时** | 期限预警、进度可视化、状态变迁通知 | 主动智伴 |
| **推荐智能** | 越用越懂你，主动建议 | 行为学习 + 自动总结 |
| **一同成长** | 系统从用户使用中学习，反向服务用户 | task_events 行为沉淀 + 学习闭环 |

## 第二章 设计参考

### 2.1 我们研究过什么

Casy 的设计不是凭空产生的。在确定最终方案前，我们系统性地研究了大量工具：

- **GTD 工具**：OmniFocus、Things 3、Todoist、Microsoft To Do
- **日历工具**：Fantastical、Google Calendar、Apple Calendar、Outlook
- **知识管理**：Notion、Obsidian、Roam Research、Bear
- **法律工具**：AlphaLaw、法天使、无讼案例
- **通用工作流**：飞书多维表格、Airtable、Trello

### 2.2 我们吸收了什么

**从 GTD 方法论吸收的**：
- 收件箱 → 厘清 → 组织的流程
- "下一步行动"概念：项目只有当下可执行的一步
- 定期 Review 机制
- 上下文标签（@办公室/@电话/@法院）

**从日历工具吸收的**：
- Forecast 双栏布局：月历 + 未来几天预测
- 自然语言输入："明天下午3点"直接解析
- 颜色编码区分事件类型
- 时间块可视化

**从知识管理工具吸收的**：
- 双向链接：[[知识标题]]快速关联
- 块级编辑：段落级引用和嵌入
- 标签系统：多维度分类
- 全文搜索 + 语义检索

**从法律工具吸收的**：
- 案件结构化：当事人、案号、审级、代理阶段
- 期限计算规则：上诉期、答辩期、举证期限
- 文书模板：起诉状、答辩状、代理词

### 2.3 为什么最终这样设计

研究了这么多工具后，我们发现一个根本问题：**没有一款工具同时满足律师的全部需求**。

- GTD 工具擅长任务管理，但没有案件上下文
- 日历工具擅长时间安排，但没有任务深度
- 知识库擅长信息沉淀，但没有工作流驱动
- 法律工具擅长文书和检索，但没有个人工作流

**Casy 的解法：不是做一个"更好的 GTD 工具"或"更好的知识库"，而是把律师工作流的三个核心——案件管理、任务执行、知识沉淀——缝合成一个连贯的体验。**

三个核心不是简单拼接，而是有机融合：

- **案件给任务提供上下文**："写上诉状"不是孤立任务，而是"A 案民事诉讼轨的下一步"
- **任务给案件注入推进力**：案件不是静态档案，而是通过顺序项目自动推进的活流程
- **知识给两者提供弹药**：办案经验沉淀为知识，新知识反过来指导新案件

这就是"全流程秩序引擎"的含义——不是三个独立模块，而是一个流动的系统。

# 中篇：八大设计原则

## 原则一：案件即流程

**洞察**：律师案件是天然的线性流程——立案 → 庭前 → 庭审 → 判决 → 上诉。但用户永远只能看到"当前这一步"。

**设计**：
- 每个案件是一个顺序项目
- 只有 blocked=0 的行动对用户可见（"下一步行动"）
- 完成当前步 → 自动解锁下一步
- 案件详情显示"项目进度环"

**为什么这样设计**：
- 通用 GTD 工具的项目是通用的，无法表达法律程序的特殊性
- 法律程序有明确的先后顺序（不能先庭审再立案）
- 律师需要看到"这个案子现在卡在哪一步"
- 自动解锁减少手动维护，降低遗漏风险

## 原则二：时间双轨

**洞察**：律师 60% 以上的任务是"等 X 发生后才能做 Y"。只有 deadline 没有 start_date，语义全错。

**设计**：
- 每个任务有双轨：start_date（什么时候进入视线）+ due_date（什么时候必须完成）
- "等判决到了再写上诉状" = start_date = 判决送达日，due_date = 判决后 15 天
- 硬性日程（开庭/口审/期限）进日历
- 弹性行动进任务清单，两者在 Forecast 视图合一但视觉分区

**为什么这样设计**：
- 单轨时间（只有 deadline）强迫用户给"还不能做"的任务硬排日期
- 双轨让"等待中"的任务有正确的语义：不是"延期了"，而是"还没到开始的时候"
- Forecast 视图让律师一眼看到"接下来几天有什么硬性安排 + 有什么弹性任务可以插空做"

## 原则三：先捕获，后整理

**洞察**：要求用户"这条信息属于哪个数据库"是反人性的。灵感出现的那 3 秒里，大脑不该被归类问题占据。

**设计**：
- 任意页面都可触发极简捕获（Cmd+T/E/N/I）
- 输入框不要标题，自动用时间戳做标题
- 捕获结果默认进收件箱（待厘清），不进最终位置
- 厘清是一个独立的、明确的动作

**为什么这样设计**：
- 捕获和厘清是两个不同的心智模式：捕获需要快，厘清需要想
- 混在一起会导致"因为懒得想怎么分类，所以不记录了"
- 收件箱作为缓冲区，让用户放心丢东西进去，知道稍后会被处理

## 原则四：数据有限，视图无限

**洞察**：数据库的数量不是优点，而是维护的负担。任何"新需求"都应先问：它是不是现有 4 元信息的一个视图？

**设计**：
- 4 元信息：案件、任务、领域、知识
- 案件列表/看板/日历是同一份案件数据的三种视图
- 任务工作台的"今天/计划中/随时/等待"是同一份任务的推导视图

**为什么这样设计**：
- 数据模型膨胀是软件死亡的主要原因
- 4 个核心实体足够表达律师工作的全部信息
- 视图是廉价的，数据是昂贵的——优先做新视图而非新数据库

## 原则五：克制即优雅

**洞察**：「那些所谓的『情绪价值』在持续不断地侵蚀我的注意力——所有的元素都在告诉我『看，这里多漂亮』，而不是『来，请开始工作』。」

**设计**：
- 拒绝装饰性功能：不做天气、倒计时、滚动相册
- 信息按需披露：三层过滤（今天该看的 → 场景内必用的 → 用时才找的）
- 视觉克制：留白、单主色、语义色、线性图标

**为什么这样设计**：
- 律师的工作流本身就很复杂，界面不能再增加认知负担
- 每个像素都应该服务于"开始工作"这个目标
- 克制不是简陋，而是精准——只展示当下需要的信息

## 原则六：主动智伴

**洞察**：工具不该是"你问它才答"的被动数据库，而该是越用越懂你的主动协作者。

**设计**：
- 任务提醒：在正确的时机、用正确的方式、提醒正确的事
- 自动总结：每日早报/每周总结/案件复盘，系统原生自动生成
- 行为学习：记录任务完成时间分布，校准预估

**关键约束**：
- 双路径：确定性功能走规则引擎，智能功能走 AI——两条路物理隔离
- 确定性功能（期限/状态/逾期）不依赖 AI，AI 只是增强
- 用户可随时关闭 AI，系统完整运行

**为什么这样设计**：
- 律师对可靠性要求极高，不能容忍"AI 没联网所以期限算错了"
- 确定性功能用规则保证 100% 可靠，智能功能用 AI 提供增量价值
- 关闭 AI 后系统依然完整运行，这是对用户选择权的尊重

## 原则七：数据蒸馏

**洞察**：真正的软件不应该"数据一直很低"，而应该越用越值钱——随着使用积累海量数据，系统通过反复提炼自我进化。

**设计**：
- 三层记忆：L1 原始数据 → L2 提炼记忆 → L3 知识库
- 蒸馏循环：积累 → 提炼 → 确认 → 清理 → 循环
- 垃圾必须删：L1 有生命周期，过期即清
- 精华必须确认：L2 候选记忆经用户确认才进 L3

**为什么这样设计**：
- 不删垃圾，提炼就永远被噪音淹没
- 不经确认，AI 幻觉会污染知识库
- 记忆带出处，可反向核对来源
- 只提炼业务相关记忆，不做通用对话记忆

## 原则八：双向开放

**洞察**：Casy 不是封闭孤岛，而是双向开放的平台。

**设计**：
- 外部访问内部：MCP Server 暴露只读接口，外部工具可查询 Casy 数据
- 内部访问外部：Copilot 窗口调用外部 skill（文档生成/法律检索）
- 写操作需确认：外部 AI 不能绕过确认流程

**为什么这样设计**：
- 律师的工作流涉及多种工具（Word、法律数据库、邮件），Casy 不能替代所有工具
- 但 Casy 可以成为这些工具的"上下文中枢"——其他工具来 Casy 查数据，Casy 去其他工具调能力
- 写操作需要确认，是因为外部 AI 可能产生幻觉，不能让它直接修改案件数据

# 下篇：模块蓝图

## 第三章 任务工作台（GTD 心脏）

### 3.1 设计目标

任务工作台是 Casy 每天被打开的理由。它回答一个问题：**"我现在该做什么？"**

### 3.2 透视系统

| 透视 | 显示什么 | 解决什么问题 |
|------|---------|------------|
| 收件箱 | 未厘清的任务 | "刚丢进来的东西还没分类" |
| 今天 | start_date ≤ 今天 且 blocked=0 | "今天必须处理的" |
| 下一步 | 所有 blocked=0 的任务 | "所有可以马上做的" |
| 等待 | waiting_for 有值 | "在等别人回复的" |
| 回顾 | next_review_date ≤ 今天 | "需要定期检视的" |
| 某天 | start_bucket='someday' | "想做但不知道什么时候做" |

### 3.3 时间双轨

- start_date：任务进入视线的日期（"等判决到了再写上诉状"）
- due_date：任务必须完成的日期（"上诉期 15 天截止"）
- 时间块：上午/下午/晚上/深夜/弹性

### 3.4 设计理由

**为什么用透视而非文件夹**：
- 文件夹是静态的，透视是动态的
- 同一个任务可以在"今天"透视和"A 案"透视同时出现
- 减少用户维护分类的心智负担

**为什么有 start_date**：
- 没有 start_date，"等判决后再写上诉状"只能硬排一个 deadline
- 结果任务列表里全是"延期"的红字，制造无意义的焦虑
- start_date 让"等待中"的任务正确消失，直到可以开始做时才出现

## 第四章 案件详情页（项目书）

### 4.1 设计目标

案件详情页是 Casy 的上下文容器。它回答一个问题：**"这个案子现在怎么样了？"**

### 4.2 项目书结构

| 区域 | 内容 | 设计理由 |
|------|------|---------|
| 案件概要 | 案号、当事人、代理阶段 | 一眼识别案件身份 |
| 三轨状态 | 民事诉讼/专利无效/行政诉讼 | 一个案件可能多轨并行，需要分别看状态 |
| 下一步行动 | 第一个 blocked=0 的任务 | 打开案件就知道现在该做什么 |
| 顺序项目 | 案件流程推进 + 自动解锁 | 法律程序有先后顺序，不能跳步 |
| 关联资源 | 任务、文书、知识 | 案件相关的所有信息在一个页面 |
| 动态轨迹 | 时间线 | 案件历史一目了然 |

### 4.3 设计理由

**为什么是"项目书"而非"档案页"**：
- 档案页是静态的，项目书是动态的
- 律师打开案件不是为了"查看信息"，而是为了"推进工作"
- 下一步行动卡放在最显眼位置，因为这才是律师最关心的

**为什么有三轨状态**：
- 一个专利案件可能同时有民事诉讼（侵权）和专利无效（确权）
- 两轨进度不同，不能混在一起看
- 三轨（民事/无效/行政）覆盖专利律师的全部程序类型

## 第五章 日历（Forecast 双栏）

### 5.1 设计目标

日历回答一个问题：**"我接下来几天有什么安排？"**

### 5.2 Forecast 双栏

- 左栏：月历（快速导航）
- 右栏：未来 7 天预测（硬性日程 + 弹性任务）

### 5.3 设计理由

**为什么是双栏**：
- 单栏月历看不到未来几天的细节
- 单栏列表看不到全局时间分布
- 双栏兼顾"概览"和"细节"

**为什么日历显示任务 deadline**：
- 传统日历只显示"事件"（开庭、会议），不显示"任务截止"
- 但律师的 deadline（上诉期、答辩期）和事件一样重要
- 日历任务合一，避免在日历和任务清单之间来回切换

## 第六章 知识库（块级 + 双向链接）

### 6.1 设计目标

知识库回答一个问题：**"我之前办过类似案子，经验在哪？"**

### 6.2 职能分类

| 职能 | 用途 | 例子 |
|------|------|------|
| 灵感 | 临时想法、待整理 | "这个案子的争议点可能在于..." |
| 方法 | 办案流程、检查清单 | "口审准备清单" |
| 参考 | 法律条文、判例、模板 | "最高人民法院关于...的司法解释" |
| 问题 | 疑难问题、待研究 | "如何证明恶意注册？" |
| 经验 | 办案心得、教训 | "上次类似案子败诉的原因是..." |
| 日志 | 工作记录、时间追踪 | "2024-03-15 与客户会议" |

### 6.3 设计理由

**为什么是职能分类而非文件夹**：
- 文件夹是单维度的，一个知识只能放一个文件夹
- 职能是多维度的，同一个知识可以同时是"参考"和"经验"
- 职能反映知识的使用场景，而非存储位置

**为什么有双向链接**：
- 知识不是孤立的，"恶意注册证明方法"可能关联"证据规则"和"判例"
- 双向链接让知识形成网络，而非树状结构
- 写文书时输入 [[恶意注册]] 自动关联相关知识

## 第七章 收件箱（全能捕获）

### 7.1 设计目标

收件箱回答一个问题：**"刚收到的东西放哪？"**

### 7.2 捕获来源

| 来源 | 方式 | 场景 |
|------|------|------|
| 手动输入 | Cmd+T 快速捕获 | 突然想到一件事 |
| 文件 | 拖拽/选择文件 | 收到法院文书 |
| 邮件 | IMAP 自动抓取 | 客户发来邮件 |
| 语音 | 语音转文字 | 开车时想到的事 |
| 剪贴板 | 自动监听（可选） | 复制了一段重要文字 |
| 屏幕截图 | 截图入收件箱 | 网页上的重要信息 |

### 7.3 厘清流程

1. 这是什么？（任务/事件/笔记/文件）
2. 属于哪个案件？（系统辅助匹配）
3. 需要什么时候做？（start_date + due_date）
4. 转行动/等待/委派/某天

### 7.4 设计理由

**为什么捕获和厘清分离**：
- 捕获需要快（3 秒内完成），厘清需要想（可能需要查资料、问同事）
- 混在一起会导致"因为懒得想怎么分类，所以不记录了"
- 收件箱作为缓冲区，让用户放心丢东西进去

**为什么有系统辅助匹配**：
- 用户可能不知道这条信息属于哪个案件
- 系统根据内容文本匹配案件关键词，给出建议
- 用户确认或修改，系统从选择中学习

## 第八章 主动智伴（报表 + 提醒 + 学习）

### 8.1 设计目标

主动智伴回答一个问题：**"系统能帮我做什么？"**

### 8.2 报表体系

| 报表 | 频率 | 内容 | 用途 |
|------|------|------|------|
| 每日早报 | 每天 8:00 | 昨天完成/今天待办/逾期/等待 | 开始一天工作前快速了解全局 |
| 每周总结 | 周日 21:00 | 本周完成/下周计划/趋势 | 周末回顾，调整下周节奏 |
| 案件周报 | 每周 | 案件进展/下一步/风险 | 向客户汇报或团队同步 |
| 每月简报 | 每月 | 月度统计/客户报告 | 月度复盘，客户关系维护 |

### 8.3 提醒分级

| 等级 | 触发条件 | 渠道 | 设计理由 |
|------|---------|------|---------|
| R1 | 期限前 7 天 | 应用内角标 | 早期预警，让用户有心理准备 |
| R2 | 期限前 3 天 | 应用内 + 系统通知 | 需要开始安排了 |
| R3 | 期限前 1 天 | 弹窗 + 系统通知 + 飞书 | 紧急，必须今天处理 |
| R4 | 期限当天 | 全渠道 + 重复提醒 | 最后防线，不可错过 |

### 8.4 设计理由

**为什么报表是系统原生而非用户手动**：
- 律师太忙，没时间写周报
- 系统有全部数据，自动生成比人写更准确
- 自动报表确保不遗漏，人写容易漏掉某些案件

**为什么提醒要分级**：
- 所有提醒都一样重要 = 所有提醒都不重要（提醒疲劳）
- 分级让用户知道"这个有多急"
- R1 是"知道就好"，R4 是"必须现在处理"

## 附录：Casy 设计哲学一句话总结

> **四个元信息，两个时间轴，一条案件主线，一个主动智伴。**
> 
> 数据有限（4 认知对象），视图无限（透视）；捕获极简，整理后置；案件即流程，克制即优雅；
> 提醒分级，总结自动，越用越懂你；报表四维（日/周/月/项目），对内结构对外可读；
> 智能产出必确认，决策留痕可追溯，模型可换记忆不丢；
> 双向开放，组件分阶段，写入口唯一，上下文有界，依据可查。
