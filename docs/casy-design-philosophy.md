# 上篇：Casy 设计哲学

## 第一章 设计原点：Casy 是什么

### 1.1 一句话定位

> **Casy 是专利律师的「全流程秩序引擎」——它既不是案件管理工具，也不是 GTD 工具，更不是知识库，而是三者合一的一个秩序系统。**

对于律师来说，既有确定的工作要提前留足时间准备，又有突然插入进来的临时性的工作，帮助律师把各种工作料理好是Casy最主要的目的。所有的案件所有的信息，既相互隔离，又能通过某种方式链接，总而提供一种全面的反馈，信息流通、流程顺畅、反馈及时、推荐智能，系统与律师一同成长，这才是Casy的完全体。

律师的工作环境比普通知识工作者更混乱：

- 事件突然涌现（收案、送达文书、对方反诉、其他类型的工作）
- 期限不可错过（上诉期 15 天、口审通知、答辩期）
- 大量时间在**等**（等法院裁定、等对方答复、等文书送达）
- 同一案件多轨并行（民事 + 无效 + 行政诉讼同时进行）

**Casy 的价值不是"帮你记更多"，而是"打开就知道——现在该做什么、在等什么、卡在哪"。**

### 1.2 律师工作的双重性：确定工作与临时工作

定位段里的第一句值得单独展开，因为它是 Casy 存在的前提：

> 既有确定的工作要提前留足时间准备，又有突然插入进来的临时性工作。

**确定工作**（可规划）：

- 开庭前要准备：证据清单、质证提纲、代理词
- 期限驱动的流程：上诉期 15 天、答辩期、口审答复
- 这类工作**可提前排期、可分解、可预测**——需要 GTD 式的时间安排（`start_date` + `due_date`）

**临时工作**（不可预测）：

- 客户突然来电要一份合同审查
- 法院临时送达一份文书，需要当天处理
- 对方反诉、新证据、新传票突然插入
- 这类工作**无法提前规划，只能快速捕获 + 立即判断优先级**——需要极简捕获 + 灵活的"今日"调度

**这两类工作的冲突，正是律师最大的焦虑源**：确定工作的准备时间被临时工作挤占，导致期限被迫赶工。Casy 的双轨设计（硬性日程 vs 弹性行动）就是为了让两类工作各得其所：

- 确定工作 → 提前锁定时间块（日历 + 任务双轨）
- 临时工作 → 极简捕获 + 实时判断"是否比现在的任务更紧急"

### 1.3 三个导向：案件是锚点，项目是主线，客户是视角

> 这个软件虽然是 Case 导向，但实际上还是项目导向，甚至客户导向的。

这句话是理解 Casy 信息架构的钥匙，需要拆开看：

| 导向             | 是什么                          | 对应 Casy 什么                  |
| -------------- | ---------------------------- | --------------------------- |
| **Case 导向**    | 入口视角：律师点开一个案件，看到这个案子的一切      | 案件详情页（三轨状态 + 顺序流程 + 关联资源）   |
| **Project 导向** | 组织视角：一个案件 = 一个项目 = 一系列有顺序的行动 | 任务工作台（5 透视聚合所有案件的行动）        |
| **Client 导向**  | 长期视角：客户是比案件更稳定的单位，多个案件共享一个客户 | 客户维度聚合（客户端 + 名下所有案件 + 历史合作） |

**为什么 Case 导向不够**：案件是**有终点的**（结案、归档），而客户关系、律师的能力积累是**没有终点的**。如果一个律师只围着案件转，结案后所有关联就断了；但如果以客户为锚，结案只是一个里程碑，客户名下还会不断长出新案件、新委托。

**为什么 Client 导向还没进 4 元信息**：客户不是第五个"顶级认知对象"——**用户心智里依然是四大核心对象**。数据库层则增加 `clients` 基础主数据表（稳定 ID + 别名归一，见 architecture.md §5.2），案件通过 `client_id` 稳定归属客户。正如同一个案件可以有多轨，一个客户可以聚合名下所有案件、所有相关任务、所有相关文书。**这就是"既相互隔离，又能通过某种方式链接"的具体落点。**

### 1.4 为什么任务管理比案件管理更长远、更重要

> 为什么要花那么多篇幅在 GTD 上呢，就是因为其实任务管理比案件管理更长远也更重要。

这句话值得记入设计基准——它解释了整份文档的篇幅分配：

| 维度        | 案件管理        | 任务管理（GTD）       |
| --------- | ----------- | --------------- |
| **生命周期**  | 案件有终点（结案归档） | 任务贯穿律师职业生涯      |
| **连续性**   | 案件之间相互独立    | 任务流是连续的（永远有下一步） |
| **优先级**   | 案件是静态档案     | 任务反映当下的轻重缓急     |
| **跨案件价值** | 无法跨案复用      | 一个任务列表 = 全局视野   |

**案件是数据容器，任务是活的线索**。Casy 的案件提供"上下文"（这个案子的约束、期限、关联），任务提供"行动流"（我此刻该干什么）。一个只做案件管理的软件是档案库，加上任务管理才成为工作台——**任务管理是软件每天被打开的理由，案件管理是每次打开的上下文。**

这也解释了为什么 GTD 的设计（时间双轨、时间桶、顺序项目、透视）在整份文档中占这么大比重：**案件是 Casy 的骨架，任务是 Casy 的血液循环系统。**

### 1.5 完全体愿景：隔离 + 链接 + 成长

定位段里"Casy 的完全体"值得展开成明确的验收标准：

> 所有的案件所有的信息，既相互隔离，又能通过某种方式链接，从而提供一种全面的反馈——信息流通、流程顺畅、反馈及时、推荐智能，系统与律师一同成长。

| 完全体特征    | 含义                  | 对应设计                       |
| -------- | ------------------- | -------------------------- |
| **相互隔离** | 每个案件数据独立，不互相污染      | 案件独立存储 + 独立状态机             |
| **又能链接** | 客户/当事人/关联案件/共同任务可互联 | 方向感 Relation（第三章）          |
| **信息流通** | 一个入口改，相关处自动更新       | 任务↔案件↔知识 Relation + 状态自动推导 |
| **流程顺畅** | 案件推进有顺序，解锁无卡点       | 顺序项目 + blocked             |
| **反馈及时** | 期限预警、进度可视化、状态变迁通知   | 主动智伴（第十一章）                 |
| **推荐智能** | 越用越懂你，主动建议          | 行为学习 + 自动总结（原则六）           |
| **一同成长** | 系统从用户使用中学习，反向服务用户   | task_events 行为沉淀 + 学习闭环    |

**简言之：Casy 的完全体 = 数据隔离但互联（骨架）+ 流程自动推进（血脉）+ 智能主动反馈（大脑）+ 与律师一同成长（灵魂）。**

### 1.6 设计目标

| 目标     | 说明                               |
| ------ | -------------------------------- |
| **秩序** | 打开就知道现在该做什么、在等什么、卡在哪             |
| **流动** | 信息沿着"捕获 → 厘清 → 组织 → 执行 → 回顾"自然流转 |
| **克制** | 不堆功能，不炫技，拒绝情绪价值装饰                |
| **成长** | 系统从使用中学习，主动推荐，与律师一同成长            |

## 第二章 八大设计原则

### 原则一：案件即流程（案件 = 顺序项目）

**洞察**：律师案件是天然的**线性流程**：

```
诉讼轨：立案 → 庭前 → 庭审 → 判决 → 上诉
无效轨：受理 → 口审 → 决定
```

但**用户永远只能看到"当前这一步"**。GTD 的铁律："项目只有下一步行动可做"——顺序项目里第一个行动可用，后续全部阻塞，完成一个解锁下一个。

**Casy 的落点**：

- 每个案件是一个**顺序项目**（`cases.sequential = 1`）
- 只有 `blocked = 0` 的行动对用户可见（"下一步行动"）
- 完成当前步 → 自动解锁下一步（事务内更新）
- 案件详情显示"项目进度环"（剩余/总数读缓存字段）

**这是 Casy 区别于一切通用 GTD 工具的独有基因**——通用工具做纯"任务管理"，Casy 把任务放进**案件这个有法律上下文、有期限、有审级的容器**里推进。但注意（呼应 1.4）：案件是任务的组织容器，任务才是更长久的主线——顺序项目机制让"案件推进"变得可执行，而任务流本身始终连续。**案件给任务提供上下文，任务给案件注入生命力。**

### 原则二：时间双轨（When 与 Deadline 分离）

**洞察**：律师 60% 以上的任务是"**等 X 发生后才能做 Y**"：

- 等判决书到了 → 才能准备上诉状 → 上诉期 15 天截止
- 等对方提交答辩 → 才能开准备会议
- 等口审通知 → 才能订行程

现在 Casy 只有 `due_date`（截止），没有 `start_date`（开始）。结果"等判决后再写上诉状"这种任务只能硬排一个 deadline，语义全错。

**Casy 的落点**：

- 每个任务有双轨：`start_date`（什么时候进入视线）+ `due_date`（什么时候必须完成）
- "等 X 后才做 Y" = `start_date = X 发生日`，`due_date = X 后 N 天`
- **硬性日程**（开庭/口审/期限）进日历，**弹性行动**进任务清单，两者在 Forecast 视图合一但视觉分区

### 原则三：先捕获，后整理（不打断心流）

**洞察**：要求用户"这条信息属于哪个数据库"是反人性的。灵感、任务、日程出现的那 3 秒里，大脑不该被归类问题占据。

**Casy 的落点**：

- 任意页面都可触发**极简捕获**（Cmd+T/E/N/I 四个动作）
- 输入框**不要标题**，自动用时间戳做标题（不让你动脑）
- 捕获结果默认进**收件箱**（待厘清），不进最终位置
- **厘清**是一个独立的、明确的动作（转行动/等待/委派/某天），在专门的厘清界面做

### 原则四：数据有限，视图无限（4 元信息 + 透视）

**洞察**：

- 数据库的数量不是系统的优点，而是**维护的负担**
- 任何"新需求"都应先问：它是不是现有 4 元信息的一个**视图**？
- "今天/计划中/随时/等待"这类透视不该是存出来的，而该由字段推导

**Casy 的 4 元信息**：

| 元信息        | Casy 实体           | 数字化形态                 |
| ---------- | ----------------- | --------------------- |
| **案件（项目）** | `cases`           | 为达成诉讼目标发起的一系列任务       |
| **任务**     | `tasks`           | 驱动行动的最小单位             |
| **领域**     | `areas`（新建）       | 长期深耕的业务方向（专利诉讼/无效/顾问） |
| **知识（笔记）** | `knowledge_items` | 支撑案件/任务/领域运转的可复用信息    |

**Casy 的落点**：

- 案件列表/看板/日历是**同一份案件数据的三种视图**
- 任务工作台的"今天/计划中/随时/等待"是**同一份任务的推导视图**，不是独立存储
- 新增需求优先做"新视图"而不是"新数据库"

### 原则五：克制即优雅（建筑师，不做室内设计）

**洞察**：

> 「那些所谓的『情绪价值』在持续不断地侵蚀我的注意力——所有的元素都在告诉我『看，这里多漂亮』，而不是『来，请开始工作』。」

**Casy 的落点**：

- **拒绝装饰性功能**：不做天气、倒计时、滚动相册、五彩时钟
- **信息按需披露**：三层过滤（今天该看的 → 场景内必用的 → 用时才找的）
- **评估匹配类型**：计算型案件看 DDL 完成率、探索型看里程碑、成长型看连续性——不用单一指标制造焦虑
- **视觉克制**：留白、单主色、语义色、线性图标（详见下篇）

### 原则六：主动智伴（AI 越用越懂你）

**洞察**：AI 时代的工具不该是"你问它才答"的被动数据库，而该是**越用越懂你的主动协作者**：

> 任务提醒不该是"到点弹一下"，而是**在正确的时机、用正确的方式、提醒正确的事**。  
> 任务总结不该是"用户自己写周报"，而是**系统原生自动生成**——昨天做了什么、今天该做什么、哪些在等、哪些要关注。

**双路径铁律**（本原则的架构基石）：

> 系统的每一项功能，必须明确属于**去 AI 路径**或**含 AI 路径**，不得混用。

|         | 去 AI 路径（确定性）             | 含 AI 路径（智能）                |
| ------- | ------------------------ | -------------------------- |
| **性质**  | 本地实现 + 本地同步              | AI 参与判断/生成                 |
| **例子**  | 期限计算、状态推导、逾期判断、数据同步、CRUD | 推荐决策、报表叙事、知识提取、文案生成        |
| **依赖**  | 零 AI 依赖，纯规则/SQL          | 依赖 AI 抽象层（可切换模型）           |
| **可靠性** | 确定性，可直接信任                | 必须过"完整 → 可查 → 可信 → 递归确认"四关 |

**含 AI 路径的四道保障**（缺一不可）：

1. **信息完整（有界）**：AI 获得**对当前决策所需事实的完整上下文**，而非数据库全部相关数据——边界由 ContextPolicy（required_sources / max_depth / sensitivity_scope）显式定义，缺关键事实即信息不完整，但上下文不无界
2. **依据可查**：送给 AI 的每一条判断依据，都带 `source_ref`（正式 JSON schema：表/记录/字段/版本），可反向查到原始数据；多来源用 provenance 表
3. **结果可信**：推荐结果带置信度 + 引用溯源，低置信度强制人工确认
4. **递归确认**：用户确认不是终点，L3 场景还要做**二次递归确认**——把推荐结果与 ContextPolicy 界定的核对范围比对，发现遗漏/矛盾则打回

**三个学习层次**：

| 层次        | 学什么          | 怎么学                                                      |
| --------- | ------------ | -------------------------------------------------------- |
| **懂你的节奏** | 你的工作时段、提醒偏好  | 记录任务完成时间分布，避开深夜/休息时段推送                                   |
| **懂你的模式** | 你的任务耗时、延期习惯  | 统计每个任务的 `estimated_minutes` vs 实际耗时，校准预估；识别"总被拖到截止"的任务类型 |
| **懂你的业务** | 案件类型、客户、期限模式 | 从案件数据里学习：哪些类型的案件总在赶期限、哪些客户常延期、哪些期限容易漏                    |

**数据关联性双通道**（贯穿所有含 AI 功能的底层机制）：

> 数据的关联性，一半靠显性设置，一半靠 AI 学习。两者互补，缺一不可。

| 通道       | 机制                                              | 例子                                                       | 谁来维护        |
| -------- | ----------------------------------------------- | -------------------------------------------------------- | ----------- |
| **显性关联** | 通过参数、名称、分类、归属等**显式设置**建立关联                      | 案件字段、Relation 外键、标签、分类归属                                 | 用户设置 + 系统约束 |
| **隐性关联** | 把**全局数据 + 决策 + 关联文档要素**持续丢给 AI 分析，AI 发现数据间的隐性关系 | "张三案与赵六案都涉及同一专利，可合并策略"、"该客户历史常延期，建议预收"、"无效程序口审平均延迟 60 天" | AI 持续学习     |

**Casy 的落点**：

- **主动提醒**：期限引擎不只是"到期提醒"，而是分级预警（见下篇专用章节）
- **系统原生自动总结**：每日早报 / 每周总结 / 案件复盘，全部由后端定时器 + 本地 LLM 自动生成，不劳用户动手
- **行为数据沉淀**：新增事件表记录任务创建/完成/延期/提醒反馈，这是"越用越懂你"的数据基础
- **双路径实现**：确定性功能（期限/状态/逾期/同步）走规则引擎，智能功能（推荐/报表/提取）走 AI 抽象层——两条路物理隔离
- **递归确认**：推荐引擎产出 → 用户确认 → 二次递归比对（ContextPolicy 界定核对范围） → 落地（详见第十一章）
- **隐性关联学习**：周期性把全局数据 + 决策链 + 文档要素喂给 AI，产出"关联洞察"，沉淀为经验（详见第三章）

### 原则七：数据蒸馏与外置记忆（软件自我进化）

**洞察**：真正的软件不应该"数据一直很低"，而应该**越用越值钱**——随着使用积累海量数据，系统通过**反复提炼**自我进化：

> 反复提炼 = 删除垃圾 + 保留重要的东西 + 存储。软件本身要有自己的"知识库"，相当于 AI 的**外置记忆**——但它只记住**与 Casy 业务相关的记忆**，不做全 AI 通用记忆。

**Casy 的记忆边界**：

| 维度 | Casy 专属外置记忆 |
| ---- | ---------------------------- |
| 记忆范围 | 只记与案件/任务/客户/期限/决策/经验相关的 |
| 存储位置 | 本地 SQLite（Casy 知识库） |
| 增长方式 | **蒸馏循环**：积累 → 提炼 → 删垃圾 → 存精华 |
| 可查性 | 每条记忆带来源引用（source_ref） |

**三层记忆架构**：

```
┌─────────────────────────────────────────────┐
│  L1 原始数据（Raw）—— 海量，含垃圾             │
│  task_events / daily_stats / inbox / logs    │
│  · 保留期限：自动清理（如 90 天前的原始事件）   │
├─────────────────────────────────────────────┤
│  L2 提炼记忆（Distilled）—— 精华，经过确认      │
│  decisions / ai_insights / 经验笔记            │
│  · 由 L1 蒸馏而来，带来源 + 确认状态           │
├─────────────────────────────────────────────┤
│  L3 知识库（Knowledge）—— 长期，可复用          │
│  knowledge_items（6 职能分类）                │
│  · 最高价值，永不删除，可检索可引用             │
└─────────────────────────────────────────────┘
```

**蒸馏循环（核心机制）**：

```
① 积累：原始数据进入 L1（行为/事件/收件箱/日志）
     ↓
② 提炼：周期性任务（如每周）把 L1 数据 + L2 决策喂给 AI
    → 产出候选记忆（经验/模式/洞察）
     ↓
③ 确认：候选记忆进确认区，用户采纳 → 进入 L2/L3
    · 采纳 → L3 知识库（带来源）
    · 拒绝 → 丢弃（不污染长期记忆）
     ↓
④ 清理：L1 定期删除过期原始数据（垃圾），L2 归档陈旧记忆
     ↓
⑤ 循环：下一轮提炼基于更干净的 L2/L3，越提越精
```

**关键设计**：

1. **垃圾必须删**：原始数据（L1）有生命周期，过期即清——不删垃圾，提炼就永远被噪音淹没。这是"删垃圾"的落点
2. **精华必须确认**：提炼出的候选记忆（L2）必须经用户确认才进 L3，防止 AI 幻觉污染知识库
3. **记忆必须带出处**：每条 L2/L3 记忆带 `source_ref`（从哪些原始数据/决策提炼而来），可反向核对
4. **重复必须合并**：近似记忆定期合并（"无效口审平均延迟 60 天"出现了 3 次 → 合并为 1 条并提升置信度）
5. **陈旧必须归档**：长期没被引用的记忆 → 活跃 → 陈旧 → 归档，防止知识库膨胀
6. **Casy 专属**：只提炼与业务相关的记忆（案件类型规律、期限模式、客户习惯、办案经验），不做通用对话记忆

### 原则八：双向开放（外部访问内部 / 内部访问外部）

**洞察**：Casy 不是封闭孤岛，而是一个**双向开放的平台**：

> 一方面，针对内部数据，AI 是可以进行修改的（经确认流程）；
> 另一方面，应该主动引入一些 skill 去处理特定的问题——尤其是文档生成部分（已有专门的 Copilot 窗口）。
> 所以需要考虑外部访问内部、内部访问外部的部分。

**三个开放方向**：

```
┌─────────────────────────────────────────────────┐
│                Casy 双向开放                       │
├─────────────────────────────────────────────────┤
│  ① 外部访问内部（对外暴露）                        │
│     外部工具（Claude Code/Pi/Codex/其他 AI）      │
│     → MCP Server 接口读 Casy 数据                 │
│     → 查询案件/任务/期限/知识，辅助外部 AI 工作     │
│     → 写操作需权限确认（与 Confirmer 联动）       │
│                                                 │
│  ② 内部访问外部（引入 skill）                     │
│     Casy 的 Copilot 窗口 → 调用外部 skill         │
│     → 文档生成（答辩状/上诉状/代理词）             │
│     → 法律检索/文书格式化/翻译等特定任务           │
│     → skill 按需加载（默认少，扩展多）            │
│                                                 │
│  ③ 轻量 harness 嵌入                            │
│     极简 harness 可直接嵌入                       │
│     → 复用其工具循环/状态管理，不重复造轮子        │
│     → 与 Casy 自己的智伴层互补                    │
└─────────────────────────────────────────────────┘
```

**关键机制**：

- **默认不堆工具**——Casy 的智伴层默认只做核心推荐/报表，特定任务（文档生成/法律检索）通过 skill 按需加载
- **skill 是扩展点**——每个 skill 带自己的说明和工具，需要时再读，不占常驻上下文
- **智伴层组件化（分阶段）**——推荐器/确认器/报表器先用 trait + enum 切换，配置决定组合，不写死流水线；真需要第三方插件时再上注册表（避免过度工程）
- **确认策略按场景挂载**——内部推荐 L1 / 结构化提取 L2 / 外部写 L3 / 文档生成 L2草稿 / 决策变更 L3+递归；最终等级 = effective_policy，`system_minimum` 不可被降低
- **事件与审计分离**——task_events 专职行为学习；ai_runs/ai_context_items 专职"模型可见即记录"；audit_events 专职领域事件
- **harness 可嵌入**——评估嵌入极简 agent harness（文档生成场景），复用工具循环，保留 Casy 智伴层做业务判断
- **"模型可见即记录"不变量**——任何到达模型的内容必须能从 `ai_runs` + `ai_context_items` 重建，这是"依据可查"的架构级保证

**Casy 的落点**：

- **MCP Server**（对外）：Casy 暴露只读接口（案件/任务/期限/知识），外部工具可查询；写操作经权限确认（system_minimum=L3）
- **MCP Client / Skill Runner**（对内）：Casy 调用外部 skill，按需加载，文档生成优先
- **权限确认**：外部访问内部的写操作，必须走确认流程（复用 11.4 Confirmer + effective_policy），外部 AI 不能绕过
- **隐私分级联动**：外部访问同样遵守 3.12 隐私分级——敏感字段不外泄
- **harness 嵌入**：评估嵌入极简 harness（文档生成场景），复用工具循环，保留 Casy 智伴层做业务判断
- **智伴层组件化（分阶段）**：M0-P2 用 trait + enum 切换组件，第三方插件需求出现时才升级 registry
- **确认策略按场景挂载**：内部推荐 L1 / 结构化提取 L2 / 外部写 L3 / 文档生成 L2草稿 / 决策变更 L3+递归；最终等级 = effective_policy
- **"模型可见即记录"不变量**：任何到达模型的内容必须能从 `ai_runs` + `ai_context_items` 重建（长期保留，不做 90 天清理）——这是"依据可查"的架构级保证

## 第三章 元信息模型（数据骨架）

### 3.1 四大实体 + 方向感关联

```
                    ┌─────────────┐
                    │  领域 Area   │  ← 长期业务方向
                    └──────┬──────┘
                           │ belongs_to（方向感：短期努力→长期方向）
                    ┌──────┴──────┐
                    │  案件 Case   │  ← 项目（顺序流程）
                    └──────┬──────┘
                           │ belongs_to（方向感：任务→目标）
              ┌────────────┴────────────┐
              │                         │
     ┌────────┴────────┐       ┌────────┴────────┐
     │   任务 Task      │       │   知识 Note      │
     │  action/waiting  │       │  6 种职能分类     │
     └────────┬────────┘       └────────┬────────┘
              │                         │
              └───────── references ────┘
              （方向感：给要做的事背景参考）
```

**方向感关联**不是"指针"，而是**带角色的关系**：

| 关联      | 角色语义         | 律师场景               |
| ------- | ------------ | ------------------ |
| 任务 → 案件 | 这件小事朝向哪个目标   | "起草答辩状"属于"张三专利侵权案" |
| 案件 → 领域 | 短期努力推动哪个长期方向 | 侵权案属于"专利诉讼业务线"     |
| 知识 → 案件 | 给案件提供背景参考    | 案例笔记关联到正在办的案件      |
| 知识 → 领域 | 可复用经验进能力仓库   | 无效决定模板属于"专利无效"业务线  |

**客户：认知上是聚合维度，数据库里是基础主数据（v2.8 修订）**：早期设计坚持"客户不建表，只作 `cases.client_name` 聚合"。但客户年度报告、客户历史行为、客户延期模式、`decisions.entity_type='client'` 等后续设计已把客户当实体使用——**"腾讯科技 / 腾讯科技有限公司 / Tencent" 到底是不是同一客户？改名后历史案件和 AI 记忆怎么关联？**

因此数据库新增 `clients` 表（稳定 ID + 别名归一，见 architecture.md §5.2），**用户认知上的四大核心对象（Area/Case/Task/Knowledge）不变**——clients 是 reference entity / 基础主数据，不是第五个顶级模块。"数据有限、视图无限"约束的是**产品认知复杂度**，不是数据库不能正常化。客户端（客户 → 名下所有案件 → 相关任务 → 相关文书）依然是聚合视图，只是现在基于稳定的 client_id 聚合。

### 3.2 数据关联性双通道（本架构的关键机制）

> **原理**：数据之间的关联，一半靠显性设置，一半靠 AI 学习。二者互补，构成"既相互隔离，又能通过某种方式链接"的完全体。

#### 通道 A：显性关联（Explicit Relation）

用户通过**显式设置**建立的关联，是可查、可编辑、确定性的。

| 显性关联方式   | 实现                   | 例子                                   |
| -------- | -------------------- | ------------------------------------ |
| **参数关联** | 案件/任务/知识上的属性字段       | `client_name`、`case_type`、`operator` |
| **名称关联** | 同一名称跨表匹配             | 同一客户名下的所有案件                          |
| **分类关联** | 6 职能分类 / 轨道分类 / 业务领域 | 知识按"经验/方法/参考"分类                      |
| **归属关联** | 表间外键 / Relation 字段   | 任务 → 案件、知识 → 案件、案件 → 领域              |
| **时间关联** | 日期字段的并集              | 同一期限段的所有案件                           |

显性关联是**确定性**的：谁建的、怎么建的、指向哪里——全部可查，永不丢失。这是系统的"骨架"。

#### 通道 B：隐性关联（Learned Relation）

AI 从**全局数据 + 决策链 + 关联文档要素**中持续学习出的关联，是动态的、不断进化的。

```
输入（周期性任务，如每周）：
  ├── 全局数据（所有案件/任务/期限/客户/知识）
  ├── 决策链（decisions 表：用户做过什么选择、为什么）
  └── 关联文档要素（文书/邮件/收件箱的要点）

AI 分析 → 产出"关联洞察"：
  ├── "张三案与赵六案涉及同一专利，建议合并策略"
  ├── "该客户历史 3 案均延期，下次接案建议预收 30%"
  ├── "无效程序口审平均延迟 60 天，期限规划应预留"
  ├── "李四案与王五案都是被告，可复用同一套答辩策略"
  └── "上周你拒绝了 2 次'立即上诉'建议——是否倾向先和解？"

落库：ai_insights 表（带置信度 + 数据来源引用）
沉淀：用户确认/修正的洞察 → 进入 knowledge_items（经验类）
```

**关键设计**：

1. **隐性关联必须有出处**：每条 AI 洞察带 `source_ref`（基于哪些数据得出），可反向核对
2. **隐性关联必须经确认**：AI 洞察不是直接生效，进"洞察确认区"，用户采纳后转为正式关联/经验
3. **隐性关联持续进化**：每次用户操作（决策、修改、拒绝）都是新学习样本，洞察会随使用变准
4. **双通道汇合**：用户把 AI 洞察转成显性关联（如手动把两案标记为关联案件）→ 隐性变显性，沉淀为确定性数据

#### 双通道的关系

```
显性关联（骨架）：确定性、可查、用户维护
    ↑ 用户采纳后固化
隐性关联（血肉）：动态、AI 学习、持续进化
```

**为什么必须双通道**：只靠显性，关联全靠用户手动建，成本高且漏掉隐性的模式（"这两个案其实有关联"）；只靠隐性，关联不可控、不透明、可能幻觉。**显性保底，隐性进化，AI 洞察经确认固化进显性**——这就是"AI 越用越懂你"在数据层的实现。

### 3.3 核心机制（Casy 自身的设计语言）

| 机制               | Casy 落点                                                      |
| ---------------- | ------------------------------------------------------------ |
| **effective 继承** | 案件设了期限，子任务没设 → 有效截止=案件期限                                     |
| **统计预缓存**        | 案件存 `overdue_task_count`/`remaining_task_count`，侧边栏红点/进度环读缓存 |
| **状态缓存标志**       | 任务存 `is_overdue`/`due_soon`，日历颜色编码读缓存                        |
| **时间桶枚举**        | 任务 `start_bucket`（inbox/anytime/someday/today），视图由它推导        |
| **手动排序索引**       | Today 列表拖拽重排只改整数，不改日期                                        |
| **Review 回顾**    | 案件 `next_review_date`，到期自动进回顾透视                              |
| **顺序项目 blocked** | 案件 `sequential=1`，只有 blocked=0 的行动可见                         |

### 3.4 案件 = 三轨状态机 × 顺序项目

这是 Casy 独有的**双维度案件模型**：

```
横向：轨道状态（三轨并行，见 modules/02-status-machine.md）
  诉讼轨 14 档 / 无效轨 6 档 / 行政轨 7 档
  ↕ 同一案件可同时在多轨（民事 + 无效 + 行政）

纵向：项目推进（顺序流程）
  只有 blocked=0 的下一步行动可见
  完成一步 → 解锁下一步 → 状态自动变迁
```

**轨道回答"这个案子法律上走到哪了"，顺序项目回答"我此刻该推进哪一步"**。两者正交，互不干扰。

# 中篇：模块改造蓝图

## 第四章 导航架构（三层信息过滤）

### 4.1 现状与问题

现在的左侧侧边栏 7 个菜单平铺（首页/案件/任务/日历/收件箱/知识库/设置），所有菜单同级。用户必须自己决定"现在该去哪个"——这正是"信息平均铺开，不知所措"。

### 4.2 目标架构

```
【第一层：全局聚合】永远能看到"今天最重要的事"
  ✓ 今日面板（顶栏常驻）
    · 硬性日程（开庭/口审/期限）
    · 今天到期的任务
    · 等待超过 3 天的
    · 需要回顾的案件

【第二层：核心模块】左侧侧栏（80% 的日常操作）
  📁 案件工作台（按轨道分组，内含"客户"透视入口）
  ✓ 任务工作台（GTD 透视）
  📅 日历（Forecast 布局）
  📚 知识库（按职能分类）
  📥 收件箱（待厘清 / 已厘清）
  ⚙️ 设置

【第三层：模块内 Tab】低频分析，用时才找
  案件：全部 / 我负责 / 等待中 / 已结案 / 按客户 / 周报
  任务：下一步 / 等待 / 今日 / 回顾 / 全部
  知识：经验 / 方法 / 灵感 / 问题 / 日志 / 参考
```

**客户视角的入口**（呼应 1.3 客户导向）：不新增顶级菜单，而是嵌在案件工作台内——`按客户` Tab 按 `client_id` 聚合案件（显示 `client_name`），点开客户卡片看到：名下案件数 / 进行中 / 等待中 / 快到期 / 历史结案。客户是案件的聚合维度（见 3.1），不需要独立成模块。

## 第十一章 主动智伴（推荐决策 + 智能提醒 + 自动总结）

> 本章是原则六的落地设计，也是 Casy 区别于传统工具软件的**差异化核心**——AI 越用越懂你。核心是 11.6 的**AI 推荐决策引擎**：抽取信息 → AI 生成推荐 → 用户确认 → 递归确认 → 落地执行 → 反馈学习。

### 11.1 现状与问题

按源码核验（2026-08-14），提醒的**真实现状**如下，与"多通道提醒已可用"的对外口径不同：

- `reminder_rules` / `reminder_log` 表与默认规则种子已落库（schema v5），`commands/reminder.rs` 提供了规则 CRUD、`test_reminder`、`start_reminder_engine`、`get_reminder_log` 命令。
- **但提醒引擎未在应用启动时拉起**：`lib.rs` 的 setup 只启动了每日 00:01 期限重算（`deadline_recalc_scheduler`）与飞书数据同步 watcher，`start_reminder_engine` 未被调用，周期检查当前不运行。
- **飞书消息/任务通道是占位**：`dispatch_reminder` 对 `feishu_message`/`feishu_task` 只返回成功并写 `reminder_log`（状态 `sent`），并未真正调用飞书 API；`send_feishu_reminder_async` / `create_feishu_task_reminder_async` 仍是 `dead_code`。
- 前端**没有**提醒规则/日志界面；本地/系统通知通道只对在线进程生效。
- 飞书自动 PUSH（`AutoPushManager`）是**案件数据同步**（5 秒防抖写回 Bitable），不是提醒，且同样要求应用在线。

由此形成待解决的设计问题：

- 应用在线时：提醒触发、同日去重、本地/系统通知可用（补上启动拉起即可工作）。
- 应用离线时：**无法保证准时提醒**——本地定时器、托盘、飞书 PUSH 全部失效，重启后只有尽力而为的补偿扫描。
- 现有触发条件是 `days_diff == trigger_days` 严格相等，离线数天后错过的 T-N 天预警无法自动补发（`task_due/task_overdue` 用 `<=` 可补）。
- 提醒后无反馈回收——不知道用户是否处理，无法学习。
- 所有提醒同一强度，没有分级策略的落地运行（规则表有，引擎未跑）。

### 11.2 主动提醒（分级预警 + 时机智能 + 离线送达语义）

> 提醒等级统一使用 **R1-R4**，避免与 AI 确认等级（L1-L3，见 11.4）混淆。

#### 分级预警（R1-R4，以期限引擎为基础）

| 级别          | 触发        | 方式            | 内容                 |
| ----------- | --------- | ------------- | ------------------ |
| **R1 温和**   | 截止前 T-3 天 | 收件箱角标 + 状态栏黄点 | "×天后到期"            |
| **R2 明确**   | 截止前 T-1 天 | 系统通知 + 应用内横幅  | "明天到期：上诉状，关联案件张三案" |
| **R3 强提醒**  | 到期当天      | 弹窗 + 通知中心置顶   | "今天到期，请优先处理"       |
| **R4 逾期追踪** | 超过截止      | 逾期视图 + 每日早报提醒 | "已逾期 N 天"          |

#### 时机智能（懂你的节奏）

- 学习用户完成任务的时间分布，提醒尽量落在用户活跃时段
- 上午 9 点前不推送 R3 强提醒（除非紧急）
- 等待类任务（waiting）到期后，**主动追问**："还在等法院答复吗？要发个催办吗？"——生成跟进动作

#### 上下文提醒（懂你的业务）

- 明天开庭 → 今晚提醒"检查证据清单 + 庭前准备"（自动生成准备清单任务）
- 口审前 → 提醒"无效理由是否已全部提交"
- 顺序项目解锁 → 主动告知"下一步可以开始：起草答复意见"

#### 离线提醒与送达语义（v2.3 收口：日历同步实现离线准时）

> **结论先行：Casy 本地进程确实无法在关机/休眠/退出/断网时触发提醒**（技术事实）。但"离线准时提醒"不必由 Casy 自己实现——**M1 起通过日历/日程同步（CalDAV + ICS via Email）把提醒固化为日程事件，同步到用户已有的 Google/Apple/Outlook 日历，由日历服务商 24/7 在线的推送基础设施负责准时送达**。完整技术决策见 architecture.md 第九章。

**四层语义**（统一口径，UI/文档/日志共用）：

| 层 | 含义 | 现状 |
|---|---|---|
| **① 计算正确** | 期限/开庭/任务触发条件由本地规则引擎确定性地算对 | ✅ 可离线计算（`deadline/engine.rs`） |
| **② 进入发送队列** | 提醒固化为可持久化、可重试、可对账的作业 | ⚠️ 现状只有 `reminder_log` 事后日志；M1 引入 `reminder_jobs`（architecture.md §9.6） |
| **③ 服务端接受** | 通道（日历服务 CalDAV / 邮件 SMTP）确认接受事件 | ⚠️ 未接通；M1 接通，日历服务返回 ETag/事件 ID 即接受 |
| **④ 终端实际送达 / 用户已读** | 推送真正到达用户设备、用户已读/已处理 | ❌ 无法保证；`delivered/read` 必须来自回执或用户确认 |

**日历服务接受 ≠ 用户已读**：ETag / Message-ID 只代表事件已入日历/邮件已发，不等于已送达，更不等于用户已读。`reminder_log` 的 `sent` 只表示"本地声称已发出"。提醒记录 UI 必须区分"日历已就绪 / 已发送 / 已送达 / 用户已处理"，禁止把同步成功推断为"用户看到了"。

**四种方案与推荐**（详见 architecture.md §9.4-9.5）：

- **方案 A 纯本地**（原生通知 + 启动补偿）：**M0 默认能力**，始终保留兜底。应用在线时触发，离线期重启后补偿扫描；明确标注"M0 尽力而为"。
- **方案 D 日历/日程同步（CalDAV + ICS via Email）：M1 推荐**。Casy 不自己推送，把提醒固化为日程事件（iCalendar .ics），通过 CalDAV（Google/Apple/Outlook，通常即用户的邮箱账号）同步到用户日历，或通过 SMTP 发送 ICS 邀请（也支持给当事人/同事发日程）；日历服务商在到期前按 alarm 跨设备推送（移动/邮件/桌面）。**零自建基础设施、零凭据托管（CalDAV/OAuth/SMTP 只存本地 keyring）、可靠性远超自建**。Casy 离线、关机、退出均不影响。
- **方案 B 自建云端中继（降级为备选）**：仅当"不配置日历 + 必须飞书渠道 + 接受自建服务"的明确需求出现时评估，不默认立项。需要自建常驻服务 + 托管飞书发送凭据 + 全套 SLO 运维，成本远高于方案 D。
- **方案 C 移动端伴侣**：**不是离线准时推送的前置条件**——移动端后台同样受 iOS/Android 系统限制，要可靠推送仍需 APNs/FCM 或常驻服务。方案 D 已通过日历生态覆盖移动端提醒（日历 App 自带推送），只有移动办公、移动录入/查阅等**独立需求**成立时才立项（architecture.md §9.4-9.5）。

**高敏案件**：对高敏案件（涉密/大额/客户指定保密）允许只同步脱敏摘要或**不出端**（只在应用内提醒）。案件级配置通知策略 ∈ {完整, 脱敏摘要, 不出端}，默认脱敏摘要；开启前弹风险提示："日程内容会出现在你的日历应用（及关联设备）中，可能被他人看到；选择'不出端'则提醒只在应用内展示。"

**阶段路线（与第十三章一致）**：

- **M0**：接通 `start_reminder_engine` 启动拉起 + 补偿扫描改区间触发；设置/日志明示"M0 本地提醒为尽力而为，配置日历同步后离线准时"。
- **M1**：**日历/日程同步（方案 D）**——接通 CalDAV（Google/Apple/Outlook）+ ICS email 邀请；提醒固化为日程事件由日历服务准时提醒；案件级通知策略（完整/脱敏/不出端）；`reminder_jobs.executor=calendar`；本地在线时飞书通道作为补充渠道。
- **移动端**：仅当移动办公、移动录入/查阅等独立需求成立时立项。

> **承诺边界**：M1 只对"已收到日历同步确认（ETag/事件 ID）"的提醒作业承诺准时——此时执行方是日历服务商，与 Casy 本地是否在线无关。尚待同步的本地变更，以及 Casy 离线时从未接入的新数据，不属于准时承诺。同步结果不明时必须对账，不能为了追求"必达"而盲目重复 PUT。

### 11.3 自动报表体系（日 / 周 / 月 / 项目 + 对内对外双轨）

> **核心原则：报表是系统自动生成的，不是用户自己写的。** 用户只需要在早晨打开、在周日扫一眼、月底看趋势、结案时看总结。

报表按**四个维度**自动生成，每个维度都有**对内/对外两个版本**：

| 维度      | 触发时机        | 对内版（结构化存储）       | 对外版（提升可读性）         |
| ------- | ----------- | ---------------- | ------------------ |
| **每日**  | 每天 8:00     | 结构化数据（JSON/DB 行） | 每日早报（Markdown，可分享） |
| **每周**  | 周日晚         | 周统计表（结构化）        | 周报（可发给主任/团队）       |
| **每月**  | 月末 23:00    | 月统计表（结构化）        | 月度简报（可发客户）         |
| **每项目** | 案件结案 / 客户周年 | 案件/客户数据汇总        | 项目结案报告 / 客户年度报告    |

**关键设计：对内对外的分界**

> **对内的，更多用结构化语言或数据库存储**——服务系统分析、回顾、学习，是"机器可读"的。  
> **对外的，尽可能提升可读性**——服务人的阅读，是"人可读"的。

```
对内报表（数据结构）：
┌────────────────────────────────────┐
│ daily_stats 表                     │
│ ├── date, task_done, task_total    │
│ ├── overdue_count, overdue_days    │
│ ├── hearing_count, deadline_count  │
│ ├── waiting_overdue_3d             │
│ └── case_transitions (JSON)        │
└────────────────────────────────────┘
  ↑ 数据库/JSON，系统可分析、可对比、可学习

对外报表（人读）：
┌────────────────────────────────────┐
│ 早安，王律师。今天是 8月14日 周五。    │
│ 【昨日回顾】 完成 6/9，比上周五高12%  │
│ 【今日要点】 14:00 口审 · 上诉状到期  │
│ 【等待跟进】 3 个等待超 3 天          │
└────────────────────────────────────┘
  ↑ Markdown，可复制、可导出、可发客户
```

**对外版本提升可读性的手段**：

- 自然语言叙事（不用表格堆砌）
- 重点加粗 / 分级标题
- 可导出 PDF / Word（客户报告、主任汇报）
- 附上"数据来源"（哪个案件、哪条期限）——可追溯

**四种对外报表形态**：

**① 每日早报**（对外可读版）：

- 对外版本作为**可编辑的文档**存库，用户可以改写、分享
- 用户对报表的修改 = 对 AI 的学习反馈（修正下次生成）

### 11.4 AI 输出确认机制（防幻觉，防遗漏）

> **核心原则：AI 生成的内容，永远不是最终答案。** 无论是总结、建议、还是从文书提取的信息，落地前必须经过确认。

**为什么必须确认**：

- LLM 可能幻觉（编造案号、期限、法条）
- LLM 可能遗漏（丢了一条关键期限、一个关联案件）
- 用户当前可能在用不同质量的模型（本地 Ollama vs 云端 API）
- 法律业务错误的代价极高——漏一个期限可能败诉

**三级确认策略**：

| 级别          | 场景                    | 做法                     |
| ----------- | --------------------- | ---------------------- |
| **L1 可读确认** | 总结/报表/建议              | 生成后进"草稿箱"，用户看一眼即可确认或编辑 |
| **L2 逐项确认** | AI 提取的结构化信息（期限/案号/日期） | 逐项列出 + 标注置信度 + 用户逐条确认  |
| **L3 双人复核** | 关键决策/对外文书             | 必须用户手动触发生成，生成后二次确认对话框  |

**确认策略按场景挂载**（原则八落地）：

| 场景 | 挂载策略 | 说明 |
|------|---------|------|
| 内部推荐（今日/优先级/预估） | L1 可读确认 | 看一眼即过，低打扰 |
| 结构化提取（期限/案号/日期） | L2 逐项确认 | 逐条核对，置信度低强制确认 |
| 外部写操作（MCP case.update） | L3 双人复核 | 外部 AI 不能绕过，强制确认 |
| 文档生成（Copilot 窗口） | L2 草稿确认 | 生成草稿 → 用户编辑 → 定稿 |
| 决策变更（状态变迁） | L3 + 递归确认 | 双重保险，二次比对数据链 |

确认策略不再是全局一套，而是**按场景挂载的插件**（`set_confirm_policy`），这是"克制"原则在确认环节的体现——该松的松（内部推荐），该严的严（外部写/决策）。

**确认等级 = effective_policy（v2.8 新增安全下限）**：

```text
effective_policy = max(
    system_minimum_policy,  -- 系统安全下限（外部写 = L3），代码层硬编码，不可被降低
    scenario_policy,        -- 场景风险（推荐 L1 / 提取 L2 / 外部写 L3）
    model_policy,           -- 模型质量（本地小模型 +1 级）
    user_policy             -- 用户设置（可提高，不能降低）
)
```

> **安全边界**：`settings.confirm_policies` 只能提高确认等级，**不能突破 `system_minimum_policy` 定义的下限**——否则设置项会成为绕过安全约束的入口。例如外部写操作：用户设置 L1、模型建议 L1 都无效，最终始终 ≥ L3。

**防幻觉的具体机制**：

1. **引用溯源**：AI 生成的内容必须带"依据"（来源案件/文件/期限），用户可以核对
2. **置信度标注**：关键字段标注模型置信度（高/中/低），低置信度强制人工确认
3. **确定性计算不走 LLM**：期限计算、状态推导、逾期判断用**规则引擎**（已有期限引擎），绝不让 LLM 算日期
4. **草稿态**：所有 AI 生成物先落 `draft` 状态，确认后才转为正式

### 11.5 递归确认与数据链比对（双重保险）

> **核心原则：递归确认按确认级别分级，不是所有场景都做。** L1/L2 场景（内部推荐/报表/结构化提取）只做**规则校验**（低成本）；L3 场景（关键决策/外部写操作）才做**完整递归确认**。**v2.8 补充：核对范围由 ContextPolicy 界定，不无界遍历"全部数据"。**

#### 分级确认策略

| 确认级别 | 场景 | 二次确认 | 成本 |
|---------|------|---------|------|
| **L1 可读确认** | 总结/报表/建议 | 仅规则校验（日期/必填/状态枚举） | 零 LLM 调用 |
| **L2 逐项确认** | 结构化提取（期限/案号） | 仅规则校验 + 用户逐条核对（已在第一重完成） | 零 LLM 调用 |
| **L3 双人复核** | 关键决策/外部写/决策变更 | **完整递归确认**（ContextPolicy 界定的核对范围） | 一次额外 LLM 调用（值得，决策风险高） |

**为什么 L1/L2 不做完整递归确认**：
- 内部推荐/报表/提取的决策风险低（用户看一眼即可修正），不值得为每次确认付一次完整 LLM 调用
- 核对范围展开可能很大（见下），token 消耗大
- 用户体验：确认后还要等 AI 二次核对，延迟感明显——L1/L2 场景不该有

**为什么 L3 必须做**：
- 关键决策（是否上诉/和解）错误代价极高
- 外部写操作（MCP case.update）是外部 AI 写入，必须防幻觉
- 决策变更（状态变迁）影响案件走向，双重保险值得

#### 核对范围由 ContextPolicy 界定（v2.8）

> "全部数据链"作为工程规范是有问题的：大客户 100 个案件 × 每案 100 个 task + 文书/决策/历史 = **无限图遍历**；且从法律数据隔离角度，"判断今天做什么"不该自动携带客户全部其他案件的细节。
> **原则：AI 必须获得对当前决策所需事实的完整上下文，而不是数据库中的全部相关数据。** 每个场景一份 ContextPolicy（required_sources / max_depth / max_items / token_budget / sensitivity_scope / snapshot_version，见 architecture.md §3.3 目标态边界，未实现），缺失关键事实 = 信息不完整，但上下文有界。

#### 完整递归确认流程（仅 L3）

```
① AI 推荐产出（带 source_ref）
      ↓
② 用户确认（L3，第一重确认）
      ↓
③ 完整递归确认（L3 专属，系统自动）：
    ├── 按该场景 ContextPolicy 展开核对范围（如 decision_advice 展开到
    │    案件→任务/期限/文书/决策；不无界遍历"同客户全部数据"）
    ├── 交给 AI 做"一致性核对"任务（独立提示词，独立工作）
    │    检查遗漏：核对范围内有但推荐没提到的关键项？
    │    检查矛盾：推荐结论与核对范围冲突？（如期限日期不符、状态已变）
    │    检查依据：推荐的每条依据都能在核对范围找到原始记录？
    └── 规则校验兜底（纯 SQL）：日期格式、必填字段、状态合法性
      ↓
④ 三种结果：
    ├── 通过 → 落地执行
    ├── 遗漏/矛盾 → 打回 AI 重新生成（补充上下文再跑）
    └── 无法确认 → 升级人工复核（标记"需人工核查"）
```

**L1/L2 的规则校验**（低成本版）：

```
确认后 → 规则校验（纯 SQL，毫秒级）：
  ├── 日期格式合法？
  ├── 必填字段非空？
  ├── 状态枚举合法？
  └── 引用记录存在（source_ref 指向的表/记录可查到）？
  → 通过 → 落地；异常 → 打回 + 提示用户
```

**关键设计：递归确认是"另一个 AI 任务"，不是"同一 AI 验证自己"。**

> 之前担心"用 AI 验证 AI"会失效，这个顾虑不必要——只要递归确认用的是**独立提示词、独立任务**（"请核对推荐结果与数据链的一致性，找出遗漏和矛盾"），它就是一次全新的推理，与生成推荐那次互不依赖。LLM 做语义比对比纯 SQL 更强：能发现"期限改了但推荐还在用旧日期"这类需要理解的矛盾。

- **语义核对走 LLM**（仅 L3）：遗漏/矛盾/依据检查靠 LLM 理解数据链与推荐的语义关系
- **规则校验走 SQL**（所有级别）：日期格式、必填字段、状态枚举等硬性约束用纯 SQL（防止 LLM 在简单校验上浪费）
- **递归确认记录模型**：`recursive_checker` 也用 `ai_model` 字段留档，可追溯"用哪个模型做的核对"
- **确认后仍是 AI 产出**：递归确认通过 ≠ 变成确定性地，落地时依然遵守"AI 产出必确认"的铁律（推荐本体已由用户确认过，递归确认只是补充校验）

#### 数据链的定义

"全部数据链"指与当前实体相关的所有数据，通过**显性关联**（3.2 通道 A）展开：

```
实体（案件/任务/客户/知识）：
  ├── 直接关联：任务、期限、文书、日志、状态轨迹
  ├── 间接关联：客户 → 名下其他案件 → 它们的任务/期限
  ├── 决策链：decisions（用户做过的选择、拒绝过的建议）
  └── 历史模式：task_events、daily_stats
```

#### 递归确认与关联性双通道的关系

- **显性关联**（3.2 通道 A）：提供"数据链"的遍历路径——递归确认按显性关联展开
- **隐性关联**（3.2 通道 B）：提供"AI 洞察"作为递归确认的额外输入——检查推荐是否与已知洞察冲突
- 递归确认的结果本身也是学习样本：发现遗漏 → 修正抽取器；发现矛盾 → 修正模型 prompt

#### 递归确认的落点

- 推荐引擎（11.6）的产出：**L1/L2 → 规则校验；L3 → 完整递归确认**
- 报表生成（11.3）的对外版本：L1 规则校验（对外叙事不触发完整递归）
- 决策记录（11.7）新增 `recursive_checked` 状态，标记是否已过二次比对（L3 场景必填）
- 递归确认失败的原因记录进 task_events（`event_type='recursion_gap'`），供抽取器改进

### 11.6 AI 推荐决策引擎（决策系统的核心）

> **核心原则：AI 只做推荐，决策永远在用户手里。** 系统从数据中抽取信息，交给 AI 生成建议，用户确认后落地，落地后学习修正。

#### 为什么要有推荐决策引擎

律师每天面对大量选择：

- **今天做什么**（从 30 个任务里挑出今天最该做的 3-5 个）
- **先做什么**（优先级排序）
- **每个做多久**（时间预估）
- **要不要做**（某些任务是否该推迟/取消/等待）

把这些选择全交给用户自己判断 = 决策疲劳。全部交给 AI = 风险（幻觉、遗漏）。正确姿势是 **AI 抽取信息 → 生成推荐 → 用户确认 → 递归确认 → 落地 → 反馈学习**。

#### 推荐闭环（六步）

```
┌─────────────────────────────────────────────────────────┐
│ ① 抽取信息（本地 SQL，不依赖 LLM）                        │
│    任务（到期/逾期/等待/耗时）                             │
│    案件（状态/期限/下一步行动）                            │
│    日历（硬性日程）                                       │
│    历史（完成任务耗时/延期模式/活跃时段）                   │
│    上下文（@办公室/@法院/@电话）                          │
├─────────────────────────────────────────────────────────┤
│ ② 构造上下文（组装 prompt，结构化）                       │
│    把抽取的信息组织成 AI 可理解的上下文                    │
│    标注来源与置信度                                       │
├─────────────────────────────────────────────────────────┤
│ ③ AI 生成推荐（模型可切换）                               │
│    今日任务推荐（3-5 个，含理由）                         │
│    时间预估（每任务预计多久）                             │
│    当日排程建议（硬性日程 + 弹性任务的时间块）             │
│    风险提示（哪些任务快逾期、哪些该处理）                  │
├─────────────────────────────────────────────────────────┤
│ ④ 用户确认（L1/L2 确认，见 11.4）                        │
│    接受 / 修改（调时间、调优先级）/ 拒绝                  │
│    每个推荐项标注"为什么推荐"（可追溯）                   │
├─────────────────────────────────────────────────────────┤
│ ⑤ 递归确认（见 11.5，自动，不打扰用户）                   │
│    与全部数据链比对 → 遗漏/矛盾则打回重生成               │
├─────────────────────────────────────────────────────────┤
│ ⑥ 落地 + 反馈                                            │
│    确认的推荐 → 写回任务（estimated_minutes/today_index）│
│    用户修改 → 作为学习信号                               │
│    记录到 decisions（决策链，见 11.7）                   │
└─────────────────────────────────────────────────────────┘
```

#### 推荐类型与数据结构

| 推荐类型       | 输入（抽取什么）                  | 输出（AI 生成什么）              | 落地到哪里                   |
| ---------- | ------------------------- | ------------------------ | ----------------------- |
| **今日任务推荐** | 所有未完成任务（含到期/逾期/等待）        | 今天该做的前 3-5 个任务 + 理由      | 今日视图（today_index）       |
| **优先级排序**  | 任务的 due_date/flagged/案件阶段 | 任务优先级调整建议                | tasks.priority          |
| **时间预估**   | 任务描述 + 历史同类任务实际耗时         | 预计分钟数（estimated_minutes） | tasks.estimated_minutes |
| **当日排程**   | 硬性日程 + 推荐任务 + 用户活跃时段      | 时间块安排（上午/下午/晚上）          | 日历/今日视图                 |
| **决策建议**   | 案件状态 + 期限 + 关键信息          | 是否该做 X（如是否上诉） + 依据       | decisions（决策链）          |
| **等待跟进**   | waiting 任务 + 等待时长         | 是否该催办 + 催办话术             | 收件箱/任务                  |

#### 与报表、确认机制的关系

```
11.3 自动报表（历史事实）──→ 11.6 推荐引擎（面向未来）
        对内结构化数据           │
                                 ↓
                           AI 生成推荐
                                 ↓
                      11.4 确认机制（防幻觉）
                                 ↓
                      11.5 递归确认（ContextPolicy 界定核对范围）
                                 ↓
                      11.7 决策记录（留痕）
                                 ↓
                      落地 + 反馈 → 修正下次报表/推荐
```

**关键点**：

- **推荐必须带理由**：每条推荐标注"为什么"（哪条期限、哪个案件状态、哪条历史规律），可追溯到来源
- **用户修改即反馈**：AI 推荐了 A，用户改成了 B——记录这个差异，下次推荐修正
- **预估会自我校准**：AI 预估"起草起诉状 2 小时"，用户实际用了 3 小时——记录实际值，下次预估修正为 2.5 小时
- **不做的事也记录**：AI 推荐"今天做 X"，用户拒绝——记入决策链（"未做 X 的原因"），防止反复推荐同一件事

### 11.7 决策记录与复核（决策留痕，可追溯）

> **核心原则：每个决策都有依据，决策前确认，决策后复核。**

**为什么需要决策记录**：

- 律师决策影响案件走向（是否上诉、是否和解、是否接受调解）
- 决策依据（期限、证据、客户意见）随时间变化
- 换 AI 模型 / 换律师交接时，必须有可追溯的决策链
- 推荐引擎（11.6）产生的每条推荐，一旦用户确认/拒绝，都应落决策链

**决策记录表**（迁移 v9，表名与字段语义见 architecture.md §5）：

> 核心字段：`entity_type`（case/client/task/knowledge）· `entity_id` · `decision_type`（appeal/settle/accept/refuse/other + recommend_* 六种）· `decision`（决策内容）· `basis`（决策依据）· `ai_advice` / `ai_model`（AI 建议留档）· `source_ref`（正式 JSON 依据）· `status`（proposed/confirmed/rejected/voided）· `recursive_checked`（是否过二次递归确认）· `confirmed_at` / `review_due` / `reviewed_at`

**决策闭环**：

```
AI 建议（proposed，带依据）
   ↓ 用户确认
确认生效（confirmed，记录依据+确认时间）
   ↓ 定时器
到复核日期 → 主动问"该决策仍有效吗？"
   ↓
有效 → 标记 reviewed_at（留档）
   ↓
无效/变化 → 记 voided + 新决策（形成决策链）
```

**决策与状态机联动**：

- 案件状态变更（三轨状态机）时，若属决策性变更（如"放弃上诉"），强制关联一条 decision
- `case_track_history` 记录"状态变了"，`decisions` 记录"为什么变"——两者互补
- 结案报告里自动附上"本案件关键决策链"

**承接推荐引擎（11.6）的落地**：- 推荐引擎每次产出（今日任务/优先级/时间预估/当日排程）→ 用户确认或修改 → 落一条 `decision`

- `decision_type` 扩展推荐类：`recommend_today` / `recommend_priority` / `recommend_estimate` / `recommend_schedule` / `recommend_action` / `recommend_followup`
- `basis` 记录推荐依据（"due_date 后天"、"该任务历史平均 2h"、"案件进入口审阶段"）
- **用户拒绝推荐也记录**：`status='rejected'` + 拒绝原因，防止 AI 反复推荐同一件事（学习信号）
- 决策链让"今天的推荐 → 用户的选择 → 实际执行结果"三者可对账
- **递归确认状态**：决策落地前必须过 11.5 的二次递归确认，`recursive_checked` 标记在确认后置 1

### 11.8 跨模型成长系统（模型无关的记忆）

> **核心原则：Casy 的成长不依赖任何单一 AI 模型。** 用户今天用 Ollama，明天换 OpenAI，成长数据不能丢。

**问题**：如果"学习"依赖模型的上下文或记忆，换模型 = 从头开始。

**解决方案：成长数据全部落在本地结构化存储，模型只是"生成器"，不是"记忆体"。**

```
┌─────────────────────────────────────────────┐
│  Casy 成长系统（模型无关）                     │
├─────────────────────────────────────────────┤
│  记忆层（SQLite，永远保留）                    │
│  ├── task_events       行为事件（完成/延期）    │
│  ├── decisions         决策记录（含依据）      │
│  ├── smart_summaries   历史报表/总结          │
│  ├── daily_stats       每日统计（结构化）      │
│  └── knowledge_items   沉淀的知识/经验         │
├─────────────────────────────────────────────┤
│  生成层（可随时切换模型）                      │
│  ├── 本地 Ollama / llama.cpp                │
│  ├── OpenAI / DeepSeek / 其他 API           │
│  └── 接口一致，切模型不改代码                 │
└─────────────────────────────────────────────┘
  模型可以换，记忆不丢
```

**关键设计**：

1. **统计永远本地算**：完成率、逾期率、时间分布——SQL 聚合，不依赖 LLM
2. **AI 能力边界（v2.8 统一）**：**LLM 不产生确定性事实；LLM 可以产生非确定性建议和叙事。** 期限日期 / 是否逾期 / 状态合法性 → rule（规则引擎）；"今天先做 A" / "是否建议催办" / "如何总结本周" → AI 可以。"只转述"指确定性数据必须由规则产生，不代表 AI 不能做推荐判断
3. **AI 建议留档**：每次 AI 调用写 `ai_runs`（provider/model/purpose/input/output hash），可对比不同模型表现、追溯"当时为什么这么建议"
4. **切换模型无感**：`smart_summaries`、`decisions` 都带 `ai_model` 字段，切换后历史仍在
5. **确认等级 = effective_policy**：`max(system_minimum, scenario, model, user)`——低质量本地模型 → `model_policy=L2`；高质量 API → `model_policy=L1`。**settings 只能提高，不能突破 `system_minimum_policy` 安全下限**（见 11.4）

### 11.9 数据支撑（行为沉淀 + AI 审计）

> 表名与字段语义以 architecture.md §5 为准。此处只列语义：

**行为学习（task_events，90 天清理）**：`task_id` · `event_type`（created/completed/deferred/snoozed/reminded）· `occurred_at` · `payload`。专职"行为学习"（预估校准/活跃时段），**不承担审计职责**。

**AI 审计（ai_runs + ai_context_items，长期保留）**：
- `ai_runs`：provider · model · purpose · prompt_version · status · input_hash / output_hash · job_id —— 每跑一次 AI 一行
- `ai_context_items`：run_id · source_type · source_id · source_field · content_hash · snapshot_version —— 该次调用模型可见的每条内容

**领域事件（audit_events，append-only）**：aggregate_type/aggregate_id · event_type · payload · actor（user/ai/system/mcp/skill）—— 领域事务内发出，事件源底座。

**报表（smart_summaries 对外叙事 + daily_stats 对内统计）**：对内结构化统计先落 `daily_stats`（机器可读），生成对外文本后写 `smart_summaries`（人可读）——职责分离，`content` 只在叙事完成时存在。

**决策记录（decisions）**：见 11.7（字段含 `recursive_checked`、`source_ref` 正式 JSON schema）。

**多来源引用（provenance）**：结论引用多个来源时用独立 provenance 表，不塞进 `source_ref`。

**学习闭环**：

```
记录（task_events 行为 + ai_runs 审计）→ 统计（daily_stats，本地算）→ 生成（LLM 转叙事）→ 确认（effective_policy）
        ↑                                                        ↓
        └──── 用户反馈（编辑报表/处理提醒/确认或否决决策）──────────┘
```

**数据一致性**：

- 统计永远本地算（SQL 聚合），LLM 不参与计算
- 报表对内版（daily_stats）在生成对外版之前先落地，保证"机器数据"先于"人读文本"
- 换模型时，旧报表、旧决策全部保留，新模型从数据库继续

**"模型可见即记录"不变量**（原则八落地）：

> 任何到达模型的内容，必须能从 `ai_runs` + `ai_context_items` 重建。新增模型可见输入 = 新增 ai_context_items 记录，先记录后使用。`ai_runs` 长期保留，**不随 task_events 的 90 天窗口清理**——换模型后可审计"当时模型看到了什么"。

这意味着：
- 抽取器给 AI 的每条上下文，都能从事件日志反查到来源（"依据可查"的架构级保证）
- 新增 AI 可见数据时，必须先扩展事件系统，不能直接塞给模型
- task_events 从"行为记录表"升级为"完整事件系统"（类型化事件 + 事件总线，见架构 §3.3 目标态边界，未实现）
- 这保证换模型/回溯/审计时，一切 AI 判断的依据都在——不是黑盒

### 11.10 数据蒸馏与外置记忆（软件自我进化）

> 这是原则七的落地设计——软件越用越聪明，靠的不是无限堆数据，而是**反复提炼**：删垃圾、存精华、循环进化。

#### 分阶段实施（M0 只做 L1 + L3）

> **三层蒸馏是一个完整产品，不要一次全做。** 先验证"记录行为数据 → 确实能改善推荐"这条链路，再引入中间的提炼层。

| 阶段 | 范围 | 说明 |
|------|------|------|
| **M0（先做）** | L1（task_events 记录行为）+ L3（已有 knowledge_items） | 行为数据先沉淀；知识库已有；验证"L1 数据能否支撑规则推荐" |
| **P3（后置）** | L2 蒸馏 + 确认区 | AI 提炼 L1 → 候选记忆 → 确认 → 进 L3；需先证明 L1 数据有用 |
| **P4（长期）** | 生命周期（active/stale/archived）+ 合并 + 自动清理 | 数据量真正上来后再做新陈代谢 |

**M0 的蒸馏形态**：
- L1：task_events 照常记录（已有设计），加保留窗口（90 天）自动清理
- L3：knowledge_items 照常维护（已有功能），用户手动沉淀经验
- **暂不做**：AI 提炼、确认区、生命周期状态机、重复合并

**为什么后置 L2**：L2 是整个蒸馏系统里最复杂的部分（AI 提炼 + 确认区 + 升级逻辑），如果 L1 数据本身不足以改善推荐，L2 就是纯负担。先跑通 L1→规则推荐，验证价值，再上 L2。

#### 蒸馏调度

```
每周日 23:00  蒸馏任务（配合隐性关联学习）：
  L1 原始数据 → AI 提炼 → 候选记忆（L2）→ 确认区 → 采纳进 L3 知识库
  L1 过期清理：删除 N 天前的原始事件（task_events 保留窗口）
  L2 陈旧归档：长期未引用的记忆 → 活跃 → 陈旧 → 归档
  L3 重复合并：近似记忆合并（"无效口审平均延迟 60 天"出现 3 次 → 合并为 1 条并提升置信度）
```

#### 记忆生命周期状态机

```
每条记忆经历：
  活跃（active）→ 陈旧（stale，30 天未引用）→ 归档（archived）
  归档后可检索但不再进推荐上下文
  ↕ 被再次引用时 → 回到活跃
```

#### 三层记忆与现有表的关系

| 记忆层   | 现有表                                           | 蒸馏动作              |
| ----- | --------------------------------------------- | ----------------- |
| L1 原始 | task_events / daily_stats / inbox / case_logs | 定期删除过期（保留窗口 90 天） |
| L2 提炼 | decisions / ai_insights / smart_summaries     | 确认后升级，陈旧归档        |
| L3 知识 | knowledge_items（6 职能）                         | 永不删除，可检索引用        |

#### 新增数据表

> `memory_entries` 建表 SQL 见 architecture.md §5（当前关键表清单；v9 目标态新表为设计草案，未落库）。字段语义：`layer`（l1/l2/l3）· `content` · `source_ref`（正式 JSON 单一来源）· `status`（active/stale/archived）· `confidence` · `ai_model` · `last_used_at`（生命周期判断）· `merged_from`（合并来源 ID）。多来源引用用 `provenance` 表。

#### 蒸馏的核心原则

1. **垃圾必须删**——L1 有生命周期，过期即清，避免噪音淹没提炼
2. **精华必须确认**——候选记忆经用户确认才进 L3，防幻觉污染知识库
3. **记忆必须带出处**——每条记忆带 source_ref，可反向核对
4. **重复必须合并**——近似记忆合并提升置信度（"无效口审平均延迟 60 天"出现 3 次 → 合并为 1 条）
5. **陈旧必须归档**——防止知识库无限膨胀
6. **Casy 专属**——只提炼业务相关记忆（案件规律/期限模式/客户习惯/办案经验），不做通用对话记忆

### 11.11 双向开放与智伴层插件化（对外对内打通）

> 这是原则八的落地设计——Casy 双向开放：外部工具可访问内部数据（MCP），内部可引入外部能力（skill/harness），且智伴层组件插件化（没有特权核心，一切皆插件）。

#### 对外暴露（外部访问内部）

| MCP 接口 | 操作 | 权限 |
|---------|------|------|
| `case.query` | 查案件列表/详情/状态/期限 | 只读，默认开放 |
| `task.query` | 查任务/等待/下一步 | 只读 |
| `knowledge.search` | 查知识库/法条 | 只读 |
| `case.update` | 外部 AI 修改案件/任务 | **需权限确认（Confirmer L3）** |
| `case.create` | 外部 AI 创建任务 | **需权限确认** |

外部工具（Claude Code / Pi / Codex）可通过 MCP 查询案件上下文，辅助外部 AI 工作；写操作不能绕过确认。

#### 对内引入（内部访问外部）

| Skill | 用途 | 加载方式 |
|-------|------|---------|
| 文书生成 | 答辩状/上诉状/代理词 | 按需（Copilot 窗口触发） |
| 法律检索 | 法条/案例查询 | 按需 |
| 格式化 | 文书格式/编号规范 | 按需 |
| 翻译 | 外文文献/文书 | 按需 |

skill 默认不加载（不占常驻上下文），使用时才读说明 + 调工具——**判断与执行分离**：智伴层做业务判断（推荐/确认），skill 做具体执行（生成/检索）。

#### 智伴层插件化

```
共享上下文（Context）
├── 模型适配器（可切换）  ← ModelProvider（trait，M0-P2 先实现）
├── 上下文构建器          ← ContextBuilder（按 ContextPolicy 取数）
├── 推荐器（产出 Proposal）← Recommender
├── 确认策略（按场景）    ← 见 11.4（effective_policy）
├── 递归确认器（L3）      ← RecursiveChecker
├── 蒸馏器（分阶段）      ← Distiller
└── 事件与审计（扩展点）  ← ai_runs / ai_context_items / audit_events / task_events
```

关键机制（v2.1 分阶段，避免过度工程）：
- **组件切换分阶段**：M0-P2 用 **trait + enum** 实现组件切换（配置决定组合，不写死流水线）；**真的需要第三方插件时**（P4+）才升级为注册表 + 事件总线 + 可逆效应
- **"模型可见即记录"不变量**：任何到达模型的内容必须能从 `ai_runs` + `ai_context_items` 重建（见 11.9），长期保留
- **写入口唯一**：Copilot 只产出 Proposal，确认后经 DomainCommand 由领域事务落库（见 architecture.md §6.3 后续收口原则，目标态）

#### 安全约束

- 外部写操作必须过 Confirmer（D4 铁律延伸），外部 AI 不能绕过
- 外部访问遵守隐私分级（3.12）——敏感字段不外泄
- skill 安装需用户确认（防恶意 skill）
- harness 嵌入仅在文档生成沙箱内运行（不直接访问主数据）

### 11.12 与现有能力的关系

| 现有能力                           | 本章升级                              |
| ------------------------------ | --------------------------------- |
| 期限引擎（15 条法定规则）                 | 从"到期提醒"升级为"分级预警"，确定性计算永不走 LLM     |
| 多通道提醒（弹窗/通知/日历/邮件/飞书）        | **现状本地/系统通知在线可用、飞书消息/任务通道为占位、引擎未自动拉起（见 11.1）**；升级为 R1-R4 分级 + 时机智能 + 离线送达语义，M1 接通日历/日程同步（CalDAV + ICS email）实现离线准时（见 11.2） |
| AI 后端（Ollama/OpenAI）           | 不产生确定性事实（规则引擎负责）；产生非确定性建议与叙事；多模型切换 + ai_runs 留档 |
| 定时器（deadline_recalc_scheduler） | 增加"每日早报/每周总结/每月简报/决策复核/蒸馏"多档调度；提醒引擎需在启动时拉起（M0，见 11.2）    |
| 收件箱                            | 成为"智能建议 + AI 产出待确认"的落地入口          |
| case_track_history             | 与 decisions 联动："状态变了 + 为什么变"      |
| 今日视图 / 日历                      | 接收推荐引擎（11.6）的落地：today_index、时间块排程 |
| tasks 表                        | 接收推荐引擎的 estimated_minutes 校准      |
| knowledge_items                | 作为 L3 长期记忆层，接收蒸馏产物（原则七）           |

| 外部工具（Claude Code/Pi/Codex）   | 通过 MCP Server 访问案件/任务/知识（11.11）     |

# 下篇：视觉与交互规范

## 第十二章 UI 视觉规范

### 12.1 视觉标准

Casy 的视觉标准遵循以下原则：**信息密度高但视觉安静**；颜色只用于语义（状态/类型），不用于装饰；装饰性元素（emoji、渐变、大图标）全部缺席；内容为主体，工具条退到角落。

### 12.2 设计 Token（已部分落地于 theme.css）

| Token | 值                         | 用途         |
| ----- | ------------------------- | ---------- |
| 主色    | `#2563EB`                 | 强调、选中、主要操作 |
| 背景    | `#FAFAFA` 浅灰              | 应用底色       |
| 表面    | `#FFFFFF`                 | 卡片、面板      |
| 文字主   | `#18181B`                 | 标题         |
| 文字次   | `#52525B`                 | 正文         |
| 文字弱   | `#A1A1AA`                 | 辅助说明       |
| 语义红   | `#EF4444`                 | 逾期、错误、硬性日程 |
| 语义琥珀  | `#F59E0B`                 | 即将到期       |
| 语义绿   | `#10B981`                 | 成功、完成、成长型  |
| 语义紫   | `#8B5CF6`                 | 探索型案件      |
| 圆角    | 8px 卡片 / 6px 按钮 / 4px 输入框 |            |
| 阴影    | 浅、低透明度、小扩散                | 仅浮层用       |

### 12.3 视觉铁律

1. **颜色只表语义，不表装饰**——每个颜色出现必须能解释"它代表什么状态"
2. **无 emoji，无渐变，无装饰性图标**——一律线性图标（Element Plus icons）
3. **信息密度优先于视觉丰富度**——一屏可看 30 条任务，而不是 8 张大卡片
4. **空状态要友好**——没数据时给出下一步引导，不是空白
5. **动效克制**——过渡 <200ms，不做弹跳/缩放表演

### 12.4 当前差距与整改清单

| 现状问题           | 整改              |
| -------------- | --------------- |
| 侧边栏 7 个平铺菜单    | 改为三层架构（见第四章）    |
| 任务四象限          | 重写为 5 透视工作台     |
| 日历单月平铺         | 重写为 Forecast 双栏 |
| 知识库主题分类        | 改为 6 职能分类       |
| 剩余 ~80 处 emoji | 全部换线性图标         |
| 首页无"今日聚合"      | 加顶栏今日面板         |

### 12.5 降级态设计（AI 不可用时用户看到什么）

> **原则：每个含 AI 的功能，都要设计"AI 不可用/处理中/失败"三种状态的具体 UI。** 用户不该看到空白或报错，而应该看到"可用的替代"。

#### 通用降级态三态

每个含 AI 功能遵循同一套三态：

| 状态 | 用户看到 | 操作 |
|------|---------|------|
| **处理中** | 骨架屏（skeleton）或"生成中..."占位 | 可离开，完成后通知 |
| **成功** | 正常内容 | 正常使用 |
| **降级/失败** | 规则版替代 + 提示条 | 可重试或手动输入 |

#### 各功能的具体降级态

| 功能 | AI 不可用时显示 | 失败重试 |
|------|---------------|---------|
| **今日面板·智能推荐** | 规则排序列表（due_date + flagged + 案件阶段），顶部提示条"AI 推荐不可用，已显示规则排序" | 无（规则版即兜底） |
| **每日早报** | 结构化表格版（今日硬性日程 + 到期任务 + 等待跟进，纯 SQL 聚合） | "重新生成"按钮（失败可手动触发） |
| **任务时间预估** | 不显示预估或显示同类任务历史平均（SQL 聚合） | 无 |
| **收件箱 AI 分类** | 收件箱原样显示，用户手动厘清 | 无 |
| **文书生成（Copilot）** | Copilot 侧栏显示"AI 不可用" + 提供模板选择（Docsy 模板） | "重试"按钮 |
| **L3 递归确认** | 降级为规则校验（日期/必填/枚举），提示"深度核对不可用" | 重试 |

#### 降级态视觉规范

- **提示条**：浅琥珀底 + 琥珀图标（不是红色——不是错误，是可降级）
- **规则版替代**：样式与 AI 版一致（只是数据来源不同），不显突兀
- **AI 状态徽标**：全局状态栏显示 AI 可用性（绿=可用/灰=关闭/琥珀=降级），用户一眼知道当前 AI 状态
- **可关闭提示**：用户可设置"不再提示"，降级时静默用规则版（设置里可配）

## 第十三章 MVP 定义与实施路线图

### 13.1 MVP（M0）—— 最小可用版本

> **原则：先跑通核心闭环，验证体验，再扩展。** 本设计文档覆盖 6-12 个月的完整蓝图，但 **M0 只做核心**——AI 功能先做纯规则版，确认体验后再接 AI。

**M0 目标**：让律师能**完整管理一个案件的生命周期**，体验"秩序引擎"的核心价值，但**不依赖 AI**。

| 模块 | M0 范围 | 不做（后置） |
|------|---------|-------------|
| 数据层 | schema v9：tasks/cases GTD 字段 + clients + areas + task_events + decisions + **ai_runs / ai_context_items / audit_events** | smart_summaries / ai_insights / memory_entries（建表可留，功能后置） |
| 任务工作台 | 5 透视 + 厘清流程 + 下一步行动（**纯规则版**） | AI 推荐引擎（先用规则排序：due_date + flagged + 案件阶段） |
| 导航架构 | 三层导航 + 今日面板（**规则聚合**：硬性日程+到期+等待） | 每日早报 AI 叙事（先做结构化版：表格列出今日要点） |
| 案件详情页 | 项目书结构 + 三轨状态 + 下一步行动卡 + 顺序项目 blocked | 案件自动复盘 |
| 日历 | 现有月视图 + 颜色预警（读 is_overdue/due_soon 缓存） | Forecast 双栏 + 拖拽改期 |
| 收件箱 | 极简捕获 + 厘清流程 | AI 自动分类 |
| 双向开放 | 不开放 | MCP Server / Skill Runner |

**M0 的"无 AI 版"原则**：

> 每个 AI 功能都有一个"纯规则替代版"。M0 先做规则版（零成本、零延迟、确定性），验证用户体验后，再在 P2+ 接入 AI。**规则版不删，作为 AI 不可用时的降级路径**（见 3.11 降级策略）。

**M0 验收标准**：
1. 律师能创建案件 → 填三轨状态 → 生成顺序任务 → 完成任务解锁下一步
2. 今日面板准确显示：硬性日程 + 到期任务 + 等待超时 + 需回顾案件（全部规则驱动）
3. 期限引擎照常工作（这是已有能力，M0 确保不被破坏）
4. 全程**不依赖 AI**——AI 挂了 M0 也能完整运行
5. 提醒 M0 为**本地尽力而为**：应用在线时触发正确；离线期由启动补偿扫描补发并列出"离线期间错过的提醒清单"；设置/日志明示"M0 尽力而为，配置日历同步（M1）后离线准时"（见 11.2）

### 坐标说明（v2.3）

> **M0 是 product milestone（最小可用版本），P0-P4 是 engineering phases。** 两者不是同一坐标：
> **M0 = P0 + P1 的规则版子集 + P2 中 blocked/顺序项目等必要能力**。M0 验收标准见 13.1（不依赖 AI 可完整管理一个案件生命周期）。
> v2.1 调整：**基础契约提前到 P0/P1**——双路径路由表、领域层单写入口、最小 Confirmer、AI 审计（ai_runs）、fallback contract 是地基，不是 P3 才补的后置功能。
> v2.3 调整：**M1 的核心能力是日历/日程同步（CalDAV + ICS email）**，落在 P3；它让"离线准时提醒"不再依赖 Casy 本地进程（见 11.2）。

## 附录：Casy 设计哲学一句话总结

> **四个元信息，两个时间轴，一条案件主线，一个主动智伴。**  
> 数据有限（4 认知对象），视图无限（透视）；捕获极简，整理后置；案件即流程，克制即优雅；  
> 提醒分级，总结自动，越用越懂你；**报表四维（日/周/月/项目），对内结构对外可读；  
> AI 产出必确认（effective_policy 安全下限），决策留痕可追溯，模型可换记忆不丢；  
> 双向开放，组件分阶段，写入口唯一，上下文有界，依据可查。**
