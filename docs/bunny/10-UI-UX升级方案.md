**你的问题不是"设计不好看"，而是三处结构性的东西挡住了任何全面升级。**

`VISUAL_SYSTEM.md` 里那套"危险=三角、等待=沙漏、卷宗=夹层"的法律行业隐喻，以及黄宣纸纸纹，是**真正有观点的设计**，不是通用后台模板。

> 下面三个结构性障碍不解决，你做任何视觉改动都是一次性投入、无法复用。

## 一、三处结构性障碍（全部实测）

### 障碍 1：没有组件层 —— 94% 的 CSS 困在单个组件里

| 位置 | CSS 行数 |
| --- | --- |
| 121 个 Vue 文件的 `<style>` 块 | **17,703（94%）** |
| 7 个共享 CSS 文件 | 1,143（6%） |

更关键的是**重复度**（按 CSS 属性签名聚类，≥3 个文件出现即计）：

| 重复次数 | 典型属性组合 | 波及文件 |
| --- | --- | --- |
| **16×** | `color, font-size, overflow, text-overflow, white-space`（文字截断） | **14 个** |
| 10× | 上一组 + `font-weight` | 10 个 |
| 9× | `align-items, display, flex-wrap, gap, justify-content`（flex 行） | 9 个 |
| 9× | `background, border-radius, color, font-family, font-size, font-weight`（卡片/药丸） | 4 个 |
| 8× | `background, border, border-radius, cursor, font-size`（可点条目） | 3 个 |

**共 56 组重复签名。** 单文件极端值：`CalendarView.vue` 内含 **1,668 行** CSS、`CaseListView.vue` **1,533 行**、`TasksView.vue` **760 行**。

> **后果**：你想把全应用的按钮圆角从 6px 改成 8px，得改 100 个文件。这就是"不敢全面升级"的真实原因——**不是审美问题，是边际成本问题**。

### 障碍 2：响应式打错了目标 —— 64% 的断点在应用永远到不了的宽度

`tauri.conf.json:16-19` 定义窗口 **1024×720，`minWidth: 800`，`minHeight: 600`**。

而全仓 59 条 `max-width` 媒体查询里：

| 情况 | 数量 |
| --- | --- |
| **目标宽度 < 800px（`minWidth` 之下，应用永远到不了）** | **38（64%）** |
| 目标宽度 ≥ 800px（真正可达） | 21 |

分布明细：`480px ×4`、`520px ×5`、`600px ×10`、`640px ×4`、`650px ×6`、`700px ×3`、`720px ×1`、`760px ×4` —— **全部不可达**；
可达区间里 `1100px ×6`、`800px ×2`、`1024px ×2`，其余 15 个断点**各只出现一次**。

> **后果**：总共 **19 个互不相同的断点**，没有体系。真正难看的 **800–1100px 窄窗区间**只被 6 条规则覆盖；而开发者一直在为手机写样式。
> 对一个**律师在 13 寸屏上并排开着案卷和文书**的桌面工具，这是把工程量花在了错误的地方。

### 障碍 3：状态组件建好了但没被采用 —— 四态区分根本没落地

`UX_CONSISTENCY_AUDIT` 自己定的标准第一条是"加载、空数据、筛选无结果、读取失败必须区分"。实测采用度：

| 共享组件 | 实际被用在几个文件 |
| --- | --- |
| `EmptyState` | 9 |
| `StateFeedback` | **2** |
| **`SkeletonCard`** | **0** |
| **`DegradedBanner`** | **0** |
| `ContextMenu` | 7 |
| `SaveConflictDialog` | 3 |

与此同时：**21 个文件各自写 `<el-empty>`，39 个文件各自写"暂无/没有数据"文案**。

> **后果**：同一应用里"没有结果"至少有三种写法。UX 审计声称已解决的"四态区分"，**在代码里并未真正统一**。
> 这也和我在 `00-行动清单` 里记的"读取失败被当成空列表"是同一类问题的 UI 面——`DegradedBanner` 造好了、**一次没用**，所以"读取失败"在界面上永远长得像"没有数据"。

## 二、一个必须先说的战略警告

**不要在修好死 UI 之前做视觉美化。**

我上一轮审查找到的界面缺陷，恰好都是"视觉上完全正常"的：

- 案件筛选面板 13 个筛选器**点了不生效**（`CaseListView.vue:775`）
- 任务"推迟"**写了库但界面无反应**（`Cmd<P,void>` 陷阱）
- AI 智伴知识卡片**点击抛 TypeError**
- 托盘菜单**点了什么也不发生**
- 收件箱拖入文件**不刷新**

**如果先做视觉升级，这五个控件会被打磨得更好看、更值得信任——然后继续骗人。** 用户会从"这按钮没用"变成"这按钮坏了"，信任损失反而更大。

> **顺序必须是：接通 → 统一 → 再美化。**

还有一个已知风险：`UX_CONSISTENCY_AUDIT` 的**第四、五、六轮都标注"验证暂停"**——连续多块选择/批量操作、选区方向与设置输入保护、六项一致性完善，**代码写了但测试、构建、浏览器验证全停**。在这批未验证代码之上做重构，等于在不确定的地基上盖楼。

## 三、分阶段方案

### 第 0 步：接通死 UI（见 `00-行动清单`，半天）

5 处、约 6 行。**这是 UI 升级的前置条件，不是可选项。**

### 第 1 步：建组件层（1–2 周）—— 投入最大，回报最长

从 56 组重复签名里抽 **8–10 个原语**，放进 `src/shared/ui/`：

| 原语 | 依据（重复次数） | 预计消灭 |
| --- | --- | --- |
| `UiTruncate`（多行/单行截断） | 16× + 10× | 26 处 |
| `UiCard` / `UiPanel` | 9× / 7× / 6× | ~20 处 |
| `UiRow`（flex 布局 + gap 语义） | 9× + 6× + 6× | ~20 处 |
| `UiPill` / `UiBadge`（状态标签） | 9× / 8× | ~17 处 |
| `UiListRow`（可点条目 + hover/focus/active） | 8× | ~8 处 |
| `UiSectionHeader` / `UiToolbar` | 7× | ~7 处 |

**做法**：逐视图替换，每替换一处删掉该处的局部 CSS。**目标不是一次性重构，而是让重复签名组数从 56 降到个位数。**
`src/shared/components/` 已有 21 个组件的先例，路径和惯例都是现成的。

> 收益：这一步做完，"改一次全局视觉"才第一次变成一件成本低的事。

### 第 2 步：统一断点体系（2–3 天）

**删掉全部 19 个散断点，收敛成 3 个：**

| 断点 | 目标 | 对应场景 |
| --- | --- | --- |
| `< 1100px` | 紧凑 | 13 寸屏 / 分屏，侧栏折叠、两栏转单栏 |
| `< 900px` | 窄 | 最小窗口 800×600，隐藏次要列 |
| `≥ 1360px` | 宽 | 大屏，三栏全展开 |

**并把 `< 800px` 的 38 条规则逐条判定**：是真需求就提上来（说明 `minWidth` 该放宽），是惯性就删。
配套：`theme.css` 里加 `--bp-compact` 等自定义属性，或至少写进 `VISUAL_SYSTEM.md` 作为硬规范。

> 这一步单独就能明显改善"窗口一缩小就乱"的体感，**性价比最高**。

### 第 3 步：真正落地四态（3–5 天）

把 `EmptyState` / `StateFeedback` / `SkeletonCard` / `DegradedBanner` **真正用起来**，并定义一张统一矩阵：

| 状态 | 表现 | 必须可区分于 |
| --- | --- | --- |
| 加载中 | `SkeletonCard`（首次）/ 保留旧数据+局部转圈（刷新） | 空 |
| 空（首次无数据） | `EmptyState` + 下一步引导 | 无结果 |
| 无结果（筛选命中 0） | `EmptyState` + "清除筛选" | 空 |
| **读取失败** | `DegradedBanner` + **重试按钮** | 以上全部 |

**硬性规则**：`catch` 分支不得渲染空列表——这是我上一轮发现的数据完整性缺陷的 UI 投影（`DegradedBanner` 造好了一次没用，就是这个原因）。

配套动作：清掉 39 个文件里的内联"暂无"文案，统一到 `locales/zh-CN.json`。

### 第 4 步：视觉升级（此时才做，2–3 周）

这一步必须是"**在组件层之上**"的重设计，而不是逐页改。优先级建议：

1. **信息密度分级**——律师是长时间专业用户，当前字号/间距偏"通用后台"。案件列表、日历、任务这三处密度最高，适合更紧凑的行高与表格化。
2. **法务专属信息层级**——期限的"红/黄/绿 + `needs_review` 待核对"是产品最核心的语义，应该有专属视觉通道，而不是和普通 tag 混在一起。
3. **确认动作的分级**——删除文书、恢复历史版本、覆盖同步这类不可逆动作，目前和普通保存同级。危险三角隐喻已经在 docket.css 里定义了，应该用足。
4. **键盘可达性**——UX 审计已提"操作不能仅在鼠标悬停时可见"。专业工具的键盘流（`j/k` 上下、`Enter` 打开、`Esc` 返回）是最高性价比的体验升级。

### 第 5 步：验证（**不能省，尤其前 3 步都是重构**）

`UX_CONSISTENCY_AUDIT` 第 4–6 轮"验证暂停"的债要先还，再做新重构。建议：

- 每步重构配 **vitest 组件测试 + 截图对比**（`outputs/release-0.1.3-themes-webdav/ui/` 已有主题截图的做法可复用）
- 至少跑一次真实原生窗口的 800×600 / 1024×720 / 1440×900 × 明暗主题矩阵——**浏览器 fixture 证明不了 WebView 下的布局**
- `prefers-reduced-motion` 已有 5 处，但应作为全局规范

#### 5.1 给 mock 加类型标注 —— **已完成（2026-10-02）**

`mockData.ts` 原先 12 个 mock 集合里有 8 个无类型标注、3 个显式 `any[]`。现已完成绑定：

| mock | 绑定到 | 状态 |
| --- | --- | --- |
| `mockCases` | `Case[]` | ✅（codex 已完成，用 `emptyCase` 模板） |
| `mockTasks` | `TaskDto[]` | ✅ 本轮，用 `emptyTask` 模板 |
| `mockInbox` | `InboxItemDto[]` | ✅ 本轮 |
| `mockLinks` | `LinkDto[]` | ✅ 本轮 |
| `mockKnowledgeVersions` | `Array<KnowledgeVersionDto & { itemId: string }>` | ✅ 本轮 |
| `mockEvents` | 本地 `MockCalendarFixture` | ✅ 本轮（**有意不用 DTO**，见下） |
| `mockCalendarRows` | `CalendarEventRow[]` | ✅ 原已有 |
| `mockTaskPlans` / `mockDrafts` / `mockDraftVersions` | 已有 | ✅ 原已有 |
| `mockKnowledge` | 仍 `any[]` | ⚠️ **有意保留，见下** |
| `mockStats` | 仍无标注 | ⚠️ **有意保留，见下** |

**绑定后由编译器新暴露的 4 处真实漂移：**

1. **`flagged: true` vs `TaskDto.flagged: i32`** —— mock 用布尔，真实是 0/1。浏览器里 `v-if` 两种都能过。
2. **`sequenceOrder`** —— bindings 声明为**必填 `number`**，而 Rust 是 `Option<i32>`。bindings 与 Rust 本身不一致，需单独确认。
3. **`KnowledgeVersionDto` 没有 `itemId`**，但 `list_knowledge_document_sources` / `import_pageindex_to_knowledge` 按 `itemId` 关联 → **真实 DTO 缺前端依赖的字段**。
4. **`mockInbox` 的 `caseId` / `caseName` / `sourceLabel`** —— `InboxItemDto` 一个都没有（只有 `linkedCaseId`），已改为 `linkedCaseId`。

**两个有意保留的缺口（已在代码里写明原因，不做沉默处理）：**

- **`mockKnowledge`**：`lawName` 和多处使用的 `sourceId` 都不在 `KnowledgeItemDto` 里，但 OCR 来源关联需要它 → **需要后端决定是否补 `sourceId`**。
- **`mockStats`**：同时喂 `get_today_stats`（`TodayStats`）和 `get_dashboard_stats`（`DashboardStats`），**两者形状完全不同** → 需要拆分后才能分别标注。

**为什么 `mockEvents` 不绑定 DTO**：它不是任何命令的返回——`get_calendar_events` 会把它投影成 `CalendarEvent`（`date`/`eventType`/`caseName`）。给"投影前的中间形状"套 DTO 是错的契约，因此改为显式的本地夹具类型并注明原因。

> **标注本身就是护栏**：绑定后任何 mock ↔ Rust 的漂移都会被 `npm run typecheck`（已在 CI）拦下，不需要额外的脚本检查。

#### 5.2 明确验证方法的边界

| | 截图能验 | 截图**永远验不了** |
| --- | --- | --- |
| 布局、间距、层级、密度 | ✅ | |
| 明暗主题、纸纹、对比度 | ✅ | |
| 响应式断点表现 | ✅ | |
| **字段名/类型是否与后端一致** | | ❌ |
| **数据链是否接通** | | ❌ |
| **按钮点了有没有反应** | | ❌（mock 直接返回数据） |

**截图只覆盖"长什么样"，不覆盖"是不是对的"。** 布局/间距/字号/配色的判断可以靠截图；功能正确性必须靠 5.1 的类型约束 + 原生端到端 + 上一轮 `00-行动清单` 里的数据链核查。

## 四、优先级与成本

| 阶段 | 内容 | 成本 | 收益 |
| --- | --- | --- | --- |
| 0 | 接通 5 处死 UI | 半天 | **前置条件**，不做会美化谎言 |
| 1 | 组件层（8–10 个原语） | 1–2 周 | **最高**。之后所有视觉改动成本骤降 |
| 2 | 断点收敛到 3 个 | 2–3 天 | **最高性价比**，直接改善窄窗 |
| 3 | 四态真正落地 | 3–5 天 | 高。消除"失败伪装成空" |
| 4 | 视觉升级 | 2–3 周 | 高，但必须在 1–3 之后 |
| 5 | 验证矩阵 | 与各阶段并行 | 不可省 |

> **一句话**：**第 1、2 步是"让升级变便宜"，第 3 步是"让界面可信"，第 4 步才是"好看"。** 现在的直觉顺序（先做好看）是反的。
