## 三、发现的新问题：OCR 配图外置被完整性契约挡住

codex 文档把这项列为剩余项，看起来是"顺手做外置"的小活。**它不是。**

`document_pipeline.rs:553`：

```rust
if sha256_file(&result.markdown_path)? != hex::encode(expected_md.finalize()) {
    return Err(anyhow!("INVALID_MARKDOWN: Markdown 备份与页面不一致"));
}
```

即 **`source.md` 必须与所有 `page.markdown` 拼接后逐字节一致**。而 `visual.rs:59` 正是把 base64 PNG 写进 `page.markdown` 的：

```rust
"<figure><img alt=\"{label}\" src=\"data:image/png;base64,{}\">…"
```

**所以不能在 `source.md` 层面做外置**——改了就破坏该校验，且 `document_pages` 里仍存 base64，一致性对不上。转换路径（`conversion.rs:117` → `markdown_export::externalize_images_from`）能做外置，是因为它不走这条契约；**这正是两条路径行为不一致的根源**。

要把 60 页带图表的扫描件（base64 约 64 MB，正文不到 200 KB）从"正文永久显示超过 16 MiB"救回来，只能改引擎产物契约（`visual.rs` 写文件 + 相对路径），涉及：已有文档兼容、重新 OCR 策略、`document_pages` 与 `source.md` 的双向一致性。**属架构决定，需先定口径。**

### 步骤 2：`CalendarView` 的 `item.type` 疑点 —— **不存在，我的怀疑错误**

我怀疑"日历行读 `item.type` 但后端 DTO 没有该字段，点开庭会跳错页"。**追完整条链后确认是正确的：**

```
calendar.rs:176        event_type: "event"                    ← 独立日程确实是 "event"
        ↓
services/calendar.ts:26  type: event.eventType                ← 关键别名
        ↓
CalendarView.vue:812     e.type === 'event' ? 合并 CalendarEventRow : {}   ← 依赖该别名
CalendarView.vue:275     item.type === 'hearing' ? 'hearings' : 'tracks'  ← 因此正确
```

`CalendarEventRow` 确实没有 `eventType`，但它**不作为带类型语义的行进入展示**——只在 `type === 'event'` 时被 merge 进来补充时刻字段，而真实独立日程的 `event_type` 恰好就是 `"event"`。`e.type === 'hearing'/'court'/'deadline_*'` 那几处也都依赖同一个别名，语义正确。

**结论：无 bug，无需修改。**

**但保留一条维护性风险（不是缺陷，不建议现在动）**：`type` 是个**重载字段**——在 service 里是 `eventType` 的别名（`'hearing'`/`'court'`/`'deadline_*'`/`'event'`），在 `openEditDetail` 构造的合并行里又是 `'task'`/`'event'` 判别式。全仓约 15 处消费它，且跨 4 个视图。任何人新增一个未经该别名的数据源、或改动 `event_type` 取值，这 15 处会**静默失效**。

> 建议（低成本、非紧急）：在 `services/calendar.ts:26` 加一行注释说明 `type` 是 `eventType` 的别名及其取值集合；后续若要收敛，可把判别式改名 `rowKind` 以消除重载。

### 步骤 3：OCR 产物契约 —— 调研完成，**需先定一个口径**

我把约束链全部走了一遍，下面是完整结论。**这不是一个可以顺手做掉的 bug，而是要改数据格式。**

#### 3.1 症状

60 页带图表的扫描件：裁图 base64 约 **64 MB**（正文不到 200 KB）→ `workspace_sync.rs:84` 的 16 MiB 上限触发 → 知识库正文面板**永久显示「正文超过 16 MiB」**，且该上限是 `bail!`，用户无法绕过。

#### 3.2 为什么不能直接在 markdown 层外置（核心约束）

`document_pipeline.rs:553`：

```rust
if sha256_file(&result.markdown_path)? != hex::encode(expected_md.finalize()) {
    return Err(anyhow!("INVALID_MARKDOWN: Markdown 备份与页面不一致"));
}
```

**`source.md` 必须与所有 `page.markdown` 拼接后逐字节一致**，而 base64 正写在 `page.markdown`（`visual.rs:58`）里。改 `source.md` 就破坏该校验，且 `document_pages` 里仍存 base64，一致性对不上。

> 这也解释了转换路径为什么能做外置：`conversion.rs:117` 走 `markdown_export::externalize_images_from`，**它不走这条校验契约**。两条路径行为不一致的根源在此。

#### 3.3 关键可行性发现：相对路径在 webview 里会 404

预览渲染链是 `WorkspaceDocumentPreview.vue:18` → `mdToSafeHtml`（DOMPurify，`ADD_DATA_URI_TAGS: ["img"]`）。

DOMPurify 允许相对 `src`，**但 webview 里 `src="assets/x.png"` 会相对应用 origin（`tauri://localhost`）解析，而不是磁盘上的产物目录** → 必然加载失败。

所以"改成相对路径"**不能直接做**，必须配一条取图通道，否则图片全变裂图——比现在更糟。

#### 3.4 三个方案

| | 方案 | 改动 | 存量文档 | 代价 |
| --- | --- | --- | --- | --- |
| **A** | **引擎写图片文件 + 新增 `read_document_asset` 命令 + 前端按需取图** | `visual.rs` / `main.rs` / 新命令 / `WorkspaceDocumentPreview` | base64 版本继续可用（读取端兼容两种） | 最大，但**唯一根治**：markdown 变小、DB 变小、16 MiB 上限不再触发，且顺带可清理产物 |
| **B** | 读取时降级：超限则剥掉 base64 留占位符，按需回源 | `workspace_sync.rs` + 新命令 | 兼容 | 中等，但**每次取图都要重扫 64 MB 文件**，实际不可行 |
| **C** | 调大/取消 16 MiB 上限 | 1 行 | 兼容 | 最小，但**把内存问题原样留下**——我 04 报告里"非全链路有界内存"这条仍然成立，webview 吃 64 MB markdown 会更糟 |

#### 3.5 我的建议

**选 A。** 理由：它是唯一同时解决体积、内存和 16 MiB 死锁的方案；B 的取图代价让"按需"名不副实；C 只是把问题往后推。

**但 A 需要你先定两件事：**

1. **前端取图策略**：拿到 base64 数据 URI 后一次性内联（简单，但页面大时仍占内存），还是按可视区域懒加载（复杂，省内存）？我倾向前者——律师场景文档页数有限，一次性换取实现简单可靠。
2. **存量文档是否需要回填**：方案 A 只让**新处理**的文档变轻。已经 OCR 过的文档仍是 base64，仍会撞 16 MiB。要不要提供一个"重新提取（不重新 OCR）"的动作把它们转成外置？这决定要不要动 `document_pages` 的迁移。

> 我没有直接动手，原因是：① 这是**数据格式变更**，会改变已有案卷文档的产物形态；② 本机无法跑真实 OCR（缺 PP-OCR 模型），端到端只能靠 mock 验证，我不认为在这种情况下单方面改产物格式是负责任的。

**你给这两条口径，我就把 A 实现掉。**
