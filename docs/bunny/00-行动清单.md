## 二、你的第二个问题：为什么模块"感觉都没做好"

三个**架构级**原因，不是执行态度问题：

### 2.1 文档描述的是设计目标，不是当前实现

`docs/ARCHITECTURE.md` 自己写了"这些数值不证明每个入口已实现或通过验收"，但读起来还是像承诺。具体失真：

- 称"甘特保存广播 `task:changed` 使任务、首页、案件与通知消费者刷新"——**后端从未 emit 过 `task:changed`**，它只是前端内部事件
- 称 schema 为 **42**——`schema.rs:5` 实际是 **43**
- 称收件箱支持"截图、剪贴板、语音"——截图/转写是占位

### 2.2 验收证据的成分被高估了

- **`tests/e2e/` 有 17 个脚本，`vitest.config.ts` 只 include `*.test.ts`，playwright 不在依赖里，CI 也不跑 → 端到端覆盖实际为 0。** 应读作"325 项单元 + jsdom 组件测试，0 项 e2e"。
- 文档反复用"浏览器 Mock 验证"当验收证据，但 **338 条命令里只有 61 条有 mock，277 条在浏览器模式直接返回失败**——包括 `create_case`、`import_files_to_case`、`webdav_*`、`create_backup` 全部。**浏览器里点得动，完全不能推断桌面端可用。**
- 最大 store `src/stores/tasks.ts` **零测试**。

### 2.3 有一类 bug 是"类型签名"造成的，不是"写错代码"

`Cmd<P, void>` 这个模式让**成功和失败都返回 `null`**（`tauriBridge.ts:83-112`：成功返回 `result`，而 `()` 序列化成 `null`；失败也返回 `null`）。于是 `if (ok !== null)` 判成功在类型上完全合法、在运行时恒假。

**这不是调用方写错，是签名泄漏。**只改那 2 处调用点的话，下一个人写 `void` 命令还会再踩。→ 见 2.4。

### 2.4 建议的机制性修复（比逐个改调用点更值）

| 机制 | 现状 | 建议 |
| --- | --- | --- |
| `Cmd<P, void>` 陷阱 | 成功=失败=`null` | 给 `void` 单独签名 `tauriCallVoid(): Promise<{ok,error?}>`，或让这批命令返回 `bool` |
| 事件总线 | 后端发 6 个，前端听 3 个 | 建一张**事件契约表**（事件名 → 发方 → 收方），加脚本测试断言每个 `emit` 都有 `listen`。这类 bug 100% 可机械检出 |
| 测试隔离 | 无隔离时**直接写真实案件库**，无任何防护 | `open_db()` 加 `#[cfg(test)]` 断言：未检测到隔离根就 panic。约 5 行 |
| 前端筛选 | 13 个筛选器各自 `emit`，父组件只 `assign` 不取数 | 在 store 加统一 `setFilter(patch)` action（assign + load），杜绝重演 |

## 四、你的实验为什么"冒 bug"——两个被忽略的结构性原因

这两条**不是**本轮新发现的缺陷，而是解释"为什么只有真实使用才炸"的关键。

### 4.1 43 版 schema 迁移，没有「迁移后 == 新装」等价性测试

- `db/schema.rs` **4,784 行**，`CURRENT_SCHEMA_VERSION = 43`（文档全写 42）
- 只有 v11/v12/v23/v24 有单独幂等测试，共 4 处版本号断言，**无 `sqlite_master` 全量比对**
- **后果**：一个用户从 v20 升到 v43 的库，与一个全新安装的 v43 库，**结构可能不同**。这类 bug 只在真实用户升级时暴露，测试永远发现不了。

> **这是"生产实验时冒 bug"的最可能来源之一。** 你现在这台机器上的库已经历过 43 次迁移，**它的状态没有任何测试覆盖过**。
> 建议：加一个测试——拿一个 v20 fixture 库跑完整迁移，然后与全新 v43 库 dump `sqlite_master` 比对。这一个测试能覆盖大量你现在无法察觉的隐患。

### 4.2 所有 CI 门禁都是纸面的

- `ci.yml` 的 push 触发是 `branches: [main]`；**当前工作在 `codex/casy-0.1.3-production-validation` 分支，仓库零 PR** → **这份代码上一次跑 CI 是 2026-08-26，落后 25 个 commit**
- 因此 clippy 零警告、`cargo audit`、bindings 漂移、**Windows 测试**——**在这份代码上一次都没跑过**
- 而分支上的 `beta.yml` 最近 3 次 Windows 打包 = **failure / failure / cancelled**，失败点正是 `portable_backup`，暴露出**生产代码在 Windows 上生成了混合分隔符路径**（`/new/case\file.pdf`）会被写进备份 Markdown。**该修复从未在 Windows 验证过。**

> **修法成本极低**：给该分支开一个 PR，或把 `push.branches` 加上它。**这一个改动是唯一能把"所有绿灯"从纸面变成现实的。**
> 在此之前，**任何"全绿"都只是某一台 macOS 上的手动结果**。

### 4.3 加密路径几乎没有测试覆盖

`db/mod.rs:292-296` 显示测试模式直接 `Connection::open`，**不开 `PRAGMA key`**。全仓仅 1 处测试用过 `PRAGMA key`（`backup_restore_test.rs:71`），且是手工构造。

> 意味着 **43 个版本的全部迁移都跑在明文 SQLite 上**，而生产库是 SQLCipher 加密的。
> 加密打开、密钥不匹配、明文→密文迁移、`VACUUM INTO` 加密备份——**测试覆盖约等于零**。
> `RELEASE_0.1.3.md` 里"节假日 SQLCipher 集成测试验证…"这句是不准确的。
> **对你做实验的直接影响**：备份/恢复是数据不丢的最后一道线，而它恰好是加密路径最缺测试的一块。

### 4.4 codex 修的那类缺陷，在 `commands/` 之外还活着 24 处 —— **我已复核**

codex 这轮修的是"查询成功却缺记录"（SQL 行解码失败被丢掉后返回成功），并加了一个守护脚本 `scripts/read-integrity.test.mjs`。**但那个脚本只扫一个目录**：
