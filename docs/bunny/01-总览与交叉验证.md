### 2.4 我发现的一个真实设计问题：向量索引锁会与真实运行实例互斥

`db/vector_index.rs:108-130` 用 `lock` 文件 + `try_lock()`，root 由 `conn.path()` 派生（`vector_index.rs:450-457`）。

- 隔离目录下**两个测试并行**会互相抢锁 → 这解释了 2.2 里那次失败。
- 更实际的影响：**只要用户的 Casy.app 正在运行，跑测试就会拿到 `unavailable` 而非崩溃**——行为是安全的（降级为关键词检索，不会损坏数据）。
- 但它意味着**测试与生产实例共享一把锁语义**，隔离保证依赖 `CASY_TEST_DATA_DIR` 正确传入。

### 2.5 测试数据隔离：**我最初判断错了，此处更正**

**我第一版写的是**：29 个集成测试中至少 10 个自身不设隔离目录，完全依赖调用者传 `CASY_TEST_DATA_DIR`；因此"一个新人执行最自然的 `cargo test`，会直接写真实资料库"。

**这个结论是错的。** 我只看了测试文件里有没有隔离语句，**没有去看 `db_path()` 本身**。07 审计做了决定性实验（假 `HOME` 验证，14 个测试二进制实测产生 **0 个文件**），我已独立复核代码确认：

```rust
// db/mod.rs:392-403
fn db_path() -> PathBuf {
    if IS_TEST_MODE.load(Ordering::SeqCst) || std::env::var("TEST_ENV").is_ok() {
        return TEST_DB_PATH.get_or_init(|| {
            std::env::temp_dir().join(format!("casy_test_{}.db", uuid::Uuid::new_v4()))
        }).clone();
    }
    crate::runtime_paths::data_root().join("casy.db")   // ← 测试模式永远到不了这里
}
```

实测分布：**19 个测试文件调用 `db::enable_test_mode()`**（进程级全局开关），**16 个自己 `set_var("CASY_TEST_DATA_DIR", ...)`**，其余用 `Connection::open_in_memory()`。

> **结论：当前没有任何测试能碰到真实案件库，可以放心。**

但两个隐患成立（详见 07 §5.3）：
1. **`npm test` 不设 `CASY_TEST_DATA_DIR`**，今天安全靠"每个测试作者都记得调 `enable_test_mode()`"这个**约定**维持。历史上已因此坏过 3 次。→ 建议把隔离写进 `package.json`，别依赖记忆。
2. **`enable_test_mode()` 是进程级全局**（`AtomicBool` + `OnceLock`），同一二进制内所有测试**共享同一个临时库**。`ai_profiles_test.rs`（5 例）、`knowledge_index_test.rs`（2 例）无互斥锁，会看到对方的行。

> **教训**：我犯的错是"用 grep 数测试文件里的隔离语句"这种**代理指标**，而没有读被测函数本身。07 用了可证伪的实验（假 HOME）来判定，这是更可靠的方法。

## 四、`Cmd<P, void>` 类型陷阱（我独立复核，确认为真）

这是本轮**最值得立刻修**的机制性缺陷。

### 机制

`core/tauriBridge.ts:83-112` 的 `tauriCall` 约定：
- 成功 → 返回 `result`
- 失败 → 返回 **`null`**，并弹 `ElMessage.error`

而 Rust 的 `Result<(), String>` 成功时 serde 序列化成 **`null`**。

于是对任何 `Cmd<P, void>` 命令：**成功返回 `null`，失败也返回 `null`**。

`TasksView.vue:582` 与 `:592` 用 `if (ok !== null)` 判成功：

```ts
const ok = await tauriCall('defer_task', {...}, { errorMessage: '推迟失败' })
if (ok !== null) {            // ← 成功时恒为 false
  ElMessage.success(...)      // 永远不执行
  showDeferDialog.value = false   // 弹窗永远不关
  await loadTasks()               // 列表永不刷新
}
```

**用户实际体验**：数据库写成功了，但**没有成功提示、弹窗不关、列表不刷新、任务还留在"今日专注"里**。用户以为失败，再点一次 → 重复推迟。

### 爆炸半径（我逐条枚举，范围很小）

全仓 44 个 `void` 返回的命令，我逐个检查其调用点是否用了 `!== null` 判成功：

- **`defer_task`、`clear_task_defer` —— 仅这 2 个中招。**
- 其余 42 个调用点未使用该 idiom。

另注：`src/core/services/tasks.ts` **没有**这两个命令的服务方法，`TasksView.vue` 直接调 `tauriCall`——同时构成服务层绕过。

### 为什么类型检查没拦住

`CommandMap[K]['result'] | null` 在 `void` 情况下是 `void | null`，`!==` 比较在类型上完全合法。**这是 `void` 泄漏进返回值联合类型造成的，不是调用方写错。**

> **修法（二选一，倾向后者）**
> 1. 治标：这两处改用 `tauriCallSafe(...).ok`。
> 2. **治本（推荐）**：给 `void` 结果单独的调用签名 `tauriCallVoid(): Promise<{ok: boolean; error?: string}>`，或让这批命令返回 `bool`。
>    只治标的话，下一个写 `void` 命令的人会再踩一次——**这类 bug 的成因在类型签名，不在调用点。**
