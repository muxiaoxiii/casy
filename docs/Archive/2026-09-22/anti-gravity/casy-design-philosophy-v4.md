# Casy 设计哲学 v4.0：可靠而安静的专业工作管家

> **版本**：v4.0 Candidate<br>
> **日期**：2026-08-28<br>
> **状态**：候选设计基准，待评审后取代旧版总纲<br>
> **适用范围**：产品方向、体验原则、领域语义、AI 权限边界、可靠性标准与后续开发裁决<br>
> **不包含**：当前实现状态、代码文件名、数据库建表语句、版本排期、已完成清单与某一版界面布局

---

## 0. 文档定位

### 0.1 这份文档回答什么

这份文档回答五类长期问题：

1. Casy 究竟是什么，不是什么；
2. 面对互相冲突的产品选择时，优先保护什么；
3. 用户、规则、AI、外部系统分别拥有什么权力；
4. 案件、项目、任务、日程、期限、知识和材料之间应遵循什么稳定语义；
5. 一个功能怎样才算符合 Casy，而不只是“已经做出来”。

它是后续产品设计、技术架构和功能评审的上位约束，但不是所有细节的唯一答案。哲学负责稳定方向，架构负责实现方式，路线图负责先后次序，状态文档负责记录事实。

### 0.2 文档层级

| 层级 | 回答的问题 | 应包含 | 不应包含 |
|---|---|---|---|
| 设计哲学 | 为什么做、保护什么、如何裁决 | 定位、原则、语义、不变量、质量标准 | 当前完成度、具体表名、临时页面结构 |
| 产品规格 | 用户如何完成一项具体工作 | 用户旅程、交互、状态、异常、验收 | 未经验证的技术细节 |
| 技术架构 | 怎样可靠地实现 | 数据模型、接口、事务、同步、安全 | 把当前代码偶然结构包装成产品原则 |
| 决策记录 | 为什么在多个方案中选了一个 | 背景、选项、证据、取舍、回滚条件 | 事后改写历史 |
| 路线图 | 何时做、依赖什么 | 阶段、优先级、资源、退出条件 | 宣称长期设计已经实现 |
| 状态与验证 | 现在真实做到什么 | 代码证据、测试结果、已知边界 | 目标态承诺冒充现状 |

### 0.3 版本纪律

- 当前实现不能反向决定长期哲学；实现只能证明某条原则可行或需要修订。
- 某个竞品的页面、某次重构方案、某套组件库和某个数据库版本，都不是哲学本身。
- 设计哲学发生实质变化时，必须写明被推翻的假设、触发证据和迁移影响。
- 本文中的示例用于解释语义，不等于冻结页面、字段名或技术选型。
- 在本候选版正式批准前，旧文档仍可作为历史材料，但不应继续扩写为新的实现清单。

### 0.4 如何理解旧材料中的意见

旧材料里混合了三种不同层次。本版按以下方式处理：

| 旧材料中的表达 | 本版判断 | 处理方式 |
|---|---|---|
| “先捕获、后整理” | 稳定原则 | 保留并补齐原始输入、厘清、撤销和来源链 |
| “任务与日历是双核” | 稳定产品结构 | 保留，但明确行动、事件、期限、时间块不能混成一个日期字段 |
| “案件是项目书” | 稳定体验目标 | 保留“打开即恢复上下文并可推进”，不冻结纵向页或 Tab |
| “专业管家” | 稳定关系隐喻 | 具体化为安静、预备、可解释、守权限、可追责的行为契约 |
| “本地规则打底、AI 增强” | 稳定架构原则 | 保留，增加规则候选的测试、批准、回滚流程 |
| “固定六个顶级入口” | 阶段性信息架构方案 | 不升格为哲学；入口由用户任务、频率和可达性验证 |
| “任务固定六个透视” | 默认产品方案 | 保留核心语义，不限制未来增加或合并派生视图 |
| “三条法律程序轨” | 专利业务预设 | 改为可配置程序轨模板，不作为领域模型上限 |
| “下一步卡必须悬浮左下角” | 界面实现选择 | 只保留“下一步行动在上下文中始终容易找到” |
| “四套指定主题” | 视觉方案 | 只保留主题可访问性、稳定语义和视觉安静 |
| “AI 成功后自动扩容规则库” | 高风险自动化 | 改为候选规则，经样本验证、人工批准后才能启用 |
| “AI 再检查一次就等于双人复核” | 不成立的安全假设 | 明确模型复核只是辅助校验，不能冒充独立事实证明或第二位人类复核者 |

# 第一篇：设计原点

## 1. Casy 是什么

### 1.1 一句话定位

> **Casy 是面向个人法律专业人士的本地优先工作系统：它把不断涌入的信息，转化为可追踪的承诺、可安排的时间、可恢复的案件上下文和可积累的专业判断。**

“全流程秩序引擎”描述的是系统机制，“专业工作管家”描述的是用户关系：

- **秩序引擎**：持续完成捕获、厘清、关联、安排、执行、回顾与沉淀；
- **专业管家**：提前准备但不擅自决定，记住上下文但不制造监控感，发现风险但不夸大确定性，执行授权动作并留下清晰痕迹；
- **本地优先**：用户设备上的数据和规则拥有最终权威，联网服务和 AI 都是可替换的增强层；
- **法律专业**：通用工作管理是地基，案件程序、期限、文书、证据与职业保密是专业层，而不是把所有日常事项都强迫装进“案件”。

### 1.2 北极星问题

Casy 的主界面、通知、搜索、AI 建议和案件详情，最终都应帮助用户更快回答以下问题：

1. **现在最值得做什么？**
2. **哪些时间或期限不能移动？**
3. **我正在等谁、等什么、何时应当跟进？**
4. **这个项目或案件卡在哪里，下一步是什么？**
5. **这条信息、结论或建议来自哪里？**
6. **系统准备做什么，会改变什么，我能否撤销？**
7. **如果 AI、网络或外部服务失效，我还能完成哪些核心工作？**

不能帮助回答这些问题的新增复杂度，默认不进入核心产品。

### 1.3 核心用户

第一目标用户是独立工作的法律专业人士，包括执业律师、法务、实习律师和律师助理。共同特征是：

- 同时承担多项长期承诺和突发工作；
- 期限错误、材料遗漏和上下文丢失的代价高；
- 个人工作方法差异明显，需要可配置但不能无边界；
- 工作信息具有较高敏感性，不能默认上云或被模型长期保留；
- 日常行动不仅来自案件，也来自客户维护、研究、行政、学习和个人安排；
- 需要与邮件、日历、文件系统、文档工具和外部 AI 协作，但不希望被任何一个外部平台锁定。

Casy 可以支持团队协作，但不以企业级审批、组织架构、工时计费和多租户管理作为默认前提。若未来进入团队场景，应作为清晰的能力层扩展，而不是让个人用户先承担企业软件的复杂度。

### 1.4 Casy 解决的根本矛盾

法律专业工作长期存在四组冲突：

| 冲突 | 典型表现 | Casy 的责任 |
|---|---|---|
| 可计划工作与突发工作 | 庭前准备被临时送达或客户请求打断 | 保护硬边界，快速收纳突发事项，帮助重新排程 |
| 案件上下文与全局行动 | 每个案件各自完整，但用户只有一个今天 | 让案件保持隔离，同时把可执行行动汇总到个人工作流 |
| 确定性责任与不确定性判断 | 期限必须算对，优先级却会随情况变化 | 规则负责事实和约束，AI 负责可解释的建议 |
| 信息积累与注意力稀缺 | 数据越来越多，但当下只需要很少一部分 | 保留完整来源，以派生视图和渐进披露控制噪音 |

### 1.5 成功不是“装得更多”

Casy 成功时，用户感受到的是：

- 新信息可以立即放下，不必先决定放进哪个模块；
- 打开软件后不需要重新拼接昨天的上下文；
- 期限、日程、行动和等待的语义不会互相混淆；
- 一个事实只维护一次，却能在相关视图中正确出现；
- 关键提醒有依据、有层级、有送达状态，不靠制造焦虑获取注意力；
- AI 能节省整理和准备时间，但关闭 AI 后核心工作仍完整可用；
- 数据可以导出、核对、备份、恢复和迁移，不被产品绑架；
- 使用时间越长，系统越懂用户的偏好，但用户仍能查看、纠正和删除这些学习结果。

## 2. Casy 不是什么

### 2.1 不是数据库外壳

案件字段再完整，也不能自动产生下一步行动。Casy 的价值不在于复刻一张更复杂的多维表格，而在于把事实转化为可执行流程，并保持事实、判断和行动之间的来源关系。

### 2.2 不是通用 GTD 工具的法律皮肤

通用任务管理无法自然表达法律期限、送达基准、程序轨、证据来源、决策依据和案件隔离。Casy 的通用工作流必须足够好，但专业层必须真正改变系统如何理解风险与上下文。

### 2.3 不是自主办案代理

Casy 可以读、整理、提议和在授权后执行，但不能把概率性生成包装为法律事实，不能在关键法律决策上替代专业判断，也不能借“自动化”绕过用户授权。

### 2.4 不是所有工具的替代品

Casy 不必重造最好的文字处理器、邮件客户端、法律数据库、云盘或视频会议。它应成为工作上下文与承诺的中枢：知道材料在哪里、为什么相关、下一步要做什么，并以稳定接口调用合适工具。

### 2.5 不是靠通知维持使用率的产品

提醒的目标是防止遗漏和保护计划，不是增加打开次数。没有新信息时保持安静，是产品正确工作的表现。

### 2.6 不是无限扩张的“超级应用”

每个新增模块都必须证明它完成了核心工作循环中一个不可替代的职责。仅因某个竞品拥有、某类数据可以存储或技术上能够实现，不构成立项理由。

## 3. 产品能力的层次

Casy 的能力按依赖关系分为四层。上层可以增强下层，不能掩盖下层缺失。

### 3.1 第一层：个人工作基础

必须在没有案件、没有 AI、没有联网服务时仍然成立：

- 快速捕获；
- 任务、等待与回顾；
- 独立日程与时间安排；
- 搜索、归档、撤销；
- 本地通知与启动补偿；
- 数据导出、备份与恢复。

### 3.2 第二层：法律专业上下文

在个人工作基础上增加：

- 案件作为专业项目的特化；
- 程序轨、关键节点与法定期限；
- 当事人、客户和关联案件；
- 材料、文书、证据与沟通记录；
- 决策依据、复核责任与职业保密；
- 案件复盘和经验沉淀。

### 3.3 第三层：主动智伴

在可靠事实和完整手动闭环已经存在后增加：

- 捕获内容的候选解析；
- 关联、优先级、排程和跟进建议；
- 文档准备、摘要和检查清单；
- 模式识别、回顾辅助和个人偏好学习；
- 带来源、假设、风险和预期影响的操作提案。

### 3.4 第四层：开放生态

在权限、审计和可逆性已经成立后增加：

- 日历、邮件、文件系统和同步服务；
- 文档生成、法律检索、翻译等按需技能；
- 面向外部工具的查询与受控写入接口；
- 条件成立时的移动访问或团队协作。

**层次纪律**：如果下层闭环仍需依赖上层才能完成，说明设计次序错误。例如，用户不能因为 AI 分类失败而无法整理收件箱，也不能因为云服务离线而看不到本地期限。

# 第二篇：专业管家的行为契约

## 4. “专业管家”不是人格包装

“专业管家”是一组可以验收的行为，而不是欢迎语、拟人头像或聊天气泡。

### 4.1 安静

- 没有需要用户处理的新事实时，不制造提示。
- 同一风险不在多个入口重复叫喊；不同通道共享去重与状态。
- 低风险建议进入可稍后查看的复核区，不抢占当前工作。
- 打断强度与风险、时效和用户偏好相匹配。

### 4.2 预备

- 在用户进入案件或任务前，准备相关材料、最近变化、待决问题和下一步。
- 预备结果先展示，不擅自改写正式数据。
- 对突发工作，说明它将挤占什么，而不只说“很紧急”。

### 4.3 记得住

- 记住稳定偏好、明确决定和被确认的经验；
- 不把所有点击、对话和原始材料永久当成“记忆”；
- 每条派生记忆可查看来源、适用范围、更新时间和失效条件；
- 用户可以纠正、停用、导出或删除。

### 4.4 说得清

- 推荐必须区分事实、推断、假设和建议；
- 关键数字、日期、状态和材料引用可以回到来源；
- 无法确定时说“不确定”，并指出缺少什么；
- 不能用流畅文案掩盖证据不足。

### 4.5 守边界

- 读取不等于修改，修改不等于发送，发送不等于送达；
- 本地可逆变更和对外不可逆行为使用不同授权等级；
- 涉及敏感数据时遵循最小必要上下文；
- 用户关闭某个通道或模型后，不通过其他路径绕开。

### 4.6 做完留痕

- 重要变化说明谁、何时、基于什么、改变了什么；
- AI 或外部工具的操作不能伪装成用户手动操作；
- 失败、部分成功、结果不明和已回滚必须可区分；
- 审计记录服务于核对与恢复，不服务于监控用户。

### 4.7 知道退场

- 用户接管后，建议应退到背景，不持续争夺控制权；
- 功能完成使命后应允许隐藏、归档或移除；
- 自动化连续被拒绝或纠正时，应降低主动性并请求重新设定规则。

### 4.8 不冒充权威

- Casy 可以帮助准备法律工作，不能对法律结论做虚假的确定性担保；
- “模型复核通过”不等于事实已被证明；
- “服务端接受”不等于终端送达或用户已读；
- “同步成功”不等于多端数据完全一致；
- “已经记录”不等于用户已经理解或同意。

## 5. 中央工作循环

Casy 的所有核心功能都应服务同一循环：

> **捕获 → 厘清 → 组织 → 计划 → 执行 → 观察 → 回顾 → 沉淀**

### 5.1 捕获 Capture

目标是完整保存当下出现的信息，避免因分类负担而丢失。

最低要求：

- 保留原始内容、来源、接收时间和附件；
- 捕获路径足够短，支持文本、文件、链接、邮件、语音转写等逐步扩展；
- 即使解析、上传、AI 或网络失败，原始输入也不能丢；
- 捕获成功与后续处理成功是两个不同状态。

### 5.2 厘清 Clarify

目标是回答：“这是什么，它要求我做什么？”

可能结果包括：

- 无需行动，作为材料或知识保存；
- 形成一个可执行行动；
- 形成一个等待或委派；
- 形成一个事件、期限或时间建议；
- 关联到已有项目、案件、客户或领域；
- 创建新项目的候选；
- 无价值、重复或错误，丢弃并保留必要审计。

系统可以预填候选结果，但用户必须能看到原文、修改解释并批量处理。

### 5.3 组织 Organize

目标是建立足够的上下文，而不是把所有字段填满。

组织只要求当前阶段真正必要的关系：责任主体、所属项目、下一步、硬时间、等待对象、材料来源。其余信息应按需补充。

### 5.4 计划 Plan

目标是把承诺放入有限的时间和注意力中。

计划必须同时看到：

- 不可移动的事件与期限；
- 已经可做的行动；
- 尚未可做的等待或阻塞；
- 可用时间、预计耗时和切换成本；
- 新突发事项会挤占的原计划。

计划建议是可调整的，不应把用户的日历填成虚假的精确计划。

### 5.5 执行 Do

目标是让用户以最低摩擦进入工作并保持上下文。

执行界面优先展示：动作、完成标准、材料、硬边界和最近决定。完成、推迟、转等待、重新安排和补充说明都应是明确且可撤销的动作。

### 5.6 观察 Observe

项目状态会因外部世界变化：收到送达、对方回复、会议改期、文件更新、同步冲突。系统必须把“外部发生了什么”与“用户决定怎么处理”分开。

### 5.7 回顾 Review

回顾不是报表展示，而是恢复控制：

- 收件箱是否清空到可接受水平；
- 每个活跃项目是否有明确下一步或明确等待；
- 等待是否超过跟进阈值；
- 未来硬时间是否已留出准备空间；
- 过期建议、无效关系和陈旧记忆是否需要修订；
- 本周计划与实际偏差说明了什么。

### 5.8 沉淀 Learn

沉淀只保存对未来有复用价值的内容：明确决定、被验证的做法、稳定偏好、模板、风险模式和专业经验。原始活动日志不自动等于知识。

# 第三篇：十二条设计原则

## 6. 原则一：承诺优先于记录

### 含义

案件、文件和字段描述世界；行动、等待、事件和期限决定用户接下来如何工作。Casy 必须从记录中提取承诺，但不能把记录完整误认为工作已经被管理。

### 设计规则

- 每个活跃项目都应有明确的下一步、明确的等待，或明确说明暂不推进；
- 案件状态变化应能触发需要复核的行动候选，而不是只改一个标签；
- 文件被归档后，仍需判断是否产生期限、任务、决定或知识；
- 首页和项目详情优先显示可行动信息，再按需展开完整记录。

### 反例

- 详情页字段很多，却看不出谁在做什么；
- “进展中”成为无意义状态；
- 只统计已录入材料数量，把它当成项目推进度；
- 完成一个程序节点后没有下一步或回顾提示。

### 验收问题

> 用户打开任意活跃项目，能否在十秒内说清下一步、责任人、硬时间和当前阻塞？

## 7. 原则二：先捕获，后厘清

### 含义

捕获追求不丢，厘清追求准确。两种心智模式不能强迫用户同时完成。

### 设计规则

- 捕获阶段只要求最少输入；
- 标题、分类、关联和日期可以由系统建议，但不能成为保存原文的前置条件；
- 原始输入保持可见，后续结构化结果与原文建立来源关系；
- 捕获入口可以按意图优化，但所有入口进入同一可追踪处理机制；
- 收件箱是待处理状态，不是垃圾桶，也不是永久存储分类。

### 反例

- 录入一句话前必须选择案件、类别、优先级和截止日；
- AI 分类失败导致输入无法保存；
- 把快捷键数量当成捕获体验本身；
- 自动生成的标题覆盖原文且无法恢复。

### 验收问题

> 用户在被打断的情况下，能否在五秒左右安全放下一条信息，并确信稍后可以找到、理解和整理？

## 8. 原则三：时间语义必须分离

### 含义

“什么时候发生”“什么时候可开始”“什么时候打算做”“什么时候必须完成”“什么时候提醒”是不同事实。把它们压缩成一个日期字段，会制造误导和错误自动化。

### 设计规则

- 事件有开始、结束、时区和是否全天；
- 行动可有可见/可开始时间，但没有日期也可以是合法的可执行行动；
- 截止期限单独表达，并记录计算依据、基准事件和适用规则；
- 时间块表示用户打算投入的时间，不改变任务的法律截止；
- 提醒是围绕事件、期限或跟进建立的派生交付计划；
- 等待有跟进时间，不应伪装成自己的截止日；
- 拖拽时必须明确将改变的是事件时间、计划时间、开始时间还是截止期限。

### 反例

- 把任务拖到明天就同时修改截止日；
- 法院送达日、上诉期限和计划起草日共用一个字段；
- “Upcoming”同时混合未来事件、未来可见任务和临近截止；
- 休眠期间错过本地提醒后仍显示“已送达”。

### 验收问题

> 用户能否区分“不能动的时间”“可以开始的时间”“打算投入的时间”和“系统提醒的时间”？

## 9. 原则四：认知对象要少，事实模型要诚实

### 含义

“数据有限，视图无限”约束的是用户必须理解的核心概念，不是强迫数据库只有几张表。独立事实应该独立建模，派生视图不应复制存储。

### 设计规则

- 新顶级概念必须证明用户真的需要以新的心智模型理解它；
- 独立日程、参与方、材料版本和发送作业等事实可以规范化建模，不必塞进案件宽表；
- “今天、下一步、等待、回顾、某天、风险”等优先作为规则派生的视图；
- 同一事实由一个权威来源维护，其他位置显示投影；
- 缓存字段可以为性能存在，但必须能从权威事实重建。

### 反例

- 为每个新列表建立一套独立数据；
- 为了坚持“四个对象”而否认独立日程的存在；
- 项目和案件保存两份互相漂移的任务；
- 视图为了方便修改权威事实的含义。

### 验收问题

> 这是新事实、新关系，还是旧事实的一种视图？若是新事实，它的权威来源和生命周期是什么？

## 10. 原则五：默认隔离，按角色链接

### 含义

法律信息需要案件级隔离，但专业工作又需要跨案件复用。链接必须表达“为什么相关”，并遵循最小披露，而不是把相似文本自动混成一个上下文池。

### 设计规则

- 案件材料默认只在本案件上下文中出现；
- 跨案件关系应有类型、方向、创建者、依据和可撤销状态；
- 客户、当事人、专利、法条、模板等可以成为跨项目的稳定连接点；
- AI 推断的关系先是候选，不直接进入正式关系；
- 搜索结果可以跨域，但敏感内容的预览和模型上下文仍受权限与范围限制；
- 知识复用应引用来源，不复制后失去出处。

### 反例

- 因为客户名相同就把两个案件的材料全部送入模型；
- 自动建立关系后用户无法知道或删除；
- 用标签替代有语义的关系；
- 复制一段法律分析到多个案件后无法追踪版本。

### 验收问题

> 每条跨对象关联是否说明了关系角色、依据、可见范围和解除方式？

## 11. 原则六：把注意力当作稀缺资源

### 含义

克制不是“少做界面”，而是让信息、动作和提醒按当前决策价值排序。专业软件可以信息密集，但不能注意力嘈杂。

### 设计规则

- 默认先显示当前工作所需内容，再展开背景和历史；
- 一个表面只有一个清晰的主要任务，不等于只能有一个按钮；
- 颜色、动效、徽标和声音都必须表达状态或因果；
- 低频管理功能退出主工作路径，但保持可达；
- 用户可以安静处理建议、批量确认和延后复核；
- 重要不是靠更大、更红和更频繁表达，而是靠可靠排序与明确说明。

### 反例

- 首页堆满统计卡、图表、鼓励语和 AI 建议；
- 每条任务都有不同颜色；
- 同一截止风险同时出现弹窗、角标、横幅和重复通知；
- 空状态展示装饰画却没有下一步。

### 验收问题

> 去掉这个视觉或通知元素后，用户是否会失去重要状态、因果或操作线索？如果不会，就应去掉。

## 12. 原则七：本地是权威，用户拥有退出权

### 含义

本地优先不是“有一个 SQLite 文件”，而是核心工作在断网时可继续、用户掌握数据与凭据、同步只是复制机制、任何云端能力都可停用和替换。

### 设计规则

- 核心增删改查、搜索、任务、日程、案件和确定性计算离线可用；
- 本地数据是默认权威副本，远端同步必须有明确冲突语义；
- 凭据进入系统安全存储，不写进普通数据库、日志或导出包；
- 提供可读、可迁移的导出与经过验证的备份恢复；
- 云端模型或服务停用后，用户数据和基础工作流不被锁住；
- 删除账户或解除连接，不应悄悄删除本地权威数据。

### 反例

- 网络失败时无法打开今日列表；
- WebDAV、日历或 AI 连接成为启动前置；
- 同步冲突静默采用“最后写入覆盖”；
- 用户能备份却从未验证恢复。

### 验收问题

> 拔掉网络、关闭 AI、撤销外部连接后，用户还能否安全完成今天的核心工作并带走全部数据？

## 13. 原则八：确定性内核，概率性增强

### 含义

规则擅长产生可重复事实，AI 擅长理解开放文本、提出候选和生成表达。二者必须分工，不能用 AI 的流畅掩盖确定性能力缺失。

### 设计规则

- 日期计算、状态合法性、去重、权限、事务和同步幂等由确定性机制负责；
- AI 可做提取候选、关联候选、排序建议、摘要、草稿和解释；
- 每个 AI 功能都有无 AI 路径或明确说明为何没有；
- AI 输出进入正式数据前必须通过与风险相称的校验和授权；
- 规则和模型的输出在界面与审计中可区分；
- 不能把模型置信度当作事实正确率。

### 反例

- 让 LLM 直接计算法定期限；
- 模型无法使用时整个收件箱无法处理；
- AI 自动改变案件状态却只留下聊天记录；
- 把结构化校验交给第二次模型调用。

### 验收问题

> 这项结果必须每次相同且可证明吗？如果是，它为什么依赖模型？

## 14. 原则九：AI 先提案，系统再执行

### 含义

AI 的默认产物是 Proposal，而不是 Mutation。提案说明准备改变什么、依据什么、可能遗漏什么，执行由统一权限入口完成。

### 设计规则

- 提案包含目标、来源、假设、风险、预期改动、可逆性和有效期；
- 用户可以逐项接受、修改、拒绝或稍后处理；
- 执行时重新检查来源版本与目标状态，防止基于过期上下文写入；
- 外部发送、删除、覆盖、法律关键状态变更使用更高授权；
- 批量操作先显示影响范围和可撤销边界；
- 自动执行只适用于用户明确建立、可暂停、可审计、风险可控的规则。

### 反例

- AI 解析邮件后直接修改期限；
- 一个“全部接受”按钮不展示将发生的具体变化；
- 用户确认后间隔很久仍用旧快照执行；
- 把一次接受推断为永久授权。

### 验收问题

> 在点击确认前，用户是否知道系统将改变哪些正式数据、触发哪些外部影响，以及如何撤销？

## 15. 原则十：重要变化必须可追溯、可撤销、可对账

### 含义

可靠不是永不失败，而是失败可见、状态可辨、影响可恢复。对法律工作而言，来源与变化链本身就是产品能力。

### 设计规则

- 重要写操作有操作者、时间、前后值、原因和关联来源；
- 本地可逆操作默认提供撤销或版本恢复；
- 外部副作用使用不可变作业标识、幂等键和对账状态；
- “失败”“部分成功”“结果未知”“已取消”“已回滚”不能合并成一个错误；
- 决策变化通过新记录取代覆盖历史；
- 审计日志与行为学习数据分离，保留策略分别定义。

### 反例

- 更新案件后只看到最新值；
- 网络超时就盲目重发邮件或重复创建日历事件；
- AI 操作在日志里显示为用户操作；
- 删除任务只能从数据库备份恢复。

### 验收问题

> 如果用户明天质疑“为什么变成这样”，系统能否给出可理解的变化链，并在可逆范围内恢复？

## 16. 原则十一：从纠正中学习，记忆必须受治理

### 含义

系统成长的高价值信号不是“用户点过什么”，而是用户如何纠正建议、实际如何执行、哪些做法后来被确认有效。记忆需要范围、来源、有效期和删除权。

### 设计规则

- 区分原始活动、派生偏好、正式决定和长期知识；
- 用户修改建议的差异是学习信号，但不自动泛化为全局规则；
- 记忆进入推荐前需要适用范围和新鲜度判断；
- 原始日志按必要性保留，不设“一切永久保存”的默认；
- 相互冲突的记忆并存时，应提示复核而非静默选择；
- 模型可替换，成长数据不能锁在模型对话历史中。

### 反例

- 用户一次把任务挪到晚上，系统就认定其偏好深夜工作；
- AI 总结未经确认直接成为案件经验；
- 所有原始行为日志永久进入模型上下文；
- 切换模型后系统“失忆”。

### 验收问题

> 这条记忆是谁确认的、依据什么、适用于哪里、何时可能失效，用户能否删除？

## 17. 原则十二：开放能力，收紧权限，诚实降级

### 含义

Casy 应与外部世界连接，但连接不能产生特权旁路。每个外部能力都必须声明读取、写入、发送、凭据、离线和失败边界。

### 设计规则

- 外部工具读写通过同一权限和审计机制；
- 技能按需加载，只获得完成任务需要的最小上下文和工具；
- 连接断开时保留本地工作能力并显示真实状态；
- 同步、发送和推送采用可对账状态，不做“必达”宣传；
- 插件或技能不可绕过数据隔离、确认规则和敏感字段策略；
- 新外部依赖必须有退出、替换和数据回收方案。

### 反例

- MCP、插件或 Copilot 拥有比用户界面更宽的写权限；
- 日历服务接受事件后显示“用户已收到”；
- 第三方技能默认读取全部案件；
- 服务失效时只显示空白页。

### 验收问题

> 断开这个外部能力会失去什么？系统是否准确告诉用户，并提供可用的本地替代？

# 第四篇：领域语言与信息模型

## 18. 认知模型与存储模型分离

用户不应理解数据库表，但产品必须使用稳定、诚实的领域语言。当前建议的认知原语如下；它们是产品语义，不是建表清单。

| 原语 | 回答的问题 | 核心特征 |
|---|---|---|
| 领域 Area | 我长期对什么负责？ | 无明确终点，持续维护 |
| 项目 Project | 我想在有限周期内达成什么结果？ | 有目标、有边界、可完成或终止 |
| 案件 Matter/Case | 哪个法律事项构成专业项目上下文？ | 项目的法律特化，包含程序、当事人、期限和材料 |
| 行动 Action | 下一次可以实际做什么？ | 可执行、可完成、可委派或转等待 |
| 事件 Event | 什么会在一个确定时间发生？ | 有开始/结束/时区，可独立于案件存在 |
| 期限 Deadline | 最迟何时必须完成，依据是什么？ | 有基准、规则、时区/工作日语义和可信状态 |
| 材料 Resource | 工作所依据或产生的外部对象是什么？ | 文件、邮件、链接、文书、证据、附件及其版本 |
| 知识 Knowledge | 什么内容值得跨情境复用？ | 有来源、适用范围、可修订 |
| 参与方 Party | 谁与工作有关？ | 人、组织、客户、法院、代理人等稳定身份 |
| 关系 Relation | 为什么两个对象相关？ | 有角色、方向、来源、范围和状态 |

### 18.1 收件箱不是第十一个永久实体

收件箱表达“尚未厘清”的处理状态。原始捕获项可以有自己的持久化记录，以保证不丢和保留来源，但一旦厘清，它应指向形成的行动、事件、材料、知识或项目，而不是复制一份孤立数据长期漂移。

### 18.2 视图不是实体

“今天、计划中、下一步、等待、回顾、某天、逾期、高风险”是对事实的查询与排序。只有在为了性能做缓存时才存派生状态，并保持可重建与一致性检查。

### 18.3 客户是参与方和聚合视角

客户需要稳定身份、别名、联系信息和历史关系，因此在数据层可以是独立主数据；但是否成为顶级导航由使用频率决定。客户不是强迫所有工作归属的容器，也不应与案件名称字符串等同。

## 19. 项目与案件

### 19.1 项目是通用工作骨架

项目至少包含：

- 可理解的目标或完成条件；
- 当前状态；
- 下一步行动、明确等待或暂停理由；
- 关键事件与期限；
- 相关材料与知识；
- 责任和回顾节奏；
- 完成、取消、暂停和归档的区别。

项目可以是法律案件、客户汇报、研究课题、团队事项或个人计划。纯个人项目不应因为没有法律字段而显得残缺。

### 19.2 案件是项目的法律特化

案件增加法律语义，而不是复制一套项目系统：

- 当事人与代理关系；
- 管辖机关、案号、程序类型和审级；
- 法律程序轨与节点；
- 送达、期限及计算依据；
- 证据、文书和卷宗结构；
- 关键法律决定及其依据；
- 保密、外发和模型使用策略。

### 19.3 程序轨是模板，不是上限

民事诉讼、无效、行政诉讼可以是专利业务中的预设程序轨，但底层语义应允许：

- 一个案件同时存在多条程序轨；
- 程序轨之间建立前置、证据引用和结果影响关系；
- 根据业务领域添加仲裁、刑事、海关、许可谈判等新模板；
- 用户在保留审计的前提下偏离模板；
- 模板升级不擅自改写已进行案件。

### 19.4 “案件即流程”的升级解释

案件不是严格线性的流水线。法律工作常有并行、回退、等待、条件分支和外部突发。正确原则是：

> **案件必须始终可被推进；系统应帮助识别当前可执行行动、阻塞关系和关键路径，但不能假设永远只有一条线或一个可见行动。**

因此：

- 顺序行动适用于明确的前置关系；
- 多个独立行动可以同时可用；
- “下一步”是最小可执行集合，不必永远唯一；
- 完成节点可提出解锁候选，但状态变化必须由确定性规则或用户确认；
- 进度不应仅用“完成任务数/总任务数”表达，关键里程碑和风险更重要。

## 20. 行动、等待与回顾

### 20.1 可执行行动

一条行动应尽量满足：

- 以动词描述；
- 完成结果可以判断；
- 所需上下文或材料可找到；
- 责任主体明确；
- 若有前置条件，系统知道其是否满足；
- 预计工作量可以选填和校准，不作为完成前置。

“推进案件”“处理材料”“研究一下”通常不是合格的下一步，需要进一步厘清。

### 20.2 等待不是被动任务

等待至少包含：

- 在等谁或什么事件；
- 从何时开始等待；
- 期望结果；
- 何时检查或跟进；
- 收到结果后会解锁什么。

等待应从可执行清单中退出，但不能从系统视野中消失。

### 20.3 委派与等待的区别

委派表达责任转移，等待表达当前不可推进。二者常同时发生但并不相同：用户可以委派后仍承担跟进责任，也可能等待法院事件而无人被委派。

### 20.4 回顾是承诺维护机制

回顾日期不是所有任务的默认截止。它表示某项内容需要重新判断是否仍有效、是否应推进或是否需要补充信息。系统应允许项目级、领域级和自定义回顾节奏。

### 20.5 默认透视语义

| 透视 | 稳定语义 | 不应混入 |
|---|---|---|
| 收件箱 | 未完成厘清的捕获项 | 已正式安排但尚未开始的任务 |
| 今天 | 用户今天承诺关注的行动 + 今天必须处理的硬边界 | 所有 start_date 早于今天的历史噪音 |
| 下一步 | 当前条件满足、可以实际执行的行动 | 被阻塞、等待、纯信息项 |
| 等待 | 当前依赖外部结果，并有跟进语义 | 只是“以后再做”的任务 |
| 回顾 | 到了重新判断时点的项目、行动或记忆 | 所有未完成事项 |
| 某天 | 不承诺近期执行但不愿丢弃的可能性 | 已有硬期限的任务 |
| 计划中 | 有未来开始、排程或期限的内容的综合视图 | 用一个含糊状态覆盖不同时间语义 |

这些是默认视图，不是数据库状态枚举，也不是永远不能调整的顶栏数量。

## 21. 时间模型

### 21.1 五种时间必须区分

| 时间 | 含义 | 示例 | 是否可随意拖动 |
|---|---|---|---|
| 发生时间 | 外部或约定事件何时发生 | 开庭、会议、口审 | 改动通常需要确认并可能通知他人 |
| 可开始时间 | 行动何时进入可执行视野 | 收到判决后开始起草上诉状 | 随前置事实变化 |
| 计划时间 | 用户打算何时投入时间 | 周二 14:00 起草两小时 | 可以重新安排，不改变期限 |
| 截止期限 | 最迟何时必须完成 | 上诉期届满日 | 只能基于事实/规则变更 |
| 提醒时间 | 系统何时通过某通道提示 | 截止前三天上午 9 点 | 可按策略调整 |

### 21.2 期限是一条可解释的推导链

关键期限至少需要记录或可恢复：

- 期限类型；
- 基准事件及其来源；
- 适用规则与版本；
- 计算时区、自然日/工作日和节假日规则；
- 计算结果；
- 人工确认、修订或例外；
- 后续提醒和行动。

规则更新后，系统应识别可能受影响的未结事项，提出复核，而不是静默重写历史。

### 21.3 日历是时间承诺界面，不是所有数据的第二份副本

- 独立事件在日历中拥有自己的权威记录；
- 案件期限作为只读或受控图层出现；
- 任务时间块是排程投影；
- 拖拽动作根据对象类型使用不同语义；
- 日历与任务互通，不等于把任务和事件合并成同一种对象。

### 21.4 时区与全天事件

- 存储使用明确的时间点或本地日期语义，不能依赖隐含系统时区；
- 涉及跨时区参与者时显示原时区与本地换算；
- 全天期限与定时事件分开处理；
- 夏令时变化使用 IANA 时区规则，不使用固定 UTC 偏移替代。

## 22. 材料、知识与沟通

### 22.1 材料是来源，知识是提炼

- 邮件、法院文书、证据、附件、网页和录音属于材料；
- 摘要、方法、观点、复盘和模板属于知识；
- 从材料提炼知识时保留引用、版本和适用范围；
- 材料更新或失效时，相关知识应可被标记复核。

### 22.2 文件不是路径字符串

文件至少需要考虑：身份、版本、来源、原始名称、受控副本、哈希、关联对象、权限、是否缺失和导出方式。移动或重命名后关系不应轻易断裂。

### 22.3 知识分类服务于使用

“灵感、方法、参考、问题、经验、日志”可作为默认职能，但不应被误解为互斥文件夹。知识可以具有多个角色，并通过案件、项目、领域、法条和材料来源被找到。

### 22.4 编辑器不是哲学

Markdown、所见即所得、块编辑或外部知识库挂载都是实现策略。长期要求是：

- 内容可携带、可导出、可全文检索；
- 引用和链接稳定；
- 结构不因编辑器更换而丢失；
- 法律写作所需的脚注、表格、引用和版本能够可靠表达；
- 编辑体验不迫使用户理解底层标记语法。

### 22.5 沟通记录与正式决定分离

邮件、会议纪要和聊天说明“发生过什么”；正式决定说明“决定了什么、依据什么、谁确认”。系统可以从沟通中提出决定候选，但不能自动等同。

# 第五篇：核心体验蓝图

## 23. 信息架构：围绕用户任务，不围绕数据表

### 23.1 三个稳定层次

Casy 的导航应长期保持三类可达性，但不冻结具体菜单数量：

1. **全局焦点层**：现在、今天、即将发生和需要复核的内容；
2. **工作上下文层**：项目/案件、行动、日历、收件箱、材料/知识等高频工作表面；
3. **工具与管理层**：搜索、文档能力、同步、审计、设置、连接和低频维护。

这三层描述信息优先级，不规定必须使用顶栏、侧栏或固定六个按钮。桌面尺寸、键盘使用和未来设备形态可以采用不同布局。

### 23.2 顶级入口的裁决标准

一个功能成为顶级入口，应同时满足大部分条件：

- 用户会独立进入它完成一项高频任务；
- 它不是另一上下文中的资源列表；
- 它有独立的浏览、创建或处理循环；
- 隐藏到搜索或二级入口会显著增加日常成本；
- 名称对应用户语言，而不是内部架构名；
- 与相邻入口的职责边界能用一句话说明。

因此，“文书”是否独立、“客户”是否顶级、“项目”和“案件”是否并列，都应由真实使用路径决定，而不是由数据库是否有独立实体决定。

### 23.3 多条到达路径

高频对象应允许通过以下路径到达：

- 导航浏览；
- 全局搜索；
- 命令面板；
- 关联对象跳转；
- 最近使用与固定；
- 系统建议或通知的深链接；
- 键盘快捷操作。

但多条到达路径不能产生多套编辑逻辑。无论从哪里修改，都应作用于同一权威对象。

### 23.4 返回上下文

从今日进入任务、从任务进入案件、从案件打开材料后，用户应能自然返回原工作位置。系统要保留筛选、滚动、选中项和临时展开状态，减少“我刚才在哪里”的认知损失。

## 24. 焦点台：现在需要注意什么

### 24.1 职责

焦点台不是传统 Dashboard。它的工作是把全局事实压缩为可行动的短列表，并帮助用户开始或重新安排一天。

### 24.2 默认组成

焦点台可以包含：

- 当前或今天的硬性事件；
- 今天届满或风险升级的期限；
- 用户明确承诺今天关注的行动；
- 已达到跟进时点的等待；
- 因外部变化需要复核的项目；
- 新突发事项与原计划的冲突；
- 少量有明确依据的建议。

### 24.3 不应包含

- 与当天决策无关的全量统计；
- 为了显得智能而生成的泛泛鼓励；
- 所有逾期历史的无差别堆积；
- 未解释来源和挤占影响的自动排程；
- 多个模块对同一风险的重复卡片。

### 24.4 日计划契约

当用户把行动加入“今天”，系统应把它理解为注意力承诺，而不是悄悄改动开始日期或法律期限。若今天容量明显不足，系统应展示冲突并允许：

- 重新排序；
- 移出今天；
- 调整计划时间；
- 拆分行动；
- 接受风险并记录原因；
- 把低优先事项转为等待、委派或某天。

### 24.5 验收

- 用户可以在一分钟内理解今天的硬边界和可调空间；
- 今日清单不会因旧 start date 自动无限膨胀；
- 没有 AI 时使用规则排序仍然完整；
- 每条建议可解释“为什么现在出现”。

## 25. 大口袋与收件箱

### 25.1 职责

大口袋负责“任何东西先安全进来”，收件箱负责“尚未完成解释和安置的东西集中处理”。它们共同构成输入边界，但不是把所有外部信息自动灌入正式系统。

### 25.2 捕获入口

可逐步支持：

- 快速文本；
- 明确意图的任务、日程或笔记入口；
- 文件拖入；
- 链接和剪贴板；
- 邮件或日历转入；
- 扫描、截图和语音转写；
- 文件夹监听和外部集成。

快捷键是入口优化。默认键位可以稳定提供，但必须允许冲突检测和用户重映射，不能把某个快捷键本身写成领域原则。

### 25.3 原始层与解释层

每个捕获项至少有两个层次：

1. **原始层**：用户实际输入或收到的内容，不因解析结果变化；
2. **解释层**：系统或 AI 对类型、日期、关联、行动和风险的候选理解。

解释可以重跑、比较和撤销，原始层保持来源锚点。

### 25.4 厘清界面

厘清时，用户应同时看到：

- 原始内容与附件；
- 来源和接收时间；
- 解析候选及其依据；
- 可能关联的项目/案件；
- 将创建或修改的对象预览；
- 冲突、重复和缺失信息；
- 接受、修改、拆分、合并、延后、归档和丢弃操作。

### 25.5 自动处理边界

- 高精度、低风险、本地可逆的规则可以自动加标签或预填；
- 形成期限、外部发送、状态变化和跨案件关系时默认需要复核；
- 批量自动化必须先在样本上预演；
- 自动下载外部材料要经过域名、文件类型、大小、恶意内容和凭据边界检查；
- 解析失败时保留原件并进入可重试状态，不能静默丢弃。

### 25.6 处理完成的含义

收件箱项只有在以下之一成立时才算完成处理：

- 已形成正式对象并建立来源关系；
- 已并入重复项；
- 已作为无需行动的材料归档；
- 已明确删除或忽略，并有必要的撤销窗口；
- 已延后到一个明确复核时间。

“AI 已分析”不等于“已厘清”。

## 26. 行动工作台

### 26.1 职责

行动工作台回答“在全部承诺中，哪些此刻可做、必须做、正在等待或需要重新判断”。它是个人工作流的中心，而不是案件模块的附属列表。

### 26.2 默认透视

默认可提供收件箱、今天、下一步、计划中、等待、回顾、某天，并允许经过约束的自定义视图。数量可以随验证调整，但每个透视必须有清晰、互不欺骗的语义。

### 26.3 下一步行动

“下一步”至少满足：

- 未完成、未取消；
- 当前可执行；
- 不处于等待；
- 所有强前置条件已满足；
- 若属顺序项目，是当前解锁集合的一员；
- 没有被明确安排到未来且设置为暂不显示。

独立行动无需强制归属案件或项目。否则通用工作基础会被法律层绑架。

### 26.4 任务完成

- 默认一次主要操作即可完成；
- 记录耗时、写总结和评价 AI 可以在完成后轻量补充，不能默认阻断；
- 完成后即时反馈，并提供撤销；
- 若完成会解锁后续、生成重复实例或影响期限，应明确展示结果；
- 外部同步异步完成，不阻塞本地完成反馈；同步失败进入可见重试状态。

### 26.5 重新安排

推迟动作必须说明改变的是：今日承诺、计划时间、可开始时间、回顾时间还是截止期限。常用动作可一键执行，但语义不能含糊。

### 26.6 自定义透视

自定义透视基于稳定字段和关系组合筛选、排序和分组。系统应：

- 防止规则互相矛盾；
- 展示自然语言解释；
- 允许保存、重命名、复制和恢复默认；
- 在字段或语义变化时提示受影响视图；
- 不因创建视图而复制数据。

## 27. 日历与排程

### 27.1 职责

日历回答“什么时间已经被占用、哪些硬边界即将到来、可执行行动可以放在哪里”。它必须同时尊重时间事实和计划弹性。

### 27.2 图层

建议至少区分：

- 外部或独立事件；
- 案件程序事件；
- 法定或约定期限；
- 用户计划的任务时间块；
- 仅供参考的可开始日期或跟进日期。

每个图层有一致的视觉和编辑权限。用户可以隐藏图层，但不能把隐藏误认为删除。

### 27.3 拖拽语义

| 被拖对象 | 默认动作 | 需要额外确认的情况 |
|---|---|---|
| 任务进入时间网格 | 创建或调整计划时间块 | 与硬事件冲突、跨工作时段 |
| 计划时间块移动 | 只调整计划 | 若关联外部邀请则升级为事件变更 |
| 独立事件移动 | 修改事件开始/结束 | 有参与人、外部日历或提醒 |
| 案件程序事件移动 | 提出变更 | 正式事实不能仅凭拖拽改写 |
| 期限标记移动 | 默认禁止直接改写 | 必须进入期限依据复核流程 |

### 27.4 外部日历

- 同步前明确主从关系和可写方向；
- 使用稳定 UID、版本/ETag 和幂等更新；
- 外部修改进入观察与复核，不盲目覆盖本地；
- 删除、取消、改期和重复事件均需可对账；
- 案件敏感内容支持完整、脱敏摘要或不出端策略。

### 27.5 Forecast 只是候选布局

月历 + 未来列表、周时间轴、日排程、年负载都是不同问题的视图。是否使用双栏 Forecast 应由屏幕空间和任务验证，不是哲学要求。稳定要求是用户能同时理解宏观负载和近期细节。

## 28. 项目书与案件工作台

### 28.1 职责

项目书不是“把所有字段铺在一页”，而是帮助用户在中断后恢复上下文并继续推进。

### 28.2 打开项目时首先应知道

- 目标和当前状态；
- 最近发生的重要变化；
- 当前可执行行动与阻塞；
- 下一个硬性事件或期限；
- 未解决问题和待确认建议；
- 关键材料在哪里；
- 重要决定及其依据。

### 28.3 完整上下文结构

案件工作台可以组织为：

1. 身份与概要；
2. 程序轨与里程碑；
3. 行动、等待和责任；
4. 事件、期限和准备窗口；
5. 当事人、客户和相关事项；
6. 材料、证据、文书和知识；
7. 沟通、时间线和状态变化；
8. 决定、风险、建议和复核；
9. 结案条件、归档和经验沉淀。

页面可以采用纵向流、分栏、局部 Tab 或渐进展开。验收重点是全景、定位和推进感，而不是某张卡必须处于某个坐标。

### 28.4 多轨展示

- 同时显示彼此影响的程序轨，不强迫逐个 Tab 查看；
- 能区分轨道自身状态和跨轨依赖；
- 关键节点可回到材料、期限、行动和决定；
- 对尚未开始的轨道保持低噪音；
- 允许用户在模板之外添加真实发生的节点。

### 28.5 进度表达

进度优先用里程碑、关键路径、等待和风险表达。任务完成比例只能作为辅助，因为一个关键答辩和十个整理任务的权重不同。

## 29. 知识与专业记忆

### 29.1 职责

知识系统回答“过去形成的哪些判断、材料和方法可以安全地支持当前工作”。它不是资料坟场，也不是把所有内容向量化后等待搜索。

### 29.2 知识进入长期层的条件

至少满足一项：

- 可在多个项目复用；
- 对某类风险或程序有持续解释价值；
- 是被确认的专业经验或决策模板；
- 是稳定引用材料、法条、判例或检查清单；
- 对未来回顾具有明确价值。

### 29.3 来源与时效

每条重要知识应尽量具备：

- 来源材料或形成事件；
- 作者/确认者；
- 适用司法辖区、业务类型或案件范围；
- 形成和最近复核时间；
- 有效、待复核、已取代或已归档状态；
- 与新材料冲突时的提示。

### 29.4 双向链接

双向链接服务于找回上下文，不应形成无法维护的“图谱表演”。系统优先展示与当前任务最相关的少量关系，完整关系网络在需要分析时再展开。

### 29.5 从复盘到知识

案件结案或里程碑回顾可以生成候选：

- 哪些做法有效；
- 哪些估时和准备窗口偏差明显；
- 哪些材料可沉淀为模板；
- 哪些决定只适用于本案；
- 哪些规则需要修订。

候选经人确认后进入长期知识。案件事实本身不因结案自动变成通用经验。

## 30. 通知中心与复核队列

### 30.1 两类内容分开

- **通知**：告诉用户发生了变化或风险升级；
- **复核项**：等待用户做决定、确认或纠正。

通知可以读后消失，复核项必须有明确处理结果。不能用“已读”代替“已处理”。

### 30.2 统一去重

同一事实可以通过多个通道送达，但共享一个事件身份和处理状态。用户在一个位置处理后，其他位置应同步收敛，避免重复追赶。

### 30.3 打断等级

打断强度综合考虑：

- 法律或业务后果；
- 距离硬边界的时间；
- 用户是否已知晓；
- 是否存在可行动的下一步；
- 当前是否处于专注、会议或休息；
- 之前提醒是否被延后或忽略；
- 通道可靠性和敏感内容策略。

等级名称和具体提前天数属于策略配置，不应在哲学中冻结。稳定要求是强度有依据、可解释、可调整。

### 30.4 反馈

提醒至少允许：完成、知道了、稍后、转等待、调整时间、错误提醒、不要再提醒。反馈既改变当前作业，也作为后续策略候选，不直接训练不可见的黑盒偏好。

## 31. 搜索、命令与跨模块操作

### 31.1 搜索是恢复上下文，不只是匹配字符串

搜索结果应区分对象类型，展示关键上下文，并支持直接行动。对敏感内容，预览和全文索引遵循本地与权限策略。

### 31.2 命令面板是高频捷径，不是功能藏匿处

命令面板适合创建、跳转、批量处理和调用技能，但核心新手路径仍应可发现。命令执行前显示目标范围，危险操作进入确认。

### 31.3 批量操作

批量修改必须：

- 说明选中范围；
- 预览规则与影响；
- 对异常项单独列出；
- 支持部分成功与重试；
- 可撤销的本地变更形成同一撤销批次；
- 外部副作用逐项可对账。

## 32. 文档与技能工作区

### 32.1 Casy 的职责

Casy 为文档工作提供：

- 已选择的案件上下文；
- 经授权的材料和知识；
- 文档目标、受众和完成标准；
- 版本、来源和决策链；
- 调用合适编辑器、模板、检索或生成技能的入口；
- 草稿、复核、定稿和归档状态。

### 32.2 不把生成器等同于文档系统

AI 生成一段文字只是草稿步骤。完整文档工作还包括证据引用、格式、版本、批注、人工修订、导出、签署和归档。

### 32.3 技能按需加载

每个技能声明：用途、需要的数据、可用工具、可能的外部传输、输出类型和风险等级。只有用户启动相关工作时才加载，默认不获得全部案件上下文。

# 第六篇：AI 与自动化哲学

## 33. AI 的角色

AI 在 Casy 中有四种正当角色：

1. **解释者**：把复杂材料转换为可读摘要、结构候选或差异说明；
2. **准备者**：在用户工作前整理上下文、检查清单、草稿和待决问题；
3. **建议者**：根据明确事实提出优先级、排程、关联和跟进候选；
4. **执行助手**：在获得具体授权后，通过统一命令完成受控动作。

AI 不是事实数据库、法律责任主体、权限管理员或不可见的系统管理员。

## 34. 规则、模型与人工的分工

| 工作 | 规则/确定性系统 | AI | 人 |
|---|---|---|---|
| 法定期限计算 | 主责 | 可解释规则，不负责结果 | 核对基准事实和例外 |
| 状态合法性 | 主责 | 可提示异常 | 决定特殊处理 |
| 文本结构化提取 | 校验格式和范围 | 产生候选 | 确认关键字段 |
| 关联发现 | 检查显式关系 | 提出隐性关系 | 接受、修正或拒绝 |
| 今日排序 | 提供硬规则基线 | 给出个性化建议 | 承诺最终计划 |
| 文档草稿 | 提供模板和引用约束 | 生成叙事 | 专业审阅与定稿 |
| 外部发送 | 幂等、权限、审计 | 准备内容和动作提案 | 授权发送 |
| 经验沉淀 | 管理版本和生命周期 | 提出候选总结 | 判断能否泛化 |

## 35. 本地规则引擎

### 35.1 适用范围

本地规则适合：

- 日期、案号、已知域名和文件模式识别；
- 法律期限和节假日计算；
- 状态、权限、去重和完整性校验；
- 已经由用户明确建立的分类或自动化；
- AI 不可用时的基础排序和建议。

### 35.2 规则不能无限膨胀

“超大规则库”不是目标。规则越多，冲突、误判和维护成本越高。每条规则需要：

- 明确用途和适用范围；
- 版本、来源和负责人；
- 正例、反例和边界样本；
- 优先级与冲突策略；
- 命中解释；
- 停用和回滚方式；
- 误判反馈和定期复核。

### 35.3 AI 发现的新模式如何成为规则

必须经过以下生命周期：

> **观察 → 候选规则 → 离线样本测试 → 冲突检查 → 人工批准 → 小范围启用 → 监测误判 → 正式启用或回滚**

AI 不能把一次成功解析自动写成全局正则，更不能自行扩大到所有案件。

## 36. Proposal 标准

任何可能改变正式数据或用户计划的 AI 结果，应尽量使用统一提案结构：

| 项 | 内容 |
|---|---|
| 目标 | 提案试图解决什么问题 |
| 建议 | 建议创建、修改、关联、安排或发送什么 |
| 事实依据 | 来自哪些对象、材料、字段和版本 |
| 推断与假设 | 哪些不是已确认事实 |
| 缺失信息 | 哪些关键内容尚不可得 |
| 置信说明 | 为什么较可信或不可信，不只给数字 |
| 风险等级 | 本地/外部、可逆/不可逆、是否法律关键 |
| 预期影响 | 将改变哪些正式对象和下游视图 |
| 可逆性 | 如何撤销，哪些外部副作用无法撤回 |
| 有效期 | 来源变化后是否需要失效或重算 |

界面可以按风险简化展示，但系统语义应完整保留。

## 37. 权限与确认梯度

为避免与提醒等级混淆，AI/自动化权限使用 A0-A3：

| 等级 | 影响 | 默认策略 | 示例 |
|---|---|---|---|
| A0 观察 | 不改变正式数据 | 可自动运行，结果可忽略 | 搜索、摘要、解释 |
| A1 本地可逆 | 改变本地低风险数据，可完整撤销 | 可逐项确认；用户可为明确规则授权自动化 | 加标签、建立草稿、调整显示顺序 |
| A2 结构/敏感 | 影响项目状态、期限候选、跨案件关系或敏感内容 | 明确预览与人工确认，执行前重验 | 修改关键日期、确认关系、接受提取字段 |
| A3 外部/不可逆 | 发送、覆盖、删除、对外发布或法律关键决定 | 具体动作即时授权；必要时真正的第二人复核 | 发邮件、提交文书、删除原件、放弃上诉 |

### 37.1 有效权限取最高风险

有效确认要求由以下因素中最严格者决定：

- 动作本身的系统安全下限；
- 场景和数据敏感性；
- 外部通道与可逆性；
- 组织或案件策略；
- 用户选择的更严格偏好。

用户可以提高确认强度，不能关闭系统安全下限。模型品牌、大小或自报置信度不能自动降低动作等级。

### 37.2 真正的“双人复核”

“双人复核”只用于确有第二位有权限的人类参与的流程。以下都不能称为双人复核：

- 同一用户点击两次确认；
- 同一模型重新检查自己的输出；
- 另一个模型给出一致答案；
- 系统通过格式校验。

这些可以提高发现错误的机会，但不能替代第二位专业人员的独立判断。

## 38. 上下文策略

### 38.1 最小必要上下文

每类 AI 任务必须声明 Context Policy：

- 需要哪些来源；
- 最大关系深度和项目范围；
- 最大条目、字符或 token 预算；
- 可见的敏感等级；
- 数据快照版本；
- 缺少哪些来源时必须拒绝或降级；
- 任务完成后上下文如何保留或清理。

### 38.2 不做无界“全局喂数”

跨案件模式分析可以在用户明确启动、经过脱敏和范围选择后运行。日常任务推荐不应默认读取客户所有案件、全部文书和历史对话。

### 38.3 来源快照

AI 建议应关联输入来源的版本。执行前若关键来源已变化，提案进入过期状态，要求重新生成或人工确认差异。

### 38.4 精确审计与隐私的平衡

- 每次模型调用至少记录用途、模型、时间、状态、来源引用和内容摘要/哈希；
- 若需要精确复现，必须保存受保护的输入输出快照；仅保存哈希不能重建原文；
- 精确快照可能包含敏感信息，应本地加密、限制访问并配置保留期；
- 用户可以选择更严格的“不保留正文”模式，此时系统诚实说明只能验证完整性，不能精确重放。

## 39. AI 输出验证

### 39.1 四种验证不能混称

| 验证 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 结构校验 | 格式、类型、必填、枚举合法 | 内容事实正确 |
| 确定性规则校验 | 日期、权限、引用存在、状态迁移合法 | 开放语义结论正确 |
| 来源覆盖检查 | 建议引用能回到给定来源，关键来源未明显遗漏 | 来源本身真实完整、结论必然正确 |
| 模型/人工复核 | 发现潜在矛盾、遗漏或表达问题 | 自动获得绝对正确性 |

### 39.2 验证顺序

1. 先做便宜且确定的结构、权限和规则校验；
2. 再检查来源版本、引用和覆盖；
3. 对高风险开放判断，使用独立提示、可选不同模型或人工复核；
4. 任何校验失败都不自动“修到通过”，而是保留失败原因和改动差异；
5. 最终界面说明“已通过哪些检查”，不笼统显示“已验证”。

### 39.3 置信度

数字置信度只有在经过任务级校准时才有意义。否则应优先展示：

- 来源数量和质量；
- 明确支持与冲突证据；
- 缺失信息；
- 规则是否可确定；
- 模型是否超出其能力边界。

## 40. 行动执行网关

无论动作来自界面、AI、MCP、技能还是自动化，都应进入统一执行网关。网关负责：

- 鉴别调用者；
- 计算权限等级；
- 重新读取目标和关键来源版本；
- 展示或验证确认凭据；
- 在事务中执行本地变化；
- 创建外部副作用作业；
- 写入领域审计；
- 发出可供界面和同步消费的事件；
- 失败时回滚本地事务或进入明确补偿状态。

任何集成不能拥有绕过网关的“特殊写入口”。

## 41. 推荐系统

### 41.1 推荐的目标

推荐不是替用户做决定，而是减少准备决策所需的搜索、比较和记忆负担。

### 41.2 可以推荐什么

- 今天值得关注的少量行动；
- 硬日程前需要预留的准备工作；
- 等待是否到跟进时点；
- 任务拆分、估时和可用时间块；
- 可能关联的案件、材料和知识；
- 项目缺失的下一步或复核；
- 重复模式和候选经验。

### 41.3 推荐排序的最低基线

没有 AI 时，系统仍可依据：

- 硬期限和事件；
- 是否已承诺今天；
- 当前是否可执行；
- 阻塞和等待；
- 用户明确旗标；
- 准备窗口；
- 预计耗时与可用时间；
- 最近忽略或连续推迟情况。

AI 在此基础上解释权衡和个性化，不取代硬规则。

### 41.4 推荐反馈

接受、调整、拒绝、忽略和最终执行结果分别记录。系统不应只学习“点击接受”，还要比较：

- 推荐时间与实际开始/完成；
- 推荐估时与实际耗时；
- 推荐关联与用户修正；
- 拒绝原因是否重复；
- 上下文变化是否使建议自然失效。

## 42. 记忆与蒸馏

### 42.1 四层而非简单三层

| 层 | 内容 | 默认用途 | 保留原则 |
|---|---|---|---|
| 活动层 | 操作、完成、推迟、提醒反馈等原始事件 | 统计、恢复、短期学习 | 按必要性和配置保留 |
| 偏好层 | 工作时段、估时校准、通知偏好等派生模式 | 个性化建议 | 可查看、可重置、有新鲜度 |
| 决定层 | 被确认的选择、依据、适用范围和后续复核 | 解释项目走向 | 版本化长期保留 |
| 知识层 | 经确认可复用的方法、经验、模板和引用 | 跨项目复用 | 有来源、状态和复核周期 |

活动不自动升级为偏好，偏好不自动升级为决定，决定也不自动成为通用知识。

### 42.2 蒸馏流程

> **选择范围 → 生成候选 → 对照来源 → 去重/冲突检查 → 人工确认 → 写入适用层 → 定期复核或归档**

### 42.3 删除垃圾的正确理解

删除的目标是减少无价值、过期或重复的数据，不是机械按固定天数清除所有行为。保留策略应考虑：

- 法律审计需要；
- 用户恢复和争议核对需要；
- 是否已经提炼出足够摘要；
- 数据敏感性；
- 本地容量；
- 用户设置和监管要求。

### 42.4 模型无关

偏好、决定和知识存储在 Casy 可读结构中，带来源与版本。模型只消费这些内容，不能成为唯一记忆载体。

## 43. AI 降级

每个 AI 能力至少定义四态：

| 状态 | 用户看到 | 系统行为 |
|---|---|---|
| 未启用 | 明确说明并提供手动/规则路径 | 不发起模型调用 |
| 处理中 | 可离开、可取消、显示范围和进度 | 使用持久作业，避免界面关闭即丢失 |
| 成功 | 结果、来源、影响和下一步 | 仍按权限决定是否落地 |
| 失败/降级 | 原因、可重试项和可用替代 | 保留原始输入，不生成伪结果 |

高风险确认工具不可用时，不应悄悄降低安全等级。如果某动作要求 A3 复核而条件不满足，正确行为是暂停该动作，而不是仅做格式校验后继续。

# 第七篇：本地优先、同步与开放生态

## 44. 本地优先的完整定义

一个功能只有同时满足以下大部分条件，才可以称为本地优先：

- 用户数据的权威副本默认在本机；
- 断网时可以读取和修改核心数据；
- 本地修改先完成，再异步同步；
- 外部服务不可用不会破坏本地一致性；
- 用户知道哪些数据离开设备；
- 凭据由用户控制并可撤销；
- 数据有开放导出和经过验证的恢复路径；
- 云端供应商、AI 模型和同步目标可替换；
- 系统不依赖隐藏账户才能访问自己的数据。

### 44.1 本地不等于单机孤岛

本地优先允许同步、备份、远程模型和跨设备访问。关键是：外部能力不能成为用户访问自己数据的唯一通道，且连接的状态与影响可见。

### 44.2 本地不等于默认不加密

法律工作数据应默认采用适合平台的静态保护，敏感凭据进入系统密钥存储。备份、导出、日志、索引和缓存分别评估泄露风险，不能只加密主数据库就宣称安全。

## 45. 同步哲学

### 45.1 同步是复制，不是事实创造

同步负责在多个副本之间传播变化。期限计算、项目状态、AI 建议和用户决定应先在领域层形成，再由同步传输，不能由某个远端字段偶然成为业务逻辑。

### 45.2 每个同步对象需要的语义

- 稳定身份；
- 本地与远端版本；
- 创建、更新、删除/墓碑状态；
- 最后成功同步时间；
- 待上传、待下载、冲突、失败和结果未知；
- 冲突比较与解决方式；
- 可重试与退避策略；
- 解除连接后的数据处理。

### 45.3 冲突不能静默覆盖

可以自动合并的变化必须有可证明的规则，例如不同字段的独立修改。涉及同一关键字段、删除与修改、版本历史或法律期限时，默认进入冲突复核。

### 45.4 同步健康状态

用户看到的不应只有“已连接/未连接”。至少应区分：

- 未配置；
- 正常且无待处理；
- 正在同步；
- 有待同步本地变化；
- 有可重试失败；
- 有冲突需要处理；
- 远端结果未知，正在对账；
- 凭据失效或权限不足；
- 已暂停。

## 46. 备份、恢复与迁移

### 46.1 备份不是复制文件按钮

可靠备份需要：

- 一致性快照；
- 版本和校验信息；
- 加密及恢复密钥策略；
- 附件、索引和配置的范围说明；
- 自动轮换与容量策略；
- 恢复前预检；
- 恢复后的完整性验证；
- 定期实际演练。

### 46.2 数据迁移

- 每次格式或 schema 变化有前置备份和幂等迁移；
- 迁移失败不留下半升级状态；
- 大版本升级前说明不可逆变化；
- 旧数据保留来源和历史语义；
- 降级无法支持时明确阻止，而不是让旧版本破坏新数据。

### 46.3 可携带导出

用户应能导出：

- 结构化对象与关系；
- 可读文档；
- 原始材料和附件；
- 时间、决定与来源历史；
- 必要配置说明。

专有格式可以用于完整备份，但不能成为唯一出口。

## 47. 提醒与送达语义

### 47.1 提醒链的六个状态

| 层 | 含义 | 可由谁证明 |
|---|---|---|
| 已计算 | 触发时间和内容已由规则产生 | Casy 本地规则 |
| 已排队 | 持久作业已创建，等待执行 | Casy 作业系统 |
| 已尝试 | 已调用本地或外部通道 | Casy 执行记录 |
| 通道已接受 | 日历/邮件/推送服务确认接收 | 外部通道回执 |
| 终端已送达 | 目标设备收到 | 仅有送达回执时可知 |
| 用户已确认 | 用户明确处理、阅读或反馈 | 用户或可信回执 |

任何一层不能推断下一层。没有回执时，显示“未知”比显示“成功”更可靠。

### 47.2 本地提醒

本地进程运行时可以准时触发系统通知。休眠、关机、应用退出或操作系统限制会影响执行，因此需要：

- 持久作业；
- 启动补偿扫描；
- 去重；
- 过期策略；
- 用户可见的错过清单；
- 不夸大“必达”。

### 47.3 外部日历交接

把提醒固化为日历事件可以利用既有日历生态在 Casy 离线时继续触发，但只有获得远端事件确认后才能认为交接完成。仍需处理：

- 稳定 UID 与幂等更新；
- 改期和撤销；
- 时区和 alarm；
- 远端删除；
- 网络超时后的对账；
- 敏感摘要策略；
- 用户关闭日历通知的不可见风险。

因此，“日历已接受”仍不等于用户一定看到。

### 47.4 自建云与移动端

不应仅为了“离线推送”立即建设自有云中继或完整移动端。只有在独立移动工作、实时跨设备协作、特定通道或可靠性要求无法由现有生态满足时，才重新评估，并把基础设施、凭据托管、SLO、合规和持续成本纳入决策。

## 48. 外部访问内部

### 48.1 查询接口

外部工具可以在用户授权范围内查询项目、行动、日程、期限、材料和知识。查询应支持：

- 明确范围和字段；
- 最小披露；
- 敏感内容脱敏；
- 来源和版本；
- 速率与资源限制；
- 可撤销授权。

“只读”仍可能泄露敏感信息，因此不是无风险等级。

### 48.2 写入接口

外部工具只产生提案或调用统一执行网关。它不能直接写数据库、跳过权限，也不能把自己的调用者身份伪装成用户。

### 48.3 授权范围

授权应尽量支持：

- 一次性、会话级、项目级和长期授权；
- 只读、提案、本地可逆写和外部动作分级；
- 按对象、字段和敏感等级限制；
- 到期、暂停和撤销；
- 最近访问和操作记录。

## 49. 内部访问外部

### 49.1 连接器与技能的区别

- **连接器**负责稳定访问一个外部系统的数据或动作，如日历、邮件、云盘；
- **技能**负责完成一类工作，如生成答辩提纲、翻译、格式检查、法律检索。

技能可以使用连接器，但二者权限、失败和生命周期不同。

### 49.2 能力声明

每个连接器或技能必须声明：

- 读取什么；
- 写入或发送什么；
- 凭据在哪里保存；
- 数据是否离开设备；
- 依赖哪些服务；
- 失败和限额；
- 产生哪些本地记录；
- 如何停用、卸载和清理。

### 49.3 沙箱与最小权限

文档生成或代码型技能默认在受限工作区运行，不直接访问全部主数据。需要新增权限时即时请求，并展示用途。

# 第八篇：视觉、交互与可用性

## 50. 视觉北极星：信息清晰，表面安静，操作有生命

“克制”不等于灰暗、僵硬或千篇一律。Casy 的视觉应让复杂信息更易理解，同时在完成、拖拽、展开、同步和撤销时提供恰当的因果反馈。

### 50.1 信息层级

每个表面优先建立：

1. 当前对象或任务；
2. 关键状态与硬边界；
3. 主要动作；
4. 支持判断的上下文；
5. 低频设置与完整历史。

层级通过排版、间距、对齐、分组和内容顺序建立，不能主要依赖颜色和卡片边框。

### 50.2 密度

- 列表和表格支持专业用户的高信息密度；
- 复杂项目页通过分段和渐进披露避免“一屏只见卡片”；
- 密度设置可以因用户和屏幕变化，但语义层级不变；
- 触控热区与视觉密度分别处理，不能为追求一屏条数牺牲可操作性。

## 51. 颜色、图标与主题

### 51.1 颜色

- 语义色表达风险、成功、等待、信息和选中状态；
- 同一语义跨模块保持一致；
- 不能只靠颜色传递状态；
- 案件类型、轨道和标签使用颜色时，应避免与风险等级冲突；
- 大面积高饱和色只用于真正需要聚焦的状态。

### 51.2 图标

- 功能图标使用一致的线性或系统图标语言；
- emoji 不作为正式功能图标或唯一状态信号；
- 图标旁在首次或含义不明确时提供文字；
- 装饰性图标默认省略。

### 51.3 主题

主题系统应保证对比度、语义色和组件状态一致。Solarized、Slate、浅色或深色都可以成为主题实现，但不存在哲学上的“唯一正确配色”。主题切换不能改变风险含义或隐藏状态。

### 51.4 渐变与装饰

渐变、插画和品牌表达不是绝对禁令，但核心工作表面默认不使用与任务无关的装饰。任何装饰都必须证明不会降低扫描、对比和长期专注。

## 52. 动效与反馈

### 52.1 动效的四种正当用途

1. 表达状态变化，如任务完成；
2. 表达空间关系，如面板来自何处；
3. 表达因果，如拖拽落位或撤销；
4. 缓冲异步过程，如提交、同步和回滚。

无法回答“这个动画解释了什么”的动效不进入核心路径。

### 52.2 动效纪律

- 高频操作反馈短且可预测；
- 列表重排保持空间连续；
- 失败回滚明确但不惊吓；
- 尊重系统减少动态效果设置；
- 不用长动画掩盖慢操作；
- 动画完成不是数据成功的唯一信号。

## 53. 键盘、鼠标与无障碍

### 53.1 键盘流

高频循环应能完整用键盘完成：捕获、搜索、切换透视、选择、完成、排程、撤销和返回。快捷键需：

- 集中注册；
- 冲突检测；
- 可发现和可重映射；
- 输入法和编辑器场景不误触；
- 焦点位置始终可见。

### 53.2 无障碍

- 所有交互可由键盘完成；
- 状态不只依赖颜色；
- 文本和控件满足合理对比度；
- 缩放到 200% 时核心流程可用；
- 屏幕阅读器能理解对象、状态和操作；
- 动效、声音和通知可调整；
- 错误提示与对应字段关联。

### 53.3 拖拽不是唯一入口

任何拖拽操作都提供菜单或键盘等价路径，且明确目标语义。

## 54. 文案与状态语言

### 54.1 使用用户语言

优先使用“今天、等待、跟进、期限、已排队、需要复核”等明确词语，避免把内部术语、模型名、数据库状态暴露给普通用户。

### 54.2 避免虚假确定性

推荐文案使用：

- “建议”“可能”“根据以下材料”；
- “缺少送达日期，无法计算”；
- “日历服务已接受，是否送达设备未知”；
- “本地已保存，远端同步失败”。

避免：

- “AI 已确认无误”；
- “提醒必达”；
- “同步完成”但仍有冲突；
- “已发送”但只是进入队列。

### 54.3 错误信息

错误应回答：

1. 什么没有完成；
2. 已经完成的部分是否保留；
3. 数据是否安全；
4. 用户现在可以做什么；
5. 是否需要查看详细技术信息。

## 55. 加载、空状态、失败与降级

每个核心表面都应设计：

- 首次使用空状态；
- 有过滤但无结果；
- 正在加载；
- 部分数据可用；
- 外部连接不可用；
- AI 不可用；
- 写入失败并已回滚；
- 写入成功但同步待完成；
- 权限不足；
- 数据需要迁移或修复。

空状态提供与当前表面相关的下一步，不用泛泛插画占据主要空间。降级状态保持核心结构稳定，避免 AI 版和规则版像两套产品。

## 56. 性能预算

性能是交互设计的一部分。默认预算：

| 场景 | 目标 |
|---|---|
| 点击到本地视觉反馈 | 100ms 内 |
| 高频本地操作 | 先乐观反馈，失败可回滚 |
| 启动到核心焦点可交互 | 约 1.5s 内，具体按设备基线验证 |
| 高频动效 | 目标 60fps，避免主线程长任务 |
| 搜索首批结果 | 输入后可感知即时，复杂语义结果异步补充 |
| 捕获保存 | 原文立即持久化，解析异步 |
| 大列表 | 超过可控阈值后分页或虚拟化 |

预算不是一次跑分。应在代表性真实数据量、冷启动、断网和低性能设备上持续验证。

## 57. 核心体验不变量

以下应成为回归验收：

1. 捕获原文不因后续解析失败而丢失；
2. 完成普通行动不被额外表单阻断；
3. 今日承诺、计划时间和截止期限不会因一个拖拽含糊联动；
4. 任意活跃项目都能找到下一步、等待或暂停理由；
5. 外部操作的队列、接受、送达和确认状态不混称；
6. 关闭 AI 后仍能完成捕获、厘清、计划、执行和回顾；
7. 撤销、失败回滚和同步冲突不会静默丢数据；
8. 键盘用户能完成日常主循环；
9. 颜色关闭或无法分辨时，状态仍可理解；
10. 当前表面不会因低价值装饰抢走主要注意力。

# 第九篇：隐私、安全与职业责任

## 58. 数据分级

建议至少区分：

| 级别 | 示例 | 默认外发策略 |
|---|---|---|
| 公开 | 已公开法律法规、公开裁判文书 | 可按用户授权使用 |
| 内部 | 个人计划、一般工作笔记 | 默认本地，外发需连接策略 |
| 机密 | 客户材料、未公开案件信息、沟通记录 | 最小必要、明确授权、可脱敏 |
| 高敏 | 商业秘密、个人敏感信息、客户特别指定内容 | 默认不出端，逐案例外授权 |

数据分级可以由对象继承并允许字段级提高，不能由 AI 自动降低。

## 59. 隐私默认值

- 默认零遥测或严格选择加入；
- 崩溃报告先本地可见，发送前说明内容；
- 日历、邮件和 AI 外发显示实际字段或摘要；
- 本地模型也不自动获得全部数据；
- 日志避免写入正文、凭据和完整路径，除非受保护诊断模式明确开启；
- 剪贴板、文件夹监听、邮件抓取等持续读取能力必须显式启用并可暂停。

## 60. 凭据与秘密

- API Key、OAuth token、邮箱和日历密码进入系统密钥存储；
- 日志、普通设置导出和数据库备份不包含明文秘密；
- 每个连接可单独撤销和轮换；
- 凭据失效与服务失败区分；
- 云端代发若未来出现，必须明确谁持有凭据、如何加密、如何审计和撤销。

## 61. 最小权限与隔离

- 技能、插件、外部工具和 AI 模型按任务获得权限；
- 项目/案件之间默认隔离；
- 文件系统访问限制到选定目录或工作副本；
- 写操作统一进入执行网关；
- 高敏对象可以完全禁止模型、同步或外部索引；
- 安全策略的拒绝必须可理解，不能鼓励用户为了方便关闭所有保护。

## 62. 法律专业责任边界

- 系统计算期限时展示基准与规则，不替代律师核对送达和例外；
- 法律分析、文书和策略建议是草稿或辅助，不宣称构成法律意见；
- 关键决定保留人类责任主体；
- 团队双人复核只有在确有第二位授权人员时启用；
- 导出或分享前提示敏感信息和引用完整性；
- 系统不能用免责声明掩盖可以通过设计避免的错误。

# 第十篇：开发与设计裁决方法

## 63. 新功能立项的十二问

任何进入核心产品的功能，应先回答：

1. 它解决哪个真实用户问题，发生频率和错误代价是什么？
2. 它位于捕获—沉淀循环的哪一步？
3. 没有它，用户目前怎样完成工作，最痛的摩擦在哪里？
4. 它是新事实、新关系、新视图，还是自动化？
5. 是否会增加新的顶级认知对象或导航入口？为什么不可避免？
6. 哪部分必须确定，哪部分可以由 AI 建议？
7. 它需要什么权限、敏感数据和外部副作用？
8. 离线、AI 关闭、服务失败时怎样降级？
9. 用户如何知道发生了什么，如何撤销、恢复或对账？
10. 怎样用真实任务验证，而不是只看页面是否完成？
11. 它增加了什么长期维护成本和迁移责任？
12. 哪些证据出现时应停止、移除或重新设计？

若这些问题没有答案，功能只能作为实验，不能进入长期基准。

## 64. 新实体还是新视图

按以下顺序裁决：

1. 现有对象增加一个关系能否表达？
2. 现有事实的筛选、排序或分组能否表达？
3. 是否存在独立身份、生命周期、权限、版本或同步需求？
4. 用户是否需要单独创建、查找、讨论和归档它？
5. 如果不独立建模，会不会造成语义混淆或数据丢失？

只有后 3 项明显成立时，才倾向新实体。日历事件是典型独立事实；“今天”是典型视图。

## 65. 功能规格最低结构

每个非平凡功能规格至少包括：

- 用户故事与不做范围；
- 入口与退出；
- 正常流程；
- 状态机；
- 数据权威与来源；
- 权限和敏感性；
- AI/规则分工；
- 空、加载、失败、离线和降级；
- 撤销、幂等和冲突；
- 键盘与无障碍；
- 性能预算；
- 埋点/审计的必要边界；
- 验收场景和测试数据；
- 迁移和回滚。

## 66. AI 功能上线清单

- [ ] 无 AI 路径存在，或已明确说明没有的原因；
- [ ] 输入 Context Policy 已定义；
- [ ] 模型可见数据和外发范围可解释；
- [ ] 输出区分事实、推断和建议；
- [ ] 关键引用可回源；
- [ ] 结构与确定性校验已先行；
- [ ] 权限等级和系统安全下限已定义；
- [ ] 提案执行前会检查快照是否过期；
- [ ] 失败不会丢原始输入或产生半写入；
- [ ] 用户可接受、修改、拒绝和撤销；
- [ ] 学习信号、记忆范围和删除方式已定义；
- [ ] 同模型复核未被宣传为事实证明；
- [ ] 模型切换、限额和不可用状态已测试；
- [ ] 敏感案件可禁用或使用更严格策略。

## 67. Definition of Done

一个功能不是“页面能打开”就完成。至少检查：

### 67.1 产品闭环

- 用户可以从入口完成目标并退出；
- 与上下游对象的关系完整；
- 不依赖隐藏手工步骤；
- 文案和状态与真实语义一致。

### 67.2 数据与可靠性

- 权威来源明确；
- 写入具备事务或补偿；
- 重试幂等；
- 删除、冲突和迁移有策略；
- 备份恢复不被破坏。

### 67.3 体验

- 加载、空、失败、离线和降级已设计；
- 高频路径符合交互预算；
- 键盘、焦点、缩放和颜色可达性通过；
- 动效有因果并支持减少动态效果。

### 67.4 AI 与安全

- 规则/AI/人工职责清楚；
- 权限和确认不能绕过；
- 来源、快照和审计足够；
- 敏感数据遵循最小披露；
- 模型不可用时行为正确。

### 67.5 验证

- 单元、集成和端到端检查与风险相称；
- 真实数据规模和异常路径已运行；
- 视觉与交互通过真实渲染检查；
- 文档只宣称实际验证过的边界。

## 68. 设计评审的优先顺序

当目标冲突时，按以下顺序裁决：

1. 不丢数据、不误导法律事实、不越权；
2. 核心循环可完成；
3. 语义一致、可追溯、可恢复；
4. 高频操作低摩擦；
5. 离线和降级可用；
6. 可访问性与性能；
7. 扩展性与技术整洁；
8. 视觉新鲜感和功能数量。

这不是说后面的不重要，而是当必须取舍时，不能用漂亮界面换取错误期限，也不能用抽象整洁换取断裂工作流。

## 69. 何时允许增加复杂度

满足以下至少一项，复杂度才可能合理：

- 消除高频重复劳动；
- 显著降低高代价错误；
- 完成之前无法完成的核心闭环；
- 让多个现有模块共享同一可靠机制；
- 满足不可回避的安全、合规或数据完整性要求；
- 有真实用户证据证明当前简化方案已经失败。

为对称、为未来可能、为展示技术能力或为追赶竞品，不足以增加复杂度。

## 70. 实验与冻结

### 70.1 实验

未验证的导航、透视、主题、AI 策略和自动化可以实验，但必须：

- 标明假设；
- 限定用户和数据范围；
- 有退出与回滚；
- 不改变长期数据语义；
- 记录成功和失败指标；
- 在验证后决定推广、修订或删除。

### 70.2 冻结

当某条主线正在验证时，可以冻结相邻功能扩张。冻结的目的是保护验证信号和资源，不是永久否定未来。解除冻结需要满足预先说明的条件。

## 71. 真实使用验收

开发完成后，应以持续真实使用验证，而不是只以演示路径验收。建议覆盖：

- 连续多日作为唯一任务与日历工具；
- 至少一个完整项目从捕获到归档；
- 一次突发事项打乱当天计划后的恢复；
- 一次外部服务断开与恢复；
- 一次 AI 关闭或失败；
- 一次同步冲突；
- 一次备份恢复；
- 一次高敏案件的“不出端”流程；
- 一次错误建议的拒绝、修正和后续学习；
- 一次提醒结果未知的对账。

真实使用发现的摩擦应进入决策记录，而不是直接把临时修补写回哲学。

## 72. 指标哲学

优先观察能反映秩序是否改善的指标：

- 捕获后丢失率；
- 收件箱长期滞留；
- 活跃项目缺少下一步/等待的比例；
- 硬期限复核和错误修订；
- 今日承诺过载与反复迁移；
- 等待超时未跟进；
- AI 建议被修改的类型与原因；
- 外部作业结果未知和冲突恢复时间；
- 备份恢复成功率；
- 高频路径所需交互和响应时间。

不把页面浏览量、通知点击率、AI 调用次数和保存数据量当作核心成功指标。

# 第十一篇：典型场景检验

## 73. 场景一：收到法院送达链接

### 73.1 理想流程

1. 用户把链接丢进大口袋，原始链接立即本地保存；
2. 本地规则识别已知送达域名，标记来源风险，但不宣称内容已经下载；
3. 经用户授权后下载文件，保留原件、哈希、下载时间和来源；
4. 解析器提出案号、送达日期、文书类型和关联案件候选；
5. 用户核对关键字段，尤其是送达日期；
6. 确定性期限引擎基于已确认事实计算期限并展示规则链；
7. 系统提出行动、准备窗口和提醒计划；
8. 用户确认后写入案件，原始捕获项与文件、期限和行动保持来源链；
9. 如配置外部日历，提醒作业进入同步并显示真实交接状态。

### 73.2 失败时

- 下载失败：原链接仍在，可重试；
- OCR 不确定：显示原图和候选，不写正式字段；
- 找不到案件：允许暂存或新建项目候选；
- 期限规则缺失：创建“需人工核对”复核项，不编造日期；
- 日历同步超时：状态为结果未知，先对账，不重复创建。

### 73.3 检验到的原则

捕获不丢、事实与推断分离、期限确定性、AI 提案、统一执行、提醒状态诚实。

## 74. 场景二：客户临时请求当天审合同

### 74.1 理想流程

1. 用户快速捕获请求；
2. 系统建议它是独立行动或客户项目事项，不强迫关联案件；
3. 用户确认完成标准和真实截止；
4. 焦点台展示它与今天既有硬事件、期限和计划行动的冲突；
5. 系统可以建议拆分、委派或移出低优先行动，并说明被挤占内容；
6. 用户做出今天承诺，计划时间块随之更新，但其他任务截止不被改写；
7. 完成后可选记录实际耗时，系统用于后续估时校准。

### 74.2 检验到的原则

通用工作基础、时间语义分离、注意力预算、建议不替代承诺、完成不打断。

## 75. 场景三：判决送达后产生上诉路径

### 75.1 理想流程

1. 判决材料与送达事实进入案件；
2. 期限引擎计算候选上诉期限并展示依据；
3. 程序轨新增或激活上诉候选分支，但不自动认定“决定上诉”；
4. 系统提出分析、客户沟通和授权等下一步行动；
5. AI 可以准备判决摘要、争点和上诉利弊清单，清楚区分引用事实与建议；
6. 用户或团队作出正式决定，记录依据、责任和复核状态；
7. 若决定上诉，执行网关创建后续项目结构和提醒；若不诉，保留决定链并安排结案动作。

### 75.2 检验到的原则

案件允许条件分支、决定与状态分离、AI 不冒充法律判断、重要变化版本化。

## 76. 场景四：AI 建议把两个案件关联

### 76.1 理想流程

1. AI 在用户授权的跨案分析范围内发现相同专利或证据模式；
2. 产生关系候选，列出支持材料、可能冲突和敏感范围；
3. 用户选择仅建立“共同专利”关系，拒绝“策略可复用”的更强推断；
4. 系统只写入被接受的关系，并记录创建者和依据；
5. 被拒绝部分作为有限学习信号，不再频繁重复；
6. 后续来源变化时，关系可进入复核状态。

### 76.2 检验到的原则

默认隔离、关系有角色、推断先候选、逐项确认、记忆有范围。

## 77. 场景五：应用关机期间的提醒

### 77.1 理想流程

- 若此前已成功交接外部日历：Casy 显示通道已接受，但不声称终端送达；
- 若仅有本地提醒：重启后补偿扫描，列出错过事项并按过期策略处理；
- 若同步结果未知：先查询远端 UID/版本对账；
- 若用户选择高敏不出端：诚实说明关机期间无外部提醒保障；
- 用户确认处理后，相关通知和复核项统一收敛。

### 77.2 检验到的原则

本地能力边界、外部交接、送达状态、隐私策略与诚实降级。

## 78. 场景六：模型切换或完全关闭 AI

### 78.1 理想流程

- 任务、日程、案件、期限、搜索、捕获和回顾继续可用；
- 原有决定、知识和偏好保持在本地结构中；
- 未完成的模型作业明确暂停或失败，不留下半写入；
- 规则版排序和结构化早报替代叙事建议；
- 切换模型后，新的调用使用相同权限、Context Policy 和提案协议；
- 用户可以查看不同模型产生的建议，但正式数据不依赖模型存在。

### 78.2 检验到的原则

确定性内核、模型无关记忆、降级一致、外部能力无特权。

# 第十二篇：非目标与重开条件

## 79. 当前默认不作为核心的方向

### 79.1 企业级管理

默认不做复杂组织架构、部门权限、绩效看板、工时计费和多级行政审批。重开条件：个人用户中出现明确团队协作需求，且可在不破坏个人体验的能力层实现。

### 79.2 自建云端中继

默认不为提醒或简单同步建设常驻云服务。重开条件：已有日历/邮件/文件同步生态无法满足已验证的可靠性或协作需求，且用户愿意承担凭据托管、合规和持续成本。

### 79.3 完整移动端

默认不因推送问题立项。重开条件：移动录入、查阅、现场工作或跨设备协作本身形成独立高频价值。

### 79.4 通用自主 Agent

默认不让 AI 自由规划并长期运行任意任务。重开条件：存在边界清晰、可沙箱、可暂停、可审计且收益显著的具体工作流。

### 79.5 无限动态字段

默认优先稳定领域语义和受控扩展，不把所有对象变成无约束表格。重开条件：真实业务持续出现无法由关系、模板或扩展字段集表达的需求，并证明维护成本可接受。

### 79.6 为技术整洁的大重写

默认采用可验证的渐进替换。重开条件：现有架构已经造成不可隔离的安全、数据一致性或交付阻塞，且迁移、兼容和回滚方案完整。

## 80. 永久需要举证的方向

以下不是绝对禁止，但提案方始终承担更高举证责任：

- 新顶级模块；
- 新持久化实体；
- 默认外发敏感数据；
- 不可撤销自动化；
- 新常驻后台服务；
- 新模型可见数据；
- 新通知通道；
- 新抽象层或插件系统；
- 改变任务、事件、期限或案件的核心语义；
- 无法导出的专有内容格式。

# 附录 A：术语表

| 术语 | 定义 |
|---|---|
| 权威事实 | 其他视图和建议应从其读取、不能被投影反向含糊覆盖的正式数据 |
| 提案 Proposal | 尚未执行、包含依据与影响说明的候选变化 |
| 执行网关 | 所有写入与外部副作用统一经过的权限、校验、事务和审计入口 |
| 硬边界 | 不能仅凭个人排程随意改变的事件、期限或外部承诺 |
| 下一步行动 | 当前条件满足、能够实际执行并有可判断结果的行动 |
| 等待 | 依赖外部结果、当前不可推进且有跟进语义的状态 |
| 时间块 | 用户计划投入时间的安排，不等于事件或截止期限 |
| 程序轨 | 案件中一条有节点、状态和关系的法律程序路径 |
| 来源链 | 从捕获/材料到事实、建议、决定和行动的可追踪关系 |
| Context Policy | 规定一次 AI 工作可见哪些来源、范围、敏感级别和版本的策略 |
| 结果未知 | 外部调用可能已产生效果但缺少可靠回执，需要对账的状态 |
| 蒸馏 | 把原始活动转化为候选偏好、决定或可复用知识的受控过程 |
| 降级 | 某增强能力不可用时仍保持核心工作可完成的替代路径 |
| 本地优先 | 本机权威、离线可用、外部可替换、数据可携带的权力与架构模型 |

# 附录 B：二十条不变量

1. 原始捕获先保存，解析后进行。
2. 案件可以复杂，但用户必须能找到下一步、等待或暂停理由。
3. 事件、可开始时间、计划时间、期限和提醒绝不含糊混用。
4. 一个事实只有一个权威来源，视图可以很多。
5. 案件默认隔离，跨案关系有角色、有依据、可撤销。
6. 今日是用户承诺，不是日期字段的机械集合。
7. 期限计算走确定性规则并保留依据。
8. AI 默认产出提案，不直接改正式数据。
9. 所有写入口共享权限、校验和审计。
10. 模型复核不是事实证明，也不是真正的双人复核。
11. 规则从候选到启用必须经过测试和批准。
12. 用户可以关闭 AI 而不失去核心工作流。
13. 模型可以更换，决定、偏好和知识不丢。
14. 本地数据是默认权威，外部服务是可替换增强。
15. 同步冲突、部分成功和结果未知必须可见。
16. 通道接受不等于送达，送达不等于用户确认。
17. 高频动作即时反馈、可撤销、失败可恢复。
18. 视觉、动效和通知只服务状态、因果与行动。
19. 当前实现、路线图和完成度不能写成长期哲学。
20. 任何新增复杂度都必须证明它减少了更大的工作或风险。

# 附录 C：一句话总结

> **Casy 把涌入的信息变成可信的事实、清晰的承诺和可恢复的上下文；规则守住确定性，AI 准备和建议，人保留决定权，本地数据保留最终权威。**

更短的产品箴言：

> **安静地准备，清楚地建议，可靠地执行，完整地留痕。**
