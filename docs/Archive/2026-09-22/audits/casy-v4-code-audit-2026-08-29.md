# Casy 当前工作区全面代码审计

> 审计日期：2026-08-29  
> 审计对象：当前未提交工作区，而非 `HEAD`、README、历史完成清单或预构建产物  
> 对照基线：设计哲学 V4、初版设计哲学（v2.4）、产品设计 v3  
> 审计性质：只读审计；本报告不包含应用代码修复  
> 结论等级：**不建议按“V4 已实现”或“可发布”验收**

---

## 1. 执行摘要

Gemini 这轮工作显著扩展了 Casy：当前前端可以通过类型检查、单元测试和生产构建，Rust 的 115 项测试也能通过；案件、任务、日历、收件箱、知识库、写作、提醒、报告、同步、AI、主题和简报皮肤已经形成相当完整的界面与代码骨架。

但本轮最重要的问题不是“界面好不好看”，而是：**功能表面积已经远大于被验证的可信闭环**。当前代码同时存在四类会破坏 V4 根本契约的问题：

1. 任务的局部更新可能清空其他字段，而且完成、阻塞等操作实际上没有被后端更新；日历又把不同时间语义混在一起。
2. 应用内 AI 工具调用没有统一的默认拒绝授权网关，大部分写操作可由模型直接执行。
3. AI、WebDAV、SMTP、CalDAV 等凭据仍可作为普通设置值进入数据库和前端；同步、备份恢复也没有形成可证明的安全闭环。
4. 首页、收件箱和简报存在硬编码的案件、期限、建议与“全部清零”等陈述，样例、空状态与真实事实没有隔离。

因此，本次审计的总判断是：

> Casy 已经从“功能不足”进入“能力很多，但系统契约尚未收口”的阶段。下一轮不应继续堆功能，应该先修复数据完整性、权限、事实可信度和恢复能力，再谈完成度。

周报皮肤等情绪价值模块**应当保留**。问题不在于它们有情绪价值，而在于它们目前与真实周报数据、样例标识、可访问性、导出隐私和事实语义的边界还不够清楚。V5 将“有边界的温度”纳入正式设计原则，不再沿用初版对情绪价值的绝对否定。

## 2. 审计边界与证据优先级

### 2.1 本次以什么为准

证据优先级如下：

1. 当前工作区源代码与实际命令结果；
2. 数据库约束、命令入口和真实调用链；
3. 设计哲学 V4；
4. 初版设计哲学与产品设计 v3；
5. README、路线图、完成勾选和历史审计文档。

当前工作区存在大规模未提交变化：94 个已跟踪文件有变化，另有 74 个未跟踪文件。`docs/anti-gravity/` 本身也是未跟踪目录。因而本报告描述的是“审计时本机工作区快照”，不是已经进入版本库或能够从远端复现的发布状态。

### 2.2 本次没有证明什么

以下事项没有因为浏览器页面可见或构建成功而被证明：

- Tauri IPC 与本地 SQLite 的完整运行行为；
- 系统钥匙串、文件系统、通知和全局快捷键；
- WebDAV、CalDAV、飞书、SMTP/IMAP 的真实账号联调；
- 数据库备份恢复后的重新启动与数据一致性；
- Windows 安装包及升级器；
- 真实案件数据下的周报、导出和脱敏结果。

浏览器模式仍然非常适合调 CSS、布局、响应式和前端交互；它只是不应被当作原生能力验证环境。没有必要仅仅因为 UI 调试而把 Vue/TypeScript 再迁移到另一套技术栈。

## 3. 三份设计基线如何理解

### 3.1 初版设计哲学（v2.4）

初版确定了 Casy 的重要方向：克制、可靠、时间双轨、案件顺序推进、统一捕获、AI 伴随、复盘与本地优先。这些仍然有价值。

但初版混合了稳定原则、具体界面、技术实现、路线图和完成状态，还包含两项后来被 V4 纠正的表述：

- 把“拒绝情绪价值装饰”写成绝对原则；
- 把同一模型的额外调用或同一用户再次确认称为“L3 双人复核”。

本次审计不把这两项当作应恢复的要求。

### 3.2 产品设计 v3

v3 把模块、路由和阶段目标整理得更可执行，但大量 P0/P1/P2 的完成标记属于历史声明，不能替代当前代码验证。它仍然沿用对情绪价值的排斥，也把若干固定视图当成原则。

### 3.3 设计哲学 V4

V4 是本次的主要判断标准。它把 Casy 定义为一个本地优先的专业工作系统，并把核心循环写成：

> 捕获 → 澄清 → 组织 → 计划 → 执行 → 观察 → 复盘 → 学习

V4 还明确纠正了旧文档：固定六入口、固定六任务视图、三轨结构、卡片位置和视觉风格都不是不可变哲学；真正不可让步的是数据语义、授权、可追溯、可恢复和诚实降级。

### 3.4 本次采用的合并原则

- V4 的安全、数据和产品契约优先；
- 初版的克制与行动导向保留；
- 初版对情绪价值的绝对否定废止；
- v3 的模块蓝图仅作为产品参考，不作为完成证明；
- 当前实现若与文档冲突，以当前实现作为“发现问题”的证据，而不是反过来改写哲学。

## 5. V4 原则符合度总览

| V4 原则 | 状态 | 结论 |
|---|---|---|
| 承诺比条目重要 | 部分符合 | 今日、下一步、复盘已出现，但状态变更链不可靠 |
| 捕获优先于分类 | 较好 | 统一捕获、收件箱和快捷入口基本形成 |
| 时间语义必须分离 | **不符合** | 截止、计划、开始、提醒在 DTO、更新和拖拽中混用 |
| 少量真实认知对象 | 不符合 | 样例、空状态和事实陈述未隔离 |
| 对象隔离、角色连接 | 基本符合 | 模块分域较清楚，案件关联广泛存在 |
| 注意力稀缺 | 部分符合 | 入口已收敛一些，但功能与设置表面积继续膨胀 |
| 本地权威与可退出 | 部分符合 | SQLCipher 是优点；同步、备份恢复尚不可信 |
| 确定性内核、概率性增强 | 部分符合 | 期限和报告规则层较好；AI 写入边界失守 |
| AI 先提案后执行 | **不符合** | 多数内部 AI 写工具没有权限策略，直接执行 |
| 可追溯、可逆、可对账 | 部分符合 | 有审计和待确认机制；覆盖范围与恢复路径不足 |
| 学习与记忆受治理 | 部分符合 | 有候选确认机制；偏好接口未接通且权限语义混杂 |
| 开放能力、收紧权限、诚实降级 | **不符合** | 浏览器 mock、同步状态和失败结果存在误导风险 |

总体上，架构方向与 V4 有明显重合，但三个底层契约——**时间、授权、事实**——尚未达到可以信任的程度。

## 6. 关键发现

严重度定义：

- **P0**：可能造成数据损坏、越权写入、错误安全判断或凭据风险；必须先修。
- **P1**：功能承诺不成立、恢复链断裂、验证缺失或高维护风险；应在下一发布前修。
- **P2**：一致性、可维护性或长期产品债务；应纳入收口阶段。

### P0-01：任务“局部更新”会丢字段，而且完成/阻塞操作不生效

**证据**

- `src-tauri/src/commands/tasks.rs:479-550` 的 `update_task` 采用一条完整 `UPDATE`，请求中缺失的多个字段会被写成 `NULL`。
- 同一命令没有更新 `completed` 和 `blocked` 字段。
- 前端大量调用只发送单个变化：
  - `src/modules/calendar/views/CalendarView.vue:193-198,232-238,265-271,856`
  - `src/modules/cases/views/CaseListView.vue:510`
  - `src/modules/tasks/views/TasksView.vue:413,429`
  - `src/modules/cases/views/CaseDetailView.vue:243-246`
  - `src/modules/tasks/components/TodayResetDialog.vue:97-102`

**实际后果**

- 勾选完成或切换阻塞时，目标字段可能根本不变化；
- 与此同时，期限、案件、上下文、估时、父任务、重复规则等未传字段可能被清空；
- 用户看到的交互成功不代表数据库状态正确。

**违反 V4**

违反“承诺完整性”“可追溯与可对账”“确定性内核”。这是本次审计优先级最高的问题。

**给 Gemini 的整改验收条件**

1. 明确采用 PATCH 语义：区分“字段未提供”与“显式清空”。
2. `completed`、`blocked` 等实际可更新。
3. 为每个局部更新入口建立数据库级集成测试。
4. 测试必须证明：只改一个字段时，其他所有字段保持不变。
5. 更新失败时前端回滚乐观状态并显示可操作错误。

### P0-02：时间模型在数据库、DTO 和日历交互中互相冲突

**证据**

- `src-tauri/src/db/schema.rs:1357-1358` 的 `start_bucket` 只允许 `inbox|anytime|someday|today`。
- 日历写入 `scheduled`：`CalendarView.vue:189,197,229,237`。
- 任务快速捕获也写入 `scheduled`：`TasksView.vue:385`。
- 稍后处理命令写入 `upcoming`：`src-tauri/src/commands/tasks.rs:455-460`。
- 日历更新发送 `startTime`，后端字段却是 `dueTime`，已有时间还可能因局部更新被清空。
- 前端类型把 `deadline` 描述为 `dueDate` 别名：`src/types/index.ts:270`。
- 后端创建任务时也把 `deadline` 和 `dueDate` 合并：`tasks.rs:199-217`。
- Rust 的任务返回 DTO 没有 `due_time`，而前端任务类型有 `dueTime`。
- 日历拖拽同时操作 `startDate`/`dueDate`，暂存区则清除 `dueDate`，没有向用户说明改的是计划时间、可开始时间还是期限。

**实际后果**

- 部分写入会触发数据库约束失败；
- 用户拖动一个任务可能改变法律期限含义；
- 保存的时间无法可靠返回前端；
- 今日承诺、可开始、计划、截止与提醒不能独立推理。

**违反 V4**

V4 明确要求事件时间、计划时间、可开始时间、截止期限和提醒分别建模，并把“拖到明天同时修改期限”列为反例。

**给 Gemini 的整改验收条件**

1. 先形成单一时间字段表，再迁移数据库、Rust DTO、TypeScript 类型和 UI。
2. 建议至少独立：`available_at`、`planned_start/planned_end`、`deadline_at`、`reminder_at`、日历事件时间。
3. `start_bucket` 只表示状态桶，不承载日期。
4. 每个拖拽目标在界面上明确显示将改变的语义。
5. 对旧数据提供可回滚迁移和歧义报告，不静默猜测法律期限。

### P0-03：应用内 AI 可绕过“Proposal → 授权 → 执行”

**证据**

- `src/modules/ai/components/AIChatPanel.vue:118-122` 传入 `{ autoConfirm: false }`。
- `src/core/ai/tool-caller.ts:153-156` 将该参数命名为 `_opts`，实际未使用。
- 同文件 `178-217` 在模型输出工具调用后直接执行 `casyContext.executeTool`。
- `src/core/plugin/context.ts:294-334` 仅在工具声明了 `policy` 时确认；缺少策略的工具直接执行。
- 类型注释把“缺少 policy”视为只读 L1：`src/core/plugin/types.ts:41-48`。
- 当前约 38 个工具中只有 5 个带 `policy`。
- 创建/更新/完成/删除任务、创建/更新案件、保存设置、配置 AI、创建提醒、启动引擎、处理收件箱、创建/更新知识条目等写操作没有完整策略。
- `context.ts:439-475` 所谓“L3 双人复核”只是同一用户输入“确认”。

**实际后果**

模型可以把一次聊天建议升级为正式数据变更；新增工具若忘记声明策略，会被当作低风险而不是拒绝执行。

**违反 V4**

V4 要求 A0-A3、先提案后执行、默认拒绝，并明确指出模型复核和同一用户再次点击都不是真正的第二人复核。

**给 Gemini 的整改验收条件**

1. 建立单一、不可绕过的服务端授权网关。
2. 工具未声明策略时默认拒绝，而不是默认 A0/A1。
3. 写操作至少先形成可读提案，展示字段差异、对象、范围和回滚方式。
4. A3 必须逐动作即时授权；没有真正第二位授权人员时不得显示“双人复核”。
5. 工具执行前后都写审计记录，并保留幂等键/撤销或补偿信息。
6. 为每个工具自动生成权限清单测试，新增工具未分类时 CI 失败。

### P0-04：多类凭据仍作为普通设置存储和返回

**证据**

- `src/stores/settings.ts:7-33` 把 `ai_api_key`、`webdavPassword`、`smtp_pass`、`caldav_pass` 放在通用设置对象中。
- 通用保存会整体发送设置：`settings.ts:48-52`。
- `src-tauri/src/commands/settings.rs:31-49` 将任意键值写入设置表；读取接口又把全部值返回前端。
- AI 配置直接从设置数据库读取/写入 `ai_api_key`：`src-tauri/src/ai/mod.rs:291-347`。
- 凭据模块定义了多种钥匙串类型，但迁移逻辑主要覆盖 IMAP；AI 凭据辅助函数未接入主流程。
- SMTP、CalDAV 在钥匙串失败时回退数据库；WebDAV 仍依赖数据库设置。

**边界说明**

主数据库使用 SQLCipher，因此这里不能简单描述为“明文落盘”。问题是：秘密仍被当成普通业务设置，可返回前端、进入数据库备份和同步范围，权限与生命周期不受凭据专门治理。

**给 Gemini 的整改验收条件**

1. 通用设置 API 永不返回秘密原文，只返回 `configured`/来源/最后验证时间。
2. 所有秘密统一进入系统钥匙串；不允许静默回退普通设置表。
3. 迁移需支持成功确认、失败回滚和旧值清除。
4. 钥匙串不可用时诚实降级，并阻止需要秘密的动作。
5. 备份、同步、日志、崩溃报告和导出均建立秘密扫描测试。

### P0-05：首页、收件箱和简报混入未标识的伪事实

**证据**

- `src/modules/home/HomeView.vue:229-269` 在没有下一步任务时生成“法庭排期与绝限红线已全部清零”。空结果并不能证明全部风险已核验。
- `HomeView.vue:620-649` 固定显示“隆基股份无效案 4 小时内截止”“知识库已检索到胜诉模板”等建议。
- 对应按钮只记录决策；“一键导入”并不导入，`HomeView.vue:405-414`。
- 下一步案件编号有固定回退值 `CIV-23-089`，`HomeView.vue:603`。
- `InboxView.vue:358-373,405,486-526` 固定显示案件名、剩余时间、“3 hours ago”、截止时间、估时和 AI 提取状态。
- `BriefingModal.vue:55-88` 默认属性内置虚构案件、期限、庭审与指标；设置预览没有明确的“样例数据”水印。
- 简报和首页会依据一个局部数组为空就输出“全部清零/无逾期”等安全结论。

**实际后果**

专业用户无法区分真实数据、演示数据、推断、空状态和加载失败；错误的“无风险”比缺少信息更危险。

**给 Gemini 的整改验收条件**

1. 生产路径删除所有具体虚构案件、期限和事实回退。
2. 预览必须使用独立 sandbox 数据源并持续显示“样例，不代表真实案件”。
3. 明确区分：未配置来源、尚未加载、加载失败、无数据、已核验无风险。
4. “全部清零/无逾期”必须附数据来源、覆盖范围、核验时间和失败源状态。
5. 按钮文案必须与真实动作一致；记录反馈不能叫“一键导入”。

### P1-01：WebDAV 状态、自动同步和失败语义不诚实

**证据**

- `src-tauri/src/sync/mod.rs:31-41` 的同步状态仍是 TODO，固定返回未连接、空时间和零待处理。
- `webdavAutoSync` 有设置开关，但未找到启动或调度读取链路。
- `src-tauri/src/commands/sync.rs:10-25` 把连接失败作为 `Ok("连接失败…")` 返回。
- `WebDAVSettings.vue:24-38` 只要调用本身 `ok` 就显示绿色成功，因此网络认证失败也可能显示“连接成功”。

**整改验收条件**

- 失败使用结构化错误或明确的结果枚举；
- 状态来自真实同步队列与最近结果；
- 未实现的自动同步开关删除、禁用并说明，或补齐可靠调度；
- 离线、认证失败、冲突、远端不可达分别展示且可恢复。

### P1-02：加密数据库同步与恢复路径尚未形成可信闭环

**证据**

- `src-tauri/src/sync/mod.rs:44-50` 使用普通 `rusqlite::Connection::open` 对 SQLCipher 数据库执行 `VACUUM INTO`，未见应用密钥。
- 拉取后 `207-215` 也用普通连接做完整性检查。
- 这从静态代码看很可能无法正确处理真实加密库，但仍需用真实 SQLCipher 数据库运行证明。
- 同步会把原始数据库密钥与加密数据库上传到同一 WebDAV 位置，`sync/mod.rs:145-149`，削弱“远端只拿到密文”的威胁模型。
- `backup.rs:95-112` 的恢复文件名校验只检查前后缀及是否含 `[`，并没有真正拒绝 `/`、`..` 等路径元素。
- 恢复前产生的 `pre-restore-*.db` 不在备份列表的 `casy-backup-*` 过滤范围，用户无法从常规界面恢复这份回滚点。
- 恢复在应用数据库连接仍活跃时覆盖数据库，之后仅提示重启，缺少原子替换与重新打开验证。

**整改验收条件**

1. 明确威胁模型：远端备份密钥不能与密文同域同权保存。
2. 使用带密钥的连接完成导出和完整性检查。
3. 恢复流程采用关闭连接 → 临时文件验证 → 原子替换 → 重开 → schema/data smoke test。
4. 路径必须通过规范化和允许目录验证；拒绝任何路径分隔符和父目录。
5. 用户能看见并恢复 pre-restore 回滚点。
6. 加入真实加密库、错误密钥、断网、半包、冲突和回滚集成测试。

### P1-03：周报皮肤已经丰富，但尚未接入“真实周报”闭环

**证据**

- `BriefingStyleSettings.vue` 定义 16 个日报样式和 16 个周报样式；注释仍写“8”，说明文档和实现已漂移。
- `BriefingModal.vue` 有 31 个显式样式分支及一个最终回退，未发现缺失样式分支。
- 两个组件合计约 2,462 行；简报组件单独形成约 240 KB 的构建块。
- 首页打开“周报”时没有读取或传入后端生成的真实周报内容，而是继续使用当前日报红线、任务统计和当前日期范围：`HomeView.vue:697-713`。
- 设置页默认先打开简报皮肤，而不是通用、安全或数据设置。

**判断**

该模块不是应删除的“装饰”。它可以提供复盘仪式感、完成感、个人表达和重新进入工作的动力。当前问题是它仍偏“皮肤展示”，未成为可靠的周报消费界面。

**整改验收条件**

1. 周报皮肤只渲染真实周报数据模型，不复用日报临时数据冒充周报。
2. 样例模式永久可辨识；真实模式不带虚构默认值。
3. 皮肤只改变表现，不改变风险等级、数字、排序和事实文案。
4. 提供中性默认、减少动态、对比度、键盘、缩放和黑白导出检查。
5. 导出前显示隐私范围；“脱敏”必须有明确规则、预览和失败提示。
6. 把样式数据化并拆分组件，降低分支和打包体积。

### P1-04：浏览器 mock 与原生事实边界过于安静

**证据**

- `src/core/tauriBridge.ts:22-45` 在纯浏览器环境使用 mock；不支持的命令可能静默返回 `browser-mode: no mock`。
- `src/core/mockData.ts` 包含大量虚构案件、任务和事件，设计目标本来就是浏览器预览。

**整改验收条件**

- 浏览器顶层始终显示可见的“预览数据 / 非原生运行”标识；
- 未模拟命令明确报“当前环境不可验证”，不返回类似成功的结果；
- 建立两套验收表：浏览器视觉验收与 Tauri 原生能力验收；
- 不需要迁移前端技术栈，只需要正确划分测试环境。

### P1-05：依赖、CI、发布配置和测试门禁没有收口

**证据**

- 严格 `clippy` 与 `cargo fmt --check` 失败。
- `npm audit --omit=dev` 有 2 个高危漏洞，来自 `html-to-docx → image-size`；自动修复要求破坏性降级，不能直接机械执行。
- `cargo audit` 有 20 个允许警告，包括 `glib 0.18.5` 的 unsound 公告。
- Windows 不在 Rust 测试矩阵内，而发布流程包含 Windows 打包。
- CI 引用的 `src-tauri/tauri.release.conf.json` 当前未跟踪；若未纳入提交，远端发布流程无法复现本地行为。
- 0 字节 `src-tauri/casy.db` 当前未跟踪且未被 `.gitignore` 排除，存在误提交本地数据库文件的风险。
- 前端只有 9 项单元测试，无法覆盖 22 个路由和关键工作流。

**整改验收条件**

- CI 必须通过 typecheck、单测、build、fmt、严格 clippy、安全审计策略和核心集成测试；
- Windows 至少进入编译/测试矩阵，真实安装启动另列发布验收；
- 审核并固定 DOCX 导出方案，不在浏览器不兼容警告下默认宣称可用；
- 发布配置纳入版本控制；本地数据库、密钥和临时脚本纳入忽略/清理策略；
- 安全公告若暂不能消除，必须有带责任人、影响判断和到期日的例外记录。

### P1-06：确定性报告做得较好，但 AI 叙事与“已确认事实”仍需分层

**正面证据**

- `src-tauri/src/ai/reports.rs:247-301` 先生成并保存规则摘要，再可选调用 AI。
- AI 提示明确要求不得编造，失败时回退规则版本，并写审计记录。

**剩余问题**

- AI 叙事会覆盖同一 `content` 字段，而记录仍沿用确定性报告的 `confirmed` 状态。
- 用户主要只能通过 `narrativeSource` 判断来源，事实层与表达层没有结构分离。

**整改验收条件**

- `facts/metrics/sourceCoverage` 与 `narrative` 分字段保存；
- 确认状态分别作用于事实快照和 AI 文案；
- AI 文案不得改变风险、数字和来源；
- 重生成只替换叙事层，保留对应事实版本和差异。

### P2-01：组件规模和功能表面积已开始妨碍可靠验证

当前几个组件体量：

| 组件 | 约行数 |
|---|---:|
| `CaseListView.vue` | 3,586 |
| `CalendarView.vue` | 3,282 |
| `BriefingModal.vue` | 1,742 |
| `TasksView.vue` | 1,533 |
| `HomeView.vue` | 1,410 |
| `InboxView.vue` | 1,262 |
| `BriefingStyleSettings.vue` | 720 |

这些文件同时承担取数、状态、业务规则、交互和展示，使一次局部修改很容易破坏另一条路径。数据库已演进到 schema v18，前端有 22 个路由，能力数量已经超过现有测试体系能够证明的范围。

**整改建议**

- 按领域用例拆分，而不是只按视觉组件拆分；
- 将任务更新、时间变换、授权、报告事实模型做成可独立测试的核心层；
- 新功能在核心闭环收口前进入 feature freeze。

### P2-02：五套有效主题仍有大量硬编码颜色

设置中列出 6 个选项，其中一个是“跟随系统”，实质上是 5 套有效配色。源码中仍有约 1,288 处十六进制、RGB/HSL 或直接色值引用，分布在约 68 个文件。报告皮肤和主题 token 占其中一部分，但写作、提醒、客户、任务、知识库等核心视图也仍有硬编码。

**整改验收条件**

- 风险、成功、提醒、选中、边界、底色等核心语义全部使用 token；
- 皮肤内部允许专属色板，但必须映射可读性和风险语义；
- 5 个主题分别进行关键页面截图回归和对比度检查；
- “跟随系统”验证浅色/深色即时切换，而不是只验证初次加载。

### P2-03：设置首页把装饰偏好置于安全和数据治理之前

`SettingsView.vue` 当前默认打开简报样式。这会让一个很有价值但非基础安全的模块，在信息架构上压过通用、凭据、备份和同步。

建议保留皮肤入口，但默认进入通用设置，或增加“设置总览”，优先展示数据库、备份、同步、凭据与 AI 权限健康状态。情绪价值应该被尊重，但不应改变风险优先级。

## 7. 已经做对、应当保留的部分

这次审计并不是否定 Gemini 的整体工作。以下方向应保留并继续深化：

1. **统一捕获入口**：全局捕获、收件箱和来源字段符合 V4 的“先卸载认知负担”。
2. **确定性期限与报告内核**：规则计算先于 AI 叙事，失败可回退，是正确方向。
3. **提醒状态语义**：已有 `delivery_unknown`、工作时间、去重等测试，体现了诚实状态设计。
4. **SQLCipher 本地数据库**：本地数据加密和数据库密钥进入钥匙串是重要基础。
5. **知识来源与 AI 洞察确认**：来源、候选和确认机制比直接把模型输出当事实更可靠。
6. **MCP 外部写入待确认队列**：外部通道已有 token、审计和 pending write，明显优于当前应用内 AI 工具链。
7. **主题与简报皮肤**：个性化和复盘仪式感有真实产品价值，应该在可信数据之上继续建设。
8. **Tauri 能力列表相对克制**：当前权限声明没有无边界扩张。

## 8. 情绪价值模块的正式审计结论

### 8.1 不应删除

周报皮肤、复盘仪式、完成反馈、个性化表达可以降低重新进入工作的阻力，给长期高压专业工作提供阶段性结束感。它们不是天然的“注意力污染”。

### 8.2 也不能无边界扩张

情绪价值必须位于事实之上，而不能替代事实。建议把界面分为三类表面：

| 表面 | 情绪表达强度 | 规则 |
|---|---:|---|
| 执行与安全核心 | 低 | 期限、权限、同步、恢复、确认始终中性、直接、语义稳定 |
| 复盘与完成表面 | 中到高 | 周报、月报、完成庆祝、阶段总结可以使用皮肤和仪式感 |
| 预览与实验沙盒 | 高 | 可大胆实验，但必须持续标明样例/预览，不得混入正式数据 |

### 8.3 不可突破的边界

- 皮肤不能改变风险颜色含义、事实数字、排序或授权动作；
- 空数据不能被写成“风险清零”；
- 样例必须永久可辨识；
- 用户可以回到中性模式，并支持减少动态和高对比；
- 导出前必须看到隐私范围；
- 情绪化文案不能制造虚假安全感、羞耻感或完成压力。

## 9. 功能成熟度建议

以后不建议再用“页面存在”或“代码已写”标记完成。建议统一使用五级成熟度：

| 等级 | 定义 | 可否对外宣称 |
|---|---|---|
| M0 想法 | 只有需求或设计 | 否 |
| M1 原型 | 可见、可交互，可能使用 mock | 只能称预览 |
| M2 已接线 | 真实命令与数据源已连接 | 只能称实验性 |
| M3 已验证 | 正常、错误、离线、权限、恢复路径通过测试 | 可称可用 |
| M4 可靠 | 真实环境长期运行、有可观测性和回滚 | 可稳定承诺 |

按本次证据的粗略判断：

| 能力 | 当前成熟度 | 主要缺口 |
|---|---:|---|
| 统一捕获/收件箱 | M2 | 伪事实清理、端到端测试 |
| 任务管理 | M1-M2 | 局部更新和时间模型阻断 |
| 案件管理 | M2 | AI 写权限、复杂路径测试 |
| 日历 | M1-M2 | 时间语义和数据库枚举冲突 |
| 提醒 | M2-M3 | 真实 OS/外部通道验证 |
| 知识库 | M2 | 来源/确认仍需端到端验证 |
| 报告规则层 | M2-M3 | 事实与 AI 叙事分层 |
| 周报皮肤 | M1-M2 | 未接真实周报模型 |
| 浏览器预览 | M2（视觉） | 必须持续标明 mock 边界 |
| WebDAV 同步 | M1 | 状态、自动同步、加密库、密钥模型 |
| 备份恢复 | M1-M2 | 原子恢复、路径安全、可回滚验证 |
| 应用内 AI 工具 | M1 | 授权网关阻断 |
| MCP 外部写入 | M2 | 真实客户端与恢复测试 |
| 发布流程 | M1-M2 | CI、Windows、未跟踪配置、安全依赖 |

## 10. 建议给 Gemini 的整改顺序

### 阶段 0：冻结新增功能

- 不再增加新按钮、新页面、新皮肤和新 AI 工具；
- 先把现有功能登记到成熟度表；
- 对 mock、实验、未接线功能统一标识。

### 阶段 1：修数据完整性

- 重做任务 PATCH 语义；
- 统一时间模型、枚举、DTO 和日历交互；
- 为任务创建、局部更新、完成、阻塞、拖拽、延后建立数据库集成测试；
- 对现存数据做迁移报告。

### 阶段 2：建立统一授权内核

- 服务端 A0-A3 网关；
- 工具无策略即拒绝；
- 所有写入先提案、再明确授权；
- 移除错误的“双人复核”命名；
- 把内部 AI、MCP、自动化和快捷动作纳入同一审计语义。

### 阶段 3：收紧凭据、同步和恢复

- 凭据全部迁移钥匙串；
- 重新设计远端备份密钥模型；
- 修复 WebDAV 结果语义和真实状态；
- 完成 SQLCipher 备份/恢复的原生端到端测试；
- 保证回滚点在 UI 中可达。

### 阶段 4：清除伪事实

- 生产数据、样例数据、加载失败和空状态完全隔离；
- 删除硬编码案件、期限和“已清零”结论；
- 给所有安全结论附来源覆盖和核验时间。

### 阶段 5：恢复工程门禁

- `fmt`、严格 `clippy`、前端安全审计和核心测试进入 CI；
- 审核 DOCX 依赖与包体；
- Windows 进入测试矩阵；
- 把发布配置纳入版本库，排除本地数据库和临时脚本。

### 阶段 6：把情绪价值模块做成可靠产品

- 周报皮肤接真实周报数据；
- 事实层与叙事层分离；
- 样例水印、无障碍、减少动态、导出隐私和主题回归测试；
- 把庞大条件分支改为数据化样式系统。

## 12. 最终审计意见

Casy 现在不是缺少功能，而是需要一次“可信度收口”。Gemini 的大量实现并非无效：许多模块已经具备继续打磨的基础，尤其是统一捕获、确定性报告、提醒状态、知识来源、MCP 待确认写入、主题和简报体验。

但在任务数据、时间语义、AI 授权、凭据、同步恢复和伪事实这几个问题修复前，任何“全面完成”“所有期限已监控”“安全可恢复”或“V4 已落地”的结论都不成立。

下一轮最正确的工作不是继续扩张，而是让用户看到的每一个状态都可以被数据库、来源、权限和测试证明；让每一个高风险动作都可追溯、可中止、可恢复；然后再用有边界的情绪表达，让可靠的结果变得更愿意被人使用。
