## 前言：为什么不是单纯「抄」

读完两篇文章后我意识到一个关键认知陷阱：**绝大多数知识管理工具只是在「攒数据库」，而 FLO.W 思流和项目看板 3.0 真正解决的是「决策时信息以什么形态进入视野」**。

FLO.W 思流的核心不是 4 个数据库，而是「三层信息过滤系统」——主页层（今天必须看到）/ 核心模块层（场景内必用）/ 细分功能层（用时才找）。它是「渐进式信息披露」的设计哲学。

项目看板 3.0 的核心不是 Obsidian 模板，而是「不同项目需要不同执行策略」——计算型要 DDL 驱动、探索型要保留自由度、成长型要打卡制。它是「承认项目异质性」的设计哲学。

下面按文章拆分核心结论，再交叉提炼对 Casy 的具体启示。

## 第一篇：FLO.W 思流的核心设计

文章核心不是模板本身，而是作者总结的 **「3-3-3 框架」**——3 个长期策略 / 3 个承重基座 / 3 个关键动作。

### 1.1 三个长期策略（心态层）

| 策略 | 反面 | 正面 |
|------|------|------|
| **做建筑师不做室内设计** | 沉迷图标、封面、配色 | 关注地基/承重/动线 |
| **建小房子不盖摩天大楼** | 一个页面塞所有数据库 | 每个独立模块有自己的页面 |
| **拥抱杂物间** | 强迫归类 | 允许 Inbox 收纳混乱 |

**最重要的洞察**：作者明确说「追求效率是副产品，追求的是秩序带来的安全感」。这是设计师的同理心起点——大部分律师工具功能堆得很满，但用户找不到「我现在该做什么」。

### 1.2 三个承重基座（骨架层）

#### 基座 A：克制的层级数量（三层过滤）

**第一层 = 主页（高优先级过滤器）**：今天必须看到的事。
**第二层 = 核心模块（场景过滤器）**：80% 的日常操作。
**第三层 = 细分功能（个性化过滤器）**：复杂报表，按需进入。

**对照图示**（FLO.W 主页设计图）：
- 顶部一行同步导航栏（11 个功能模块横向排列）
- 左侧浮动添加按钮（Add | 笔记/速记/任务/选题）—— **关键洞察**：捕获入口要随时可见
- 中部自定义标语区
- 下部日程 Tab（本周/本月/所有日程）
- 底部项目 Tab（项目/任务/笔记三视图切换）

#### 基座 B：有限的元信息类型（4 个核心数据库）

只建 4 个数据库，**所有细分需求都是这 4 个的视图**：

| 元信息 | 数字化形态 | Law 律师业务对应 |
|--------|-----------|----------------|
| **任务 (Task)** | 驱动行动的最小单位 | 行动项 / 期限 |
| **项目 (Project)** | 为达成目标而发起的一系列任务 | 案件（一个案件 = 一个项目） |
| **领域 (Area)** | 长期深耕的人生方向 | 律所业务方向（专利诉讼/无效/顾问） |
| **笔记 (Note)** | 支撑任务/项目/领域运转的可复用信息 | 知识库（法条、案例、模板） |

**关键洞察**：作者从 PARA 四元（Project/Area/Resource/Archive）改造而来，认为 Resources 定义模糊、Archives 是状态而非类型。这一修正在 Casy 也成立——「案件文件」应该存在「任务」或「笔记」里，而不是单独的第五个数据库。

#### 基座 C：有方向感的信息关联（Relation 字段）

**关键设计**：关联字段不仅仅是指针，它**带有角色和意图**。

```
任务 关联 项目 → 搞清这件小事朝向哪个更大目标
项目 关联 领域 → 确保短期努力推动长期方向
笔记 关联 领域 → 把可复用经验存进能力仓库
任务 关联 笔记 → 给马上要做的事更多背景参考
```

**对照图示**（FLO.W 元信息视图分类图）：

任务的视图分类：
- **核心分类**（按类型）：待办 To-do / 日程 Event / 今日待办 / 任务收集 / 周月规划 / 预期警报
- **关键视图**（按排期）：Todo / Doing / Done
- **关键视图**（按状态）：Todo / Doing / Done

笔记的视图分类（**这是律师知识库的关键启发**）：
- **核心分类**（按类型）：经验 / 方法 / 灵感 / 问题 / 日志 / 参考
- **关键视图**（按进度+关注度）：进行中 / 未开始 / 已完成 / 活跃 / 等待 / 暂停
- **关键视图**（按关系+状态）：专题笔记 / 常用笔记 / 会议笔记 / 复盘笔记 / 日记笔记

**对照图示**（FLO.W 笔记 DB 视图切换）：同一份笔记数据库，可以按 Role / Area / sub-Area / Focus / Stage / Today / Create / Edit / Playground 等 9 个维度查看。**这是 Notion「数据库是页面的立体组织和透视」的核心论断的图示**。

### 1.3 三个关键动作（肌肉层）

#### 动作 A：别多想，先记下来（flomo 式捕获）

**问题**：Notion 太重，App 打开到找到数据库那几秒灵感就消失了。

**FLO.W 解决方案**：
- **顶部浮动按钮**作为快速入口（红色 1 标注）
- **底部固定输入框**（不用找页面）
- **不能写标题**（不让你动员额外脑力）
- **按钮自动生成时间戳作为标题**（检索线索但不需要思考）
- **iPhone 快捷指令语音输入 → 转文字 → DeepSeek 加标点 → 自动入库**

**对照图示**（FLO.W 速记设计图）：点击按钮 → 速记 Tab（待整理/已整理）→ 一行输入 + 时间戳自动生成。

#### 动作 B：将下一步动作具体化（Next Action 字段）

**核心发现**：拖延不是因为任务难，而是因为模糊。同一篇文章「写完」可以走 10 条不同路径，而「两条路径可能存在的问题叠加」才是拖延根源。

**解决方案**：每个任务都有「下一步做什么」字段，且必须是**第一次见就能开始做**的具体动作。

```
❌ "继续推进"（模糊）
✅ "翻开笔记本第 23 页"（具体）
```

#### 动作 C：围绕行动去组织信息（按职能而非主题分类）

**对照图示**（FLO.W 笔记 6 种职能分类）：笔记按它能做什么来分类，而不是按它属于什么主题。

| 笔记职能 | 律师知识库对应 |
|---------|--------------|
| 经验 | 案件复盘 / 办案心得 |
| 方法 | 流程模板 / 标准操作 |
| 灵感 | 写作素材 / 业务灵感 |
| 问题 | 研究问题 / 调研难点 |
| 日志 | 办案日志 / 沟通记录 |
| 参考 | 法条 / 案例 / 教材摘录 |

**关键洞察**：标签也是动态的——一篇笔记关联哪个项目/任务/领域，直接决定它的「标签」。**不需要在无数标签里做归纳**，只需要在「当前正在执行的」任务/项目/领域里选。

## 第二篇：项目看板 3.0 的核心设计

### 2.1 核心问题：单一 vs 专注

作者明确了一个认知边界：**专注是能力，单一是局限**。

- **专注**：高效集中注意力完成当下任务
- **单一**：把鸡蛋全装在一个篮子里

绑定过日子：专一琢磨科研 → 错失实习机会 / 努力工作 → 忽视健康 / 全力做一件事 → 卡在半路。所有「专注」的人都容易陷入第二种。

**洞察**：这正是 Casy 设计要避免的——不能让律师觉得「我必须把所有时间都给最重要的案件」。

### 2.2 三种项目分类（核心架构）

| 类型 | 特征 | GTD 策略 | 律师案件对应 |
|------|------|---------|-------------|
| **功利计算型** | 目标明确、可拆解、DDL 驱动 | 重点规划 + 无压执行 | 民事/行政诉讼（起诉/答辩/开庭有明确期限） |
| **探索型** | 目标明确但路径不确定、收益难量化 | 经验积累 + 自由探索 | 专利无效（口审策略需灵活应变） |
| **成长型** | 目标模糊（变得更好）、过程导向 | 打卡驱动 + 习惯养成 | 顾问业务 / 律所品牌建设 / 个人成长 |

**关键洞察**：这三种类型的**评估指标完全不同**——计算型看 DDL 完成率、探索型看里程碑达成、成长型看打卡连续性。Casy 不应该用「完成率」单一指标评估所有案件。

### 2.3 项目书结构（项目详情页模板）

**对照图示**（秋日团建策划项目书）：

```
┌─────────────────────────────────────┐
│ 秋日团建策划          [tags]  [archived] │
├─────────────────────────────────────┤
│ 项目目标                              │
│ 1. 好吃喝好玩好                        │
│ 2. 尽量多人参与                        │
│ 3. 不超预算                            │
│                                      │
│ 规则条件                              │
│ 1. 预算：总预算 5000                    │
│ 2. 日期：2025.10.19                    │
│ 3. 人数：估计不超过 30 人               │
│                                      │
│ 具体计划（任务列表）                     │
│ ☑ 调研 (@2025-09-26)                  │
│ ☑ 出方案 (@2025-09-29)                │
│ ☐ 执行 (@2025-10-19)                  │
└─────────────────────────────────────┘
```

**关键洞察**：项目书是「结构化但自由」的——上半部分有结构（目标/规则/计划），下半部分是普通文本（自由记录）。这是 Casy 案件详情页应该有的形态。

### 2.4 探索型项目的特殊设计

**对照图示**（科研项目结构）：

```
┌─────────────────────────────────────┐
│ 科研                                  │
├─────────────────────────────────────┤
│ 总览                                  │
│ 1. 这是一个模板科研项目                  │
│ 2. 我们假定一个研究课题：                │
│ 3. 假定我们对此一窍不通                  │
│                                      │
│ 📋 科研 - 探索路径 [Canvas]              │
│  [项目方块] ─── [空白方块]               │
│      │              │                  │
│  [空白方块]      [任务方块]             │
│                                      │
│ 任务列表                              │
│ 未完成 ⌛                              │
│ - 调研一下模型方法                       │
│ - 分析一下现有的数据 (@2025-09-29 13:00) │
│                                      │
│ 已完成 ✅                              │
│ - 调研一下字典方法 ✅ 2025-09-27         │
│                                      │
│ 🏆 里程碑                              │
│ - 阶段一：问题定义与基础研究              │
│   - 里程碑 1.1：核心概念定义              │
│   - 里程碑 1.2：技术路线调研              │
│ - 阶段二：最小可行产品开发                │
│   - 里程碑 2.1：数据处理管道搭建          │
│   - 里程碑 2.2：核心算法原型实现          │
└─────────────────────────────────────┘
```

**关键设计**：
- **总览**：3-5 句说明项目是什么
- **探索路径 Canvas**：方块 + 关联线，路径可视化
- **任务列表**：未完成 / 已完成分区
- **里程碑**：嵌套子任务树（阶段 → 里程碑 → 子任务）

**对 Casy 的启示**：律师案件也有阶段（立案 → 庭前 → 庭审 → 判决 → 上诉），也应该有阶段→里程碑→具体行动的嵌套结构。

### 2.5 任务 = Markdown 任务 + @日期标记

**最简实现**：
```markdown
- [ ] 调研一下模型方法 (@2025-09-26)
- [ ] 分析一下现有的数据 (@2025-09-29 13:00)
```

Reminder 插件自动识别 `@日期`，把任务按 Overdue / Today / Over 1 week 分组。

**关键洞察**：**任务语法是文本的一部分，而不是单独的字段**。律师在案件文档里写文本时，自然就把任务标记出来了，不需要切到任务模块去。

### 2.6 时间分配网格（核心交互）

**对照图示**（彩色 Excel 时间表）：

```
       周一  周二  周三  周四  周五  周六  周日
上午  文献  实验   实验   实验  实验   写作  休息
中午  选题  选题   选题   选题  选题
下午  实验         学习   实验  学习  写作
晚上  公共  实验   公共   实验  学习
睡前  阅读  阅读   阅读   阅读  阅读  阅读  阅读
```

**关键设计**：
- **行 = 时间块**（上午/中午/下午/晚上/睡前）
- **列 = 周一/二/三/.../周日**
- **颜色 = 项目类型**（蓝色 = 成长型，紫色 = 探索型，绿色 = 计算型，橙色 = 休息）

**分配策略**：
1. 先排**计算型**（DDL 驱动，固定时间）
2. 再排**成长型**（每周固定时间，养成习惯）
3. 最后剩余时间给**探索型**（不计成本追求探索）

**对 Casy 启示**：律师日历不该只是「开庭/口审/期限」的硬性日程，应该有「开庭 + 起草 + 沟通 + 调研」的时间块分配，颜色按案件类型区分。

### 2.7 自动化机制

| 自动化 | Obsidian 怎么实现 | Casy 怎么实现 |
|--------|-----------------|--------------|
| 周报生成 | periodic notes + Dataview | 每周自动生成「案件周报」合并所有相关任务/日志 |
| 月报生成 | periodic notes + Dataview | 每月自动生成「案件月报」含轨迹、统计、复盘 |
| 项目分表 | Bases + Filter | 案件按轨道（专利/民诉/行政）自动分组视图 |
| 项目总表 | Bases + Filter | 案件全局视图（按代数/客户/状态） |
| Reminder 提醒 | Reminder 插件 | 任务 → 期限引擎 → 多通道提醒（已实现） |

## 跨文章共识：3 个底层原则

两篇文章基于完全不同的工具（Notion vs Obsidian），但得出惊人一致的设计原则：

### 原则 1：数据有结构，访问有层次

> FLO.W：4 个数据库 + 3 层过滤
> 项目看板 3.0：3 种项目类型 + 项目书结构

**核心**：底层数据有限、严谨；上层视图丰富、灵活。**Casy 现在的反向——底层数据散乱（每个模块独立 schema），上层视图单一**。

### 原则 2：捕获必须极简，组织可以稍后

> FLO.W：底部固定输入框 + 自动时间戳
> 项目看板 3.0：Markdown 任务 + @日期

**核心**：要求用户思考「这条信息去哪个数据库」是反人性的。**Casy 现在的收件箱强分类太早**——用户还没说清楚「这是什么」，AI 就强制分类了。

### 原则 3：评估需匹配项目类型

> FLO.W：项目状态（执行/待办/调研）+ 任务进度条
> 项目看板 3.0：计算型看 DDL，成长型看打卡，探索型看里程碑

**核心**：单一指标评估所有项目会让用户焦虑。**Casy 应该让不同类型的案件有不同的「完成度」展示**。

## 对 Casy 的具体启示（按模块）

### 启示 1：导航架构应该重构

**现状**：左侧侧边栏 7 个固定菜单（首页/案件/任务/日历/收件箱/知识库/设置），平铺。

**问题**：所有菜单同级，用户必须自己决定「现在该去哪个」。

**改造建议**：

```
Casy 导航（三层结构）：

【第一层：全局聚合（顶栏）】
  ✓ 今日（硬性日程 + 期限 + 等待超过 3 天）
  ✓ 收件箱（未处理项）
  ✓ 我（我的任务 + 我的案件）

【第二层：核心模块（左侧侧栏）】
  📁 案件 Workspace（按轨道分组）
  ✓ 任务工作台（GTD 5 透视）
  📅 日历（Forecast 左右布局）
  📚 知识库（按职能分类）
  📥 收件箱（已整理 / 待整理）
  ⚙️ 设置

【第三层：模块内（顶部 Tab）每个模块独立】
  案件 Workspace：所有案件 / 我负责 / 等待中 / 已结案 / 案件周报
  任务工作台：下一步行动 / 等待 / 今日 / 项目视图 / 回顾
  知识库：经验 / 方法 / 灵感 / 问题 / 日志 / 参考
```

**关键设计**：
- **顶部「今日」永远显示当天前三件大事**（硬性日程 + 高优先级任务 + 等待超时）
- **左侧浮动快速捕获按钮**（任务 / 日程 / 笔记 / 速记）
- **每个模块顶部同步块导航栏**（4 个核心模块 + 临时模块）

### 启示 2：案件应该重构为「项目」

**现状**：案件是数据库的一张记录，字段硬编码（45 个），没有项目书结构。

**改造建议**：

**案件详情页（项目书）**：

```
[顶部] 案件概要 + tags + 状态徽章 + 关联资源

[第一栏] 项目总览
  1. 案件目标（30 字以内）
  2. 案件类型（计算型/探索型/成长型，自动判断）
  3. 关键里程碑（嵌套列表：阶段 → 里程碑 → 任务）

[第二栏] 详细信息（按轨道三轨分别展示）
  诉讼轨：立案/庭前/庭审/判决/上诉
  无效轨：受理/口审/决定
  行政轨：复审/诉讼

[第三栏] 关联资源
  任务（4 个统计：行动/等待/已完成/逾期）
  文书（按类型：答辩状/上诉状/代理词）
  知识引用（关联的笔记/法条）
  沟通记录（邮件/IMAP 关联）

[第四栏] 动态轨迹
  时间线（状态变迁/重要事件/期限）
  收件箱自动入库
  案件日志
```

### 启示 3：任务模块的 5 透视 + 4 类型

**重写任务模块**（基于两篇文章 + gtd-design.md）：

```
任务工作台顶部 Tab：
├── 📥 收件箱（未厘清项）
├── ✅ 下一步行动（type=action）
├── ⏳ 等待（type=waiting，显示「等谁 N 天」）
├── 📅 今日（due_date=today OR calendar_event）
├── 🔄 回顾（项目健康度，每案行动/等待/已完成/卡住）
└── 📊 全部（按项目分组视图）

任务类型（task_type）：
- action：下一步行动
- waiting：等待（等法院/对方/客户）
- delegated：委派
- someday：也许有一天
- reference：参考资料（不提醒）

每任务必填：
- next_action（下一步具体动作）
- project_id（关联案件）
- due_date（截止日期）
- defer_date（推迟/开始日期）
```

### 启示 5：知识库按职能而非主题分类

**现状**：知识库按 `category`（法律法规/案例/模板/诉讼策略）分类。

**问题**：分类是主题，不是职能。律师找资料时不是想「我想看法」，而是「我想找应对方案/看类似案例/查具体条文」。

**改造建议**：

```
知识库分类（按职能）：
├── 💡 灵感（案件触发的灵感、业务洞察）
├── 📋 方法（标准流程、操作模板）
├── 📚 参考（法条、案例、教材摘录）
├── ❓ 问题（待研究问题、调研难点）
├── 📝 经验（办案复盘、心得）
└── 📔 日志（会议纪要、沟通记录）

每条知识带：
- type（6 种职能之一）
- related_to（关联案件/任务/领域）
- useful_at（什么时候能用上）
```

### 启示 6：捕获系统应极简

**现状**：收件箱要求 AI 强分类（案件/任务/笔记/期限），用户必须接受自动分类。

**改造建议**：

```
快速捕获机制（按 FLO.W + 项目看板 3.0）：

[顶部浮动按钮] 4 个动作：
  + 任务（Cmd+T）→ 弹极简输入框（标题自动 = 时间戳）
  + 日程（Cmd+E）→ 弹极简输入框（标题 + 日期）
  + 笔记（Cmd+N）→ 弹极简输入框（多文本 + 标签）
  + 速记（Cmd+I）→ 弹极简输入框（纯文本）

所有输入框：
- 标题自动生成（不让你想）
- 底部提交后默认进「收件箱」待整理
- 整理界面视图：左原始收件箱，右判定面板（这是什么/项目/优先级/截止）
```

**关键洞察**：**先捕获后整理**，不要捕获时强行分类。

## 三个值得深入探索的方向

1. **「下一步做什么」字段是核心竞争力**。FLO.W 作者明确说这是「拖延症的解药」。Casy 应该在每个任务和每个案件详情里都有这个字段，且不容许空值。

2. **「预判警报」是律师独有的 GTD 需求**。FLO.W 把「预期警报」作为任务的一种类型。律师有大量「未来才会用到的任务」——「等判决下来后写上诉状」「等对方提交答辩后开准备会议」。这是 OmniFocus 的 Deferred 机制 + 律师业务的结合。

3. **「项目健康度」是项目看板 3.0 的核心洞察**。只看「完成率」会让所有项目都焦虑。应该用差异化评估：计算型看 DDL 完成率、探索型看里程碑达成、成长型看打卡连续性。
